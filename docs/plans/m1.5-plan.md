# M1.5 Plan — Always On

> The bar: **what is left before this becomes "a tool left running and used every day."**
> Ordered not by feature list but by what is actually blocking real use.
>
> **This document is the plan after M1. M1 is complete** ([m1-result.md](m1-result.md)).

## What changed from the original M1.5

The M1.5 in product-spec §8 was 4 "reliability" items. Along the way, 2 of them finished early, and
after the G5 measurement the scope was **widened and redefined as "always on."** Comparison table:

| Original M1.5 item | Current status |
|---|---|
| Restart recovery (FR-10) | Still outstanding → **C-1** |
| Context gauge (FR-14) | **Done in M1** (shown as a % in the session header, confirmed measured in G5) |
| Limit status `limited` + reset time (part of FR-9) | **Done in M1** (limit badge + reset time) |
| Polishing the first-run experience (FR-19) | Still outstanding → **E-1** |

On top of this, items originally in later milestones were pulled forward:

| Pulled forward | Original location | Why it was pulled forward |
|---|---|---|
| Tauri migration steps 1–3 | around M3 | notifications, badges and global shortcuts are all tied to this |
| OS notifications and badges | M2 | "so nothing is missed" is the whole reason the control tower exists, and the web cannot implement it |
| Virtual scrolling and windowing | (a known limitation from m1-result) | felt immediately once sessions run long |

Conversely, **the Codex adapter was pushed back to M2** (M2 is where it originally was anyway, so nothing moves).

## Current state, summarized

M1 got the control loop turning (G5 measured and complete, [m1-result.md](m1-result.md)).
But it is not yet **something that can stay on through the workday.** Three things block it:

| What blocks it | What happens now |
|---|---|
| 2 terminals have to be started by hand | `pnpm host` + `pnpm dev`. Stopping and restarting costs enough that "just take a quick look" is not really an option |
| A dead host kills the sessions with it | The record survives, but the conversation cannot continue. A new session has to be created |
| Stepping away means missing approvals | Sitting behind a browser tab, there is no way to know. This defeats the whole reason the control tower exists |

All three were out of M1 scope on purpose, but **until these three are solved, there is no occasion to use Codex or a git panel either.**
So the next milestone is set not as adding features but as **always on.**

## M1.5 — Always on (next up, recommended)

Goal: **launches from a single app icon, picks back up after being stopped and restarted, and nothing is missed while away.**

### A. Desktop shell (Tauri steps 1–3)

Follows the playbook in [platform-abstraction.md §5](../platform-abstraction.md) exactly. Steps 1
through 3 alone reach the goal, and **not a single line of UI code changes** (the payoff moment for
the design).

- **A-1. Create `apps/desktop` + supervise the sidecar** — Tauri spawns agent-host, reads the port
  and token from stdout and hands them to the UI. Restarts it if a crash is detected.
  - Done: launch the app → create a session and finish a conversation with no terminal (Level 3 S1)
  - Done: `kill -9` on the host still lets the app auto-restart it, and the UI transitions "disconnected → connected" (Level 4 L4-2)
  - Done: the sidecar dies with the app on quit (no zombie processes — confirmed with `pgrep`)
- **A-2. `createTauriPlatform()` = reuse the web implementation** — it is all delegated over WS, so there is almost no new code.
  - Done: the same contract test suite passes against the tauri implementation too (web/mock, 2 today, → 3)
  - Done: **the ui package diff is 0 lines** — whether the design actually kept its promise (`git diff --stat packages/ui`)
- **A-3. Swap the system port for a Tauri plugin** — notifications, dock badge, global shortcuts, opening in the IDE.
  Flipping the capability to true switches on the corresponding UI feature by itself (already designed that way).
  - Done: forcing the capability to false does not break the UI — only that feature hides (web-fallback regression)

### B. Not missing anything (notifications)

- **B-1. OS notification on approval or error** — clicking it jumps to that session.
  - Done: Level 4 L4-1 (stepping away) measured. No notification fires while the app is in the foreground
- **B-2. Dock icon badge** — the pending count. Whether it counts approvals only or everything gets decided after trying it.
- **B-3. A single "all done" notification (1×)** — when every session has finished its work (the policy decided in product-spec).
- **B-4. Global shortcut** — ⌘⇧A pulls up pending sessions even while the app is in the background.

### C. Not getting cut off (recovery)

- **C-1. Session resume (FR-10)** — on a host restart, attempt `resume` with the stored external_id.
  On success the conversation continues right where it left off; on failure it falls back to "view the record + new session" as today.
  SDK resume was already verified in M0 (confirmed it remembers the earlier conversation).
  - Done: Level 3 S5 — after a restart, "what did I say earlier?" gets answered from the earlier context
  - Done: Level 3 S6 — deliberately corrupting the external_id to fail resume does not die silently
- **C-2. Persistent restore of approval rules** — "always allow" currently lives only in session memory.
  Wire it up to the store's `approval_rules` for real (the table already exists).
- **C-3. Workspace snapshot** — restore window layout, the focused session and read position.

### D. Holding up at scale

- **D-1. Virtual scrolling for the conversation** — the current structure struggles once messages run into the hundreds.
  `@tanstack/react-virtual` is already installed and unused.
  - Done: Level 3 S8 — scrolling and streaming stay smooth in conversations of 100+ turns
  - Done: auto-scroll during streaming does not fight the user's scroll-up (no yanking someone back down while they are reading)
- **D-2. Message windowing** — release messages for unfocused sessions (per the design in [state-management.md §4](../state-management.md)).
- **D-3. Performance measurement** — measure against the §7.1 target with 4 idle sessions (only the host has been measured so far).

### E. The person opening it for the first time (an original M1.5 item that got dropped)

- **E-1. First-run experience (FR-19)** — actually design the three empty states:
  the CLI not installed (copy the install command), not logged in (guidance + re-detect), 0 projects (one flow from first registration to first session).
  Right now the sidebar just shows one line, "no registered projects," and `agents.detect` exists only as an RPC that nothing on screen calls.
  Once this is a Tauri app, the person opening it for the first time is myself, so this goes together with A.
  - Done: deliberately hiding the CLI path to fake a not-installed state still lets the app launch and tells the person what to do
  - Done: Tauri uses a directory picker to choose a project (typing a path is the web-dev fallback)

## Decisions worth noting

1. **Why the Tauri migration was pulled into M1.5** — the original roadmap had it around M3, but the
   cost of entry into real use is the biggest friction, and notifications, badges and global
   shortcuts are all tied to Tauri. The control tower's core value ("so nothing is missed") cannot
   be implemented on the web.
2. **Why Codex was pushed to M2** — adding more tools means nothing if it is not turned on every day.
   Always-on comes first. The adapter work itself is low-risk thanks to the M0 verification.
3. **The remaining open question** — how the unit-price table for usage cost estimation gets managed (decided in M3).

## Dogfooding timing (decided 2026-08-15)

Instead of using it myself right after M1, **the improvement-through-real-use pass happens only
after M2 is fully built** (the user's decision). Reasoning: right now there is no git panel, file
tree, search or attachments, so it is hard to do more than "take a quick look," and impressions
from using it in that state would only confirm a conclusion already known (the features are not there).

So one "use it myself, then improve" phase is placed at the end of the milestones:

- M1.5 → M2 run back to back (no human check in between, automated gates only)
- After M2 is done, a **real-use period** — run it on a real project for a few days
- Whatever complaints come out of that become a backlog handled as the **M2.5 improvement phase**
- Then M3 (usage dashboard, orchestrator)

The cost of this order is "finding out what was built wrong, late." To reduce that:
at the end of each phase, an agent runs the control loop once with a real session and leaves behind
a G5-style measurement (this is how M1 caught its 3 defects).

# Verification protocol

The lesson from M1: **3 real-use defects still survived while all 180+16 unit and E2E tests passed.**
The types the automated tests missed were all distinct in character — focus state, a dead session, a
visual regression. So verification is split into 5 levels, and **each level states plainly what it
cannot catch.**

## Model and cost policy (decided 2026-08-15)

Cost is not a constraint (Max plan). Do not be sparing with real sessions for verification.
That said, **do not use the top-tier model for verification** — verification is high-volume and
repetitive, so there is no reason to burn a top-tier model on it.

| Purpose | Model |
|---|---|
| Baseline verification sessions (approval round trip, state transitions, streaming) | Claude **haiku** / Codex **default model** |
| Verification needing judgment (complex multi-turn, tool combinations) | Claude **sonnet** |
| Top-tier (Claude Fable, Codex top-tier) | **Not used for verification.** Only when design or implementation judgment is needed |
| Load verification (many concurrent sessions, long conversations) | haiku — this is a volume game, so a higher-tier model is wasted |

Real-session verification is **mandatory at the end of every phase**, and the run log is left in `docs/spikes/`.

## Level 1 — unit and contract (`pnpm test`)

- Scope: core pure functions, protocol schemas, adapter conversions, the store, EventLog
- Rule: **a new rule added to core must be tested here first** (reimplementing it as an if statement in the UI is not allowed)
- Contract tests grow their targets as implementations grow (web/mock, 2 today, → 3 once tauri is added)
- **What this cannot catch**: wiring mistakes, focus/event ordering, render output

## Level 2 — E2E (`pnpm e2e`, mock platform)

3 authoring rules — these block exactly what caused M1 to miss defects:

1. **Reproduce the real order of use exactly.** Do not click `body` before a key press.
   Focus staying in the composer right after a message is sent is the normal state.
2. **Always include one case per abnormal state.** Sending to a dead session, a dropped connection,
   an empty response, a permission denial, hitting a limit. A feature with only a "happy path" is
   considered unfinished.
3. **Verify the cleanup too.** Whether the screen actually tidies up after an archive, an interrupt or a rejection.

- **What this cannot catch**: contract drift from the real SDK, style breakage, performance

## Level 3 — real-session smoke (`pnpm smoke`, real host + real CLI)

Run by an agent at the end of each phase. Scenario catalogue (what M1.5 needs):

| # | Scenario | Pass criteria |
|---|---|---|
| S1 | Approval request → allow with `y` → complete | The file is actually created and status goes to `waiting_input` |
| S2 | Approval request → reject with `n` | The agent registers the rejection and ends the turn, no file created |
| S3 | Approval request → `a` always allow → re-request the same command | The second one passes with no approval (confirms the rule applies) |
| S4 | Interrupt mid-task | Status returns to `waiting_input` and the process stays alive |
| S5 | **Resume after a host restart** (new in M1.5) | The same session continues, remembering the earlier conversation |
| S6 | **Fallback when resume fails** (new in M1.5) | Shows "view the record + new session," no silent failure |
| S7 | 3 sessions running concurrently | Events do not get mixed up between sessions, the inbox sorts correctly |
| S8 | A long conversation (100+ turns) | Scrolling and memory are normal, no streaming lag |

- The run log is committed as `docs/spikes/<phase>-smoke-log.txt` (the same approach as M1's g3-smoke-log.txt)
- **What this cannot catch**: long-running leaks, visual regressions

## Level 4 — reproducing real-use conditions (new in M1.5)

The layer that was missing the most in M1. **An agent operates the browser/app directly**, mimicking
the order a person would follow.

- **L4-1. Stepping-away scenario** — with 3 sessions running, send the app to the background, then
  check whether an OS notification actually arrives when an approval fires → and whether clicking it
  jumps to that session
- **L4-2. Interrupt and resume** — force-kill the host (`kill -9`), then restart it. Check session
  recovery, whether any events were lost, and whether the UI transitions accurately from
  "disconnected" to "connected"
- **L4-3. Repeated operation** — process 10 items in the inbox back to back, keyboard only. Check
  that cursor position and auto-advance do not drift
- **L4-4. Window size** — check that the layout does not break in a narrow window (1024px) or a large one

## Level 5 — visual regression (new in M1.5)

A missing Tailwind source detection let **all 16 E2E tests pass even with CSS completely empty.**
This level blocks that class of failure.

- **L5-1. Style-presence check** — grep the built CSS for the key utilities (`bg-void`, `.keycap`).
  Fail if missing (a 1-line test is enough, and it catches exactly this incident)
- **L5-2. Screenshot baseline** — capture and store the 4 main screens (empty state, session, inbox, approval).
  An agent compares them by eye on change, and updates the baseline if the change was intentional
- **L5-3. Contrast check** — with an achromatic palette, lightness contrast is readability. Measure the contrast ratio of body and secondary text

## Phase-end checklist

A phase is considered done only once all of the following are satisfied:

- [ ] `pnpm verify` passes (lint, dependency rules, types, unit)
- [ ] `pnpm e2e` passes, at least **1 happy path + 1 abnormal case** per new feature
- [ ] The Level 3 scenarios relevant to this phase have been run, log committed
- [ ] At least 1 Level 4 case reproduced (whichever real-use condition this phase changed)
- [ ] Level 5 screenshots compared
- [ ] Defects found are **fixed with a regression test added** — not just written down and left
- [ ] Decisions made during this phase are recorded in the result document (so a person can reverse them later)

## When starting

Same approach as M1: attach done criteria to each phase's tasks, with a single human check at the
dogfooding point. The difference is that the verification protocol above is **enforced as part of
the done criteria.**
