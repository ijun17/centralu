# M1.5 실행 플랜 — 상시 가동

> 기준: **"매일 켜두고 쓰는 도구"가 되기까지 무엇이 남았는가.**
> 기능 목록 순서가 아니라, 실제 사용을 막고 있는 것 순서로 정렬한다.
>
> **이 문서는 M1 이후 계획이다. M1은 완료됐다** ([m1-result.md](m1-result.md)).

## 원래 M1.5와 무엇이 달라졌나

product-spec §8의 M1.5는 "신뢰성" 4개 항목이었다. 실제 진행하며 2개가 앞당겨 끝났고,
G5 실측 후 **범위를 넓혀 "상시 가동"으로 재정의**했다. 대조표:

| 원래 M1.5 항목 | 현재 상태 |
|---|---|
| 재시작 복원 (FR-10) | 그대로 남음 → **C-1** |
| 컨텍스트 게이지 (FR-14) | **M1에서 완료** (세션 헤더에 % 표시, G5에서 실측 확인) |
| 한도 상태 `limited` + 해제 시각 (FR-9 일부) | **M1에서 완료** (한도 뱃지 + 해제 시각) |
| 첫 실행 경험 다듬기 (FR-19) | 그대로 남음 → **E-1** |

여기에 원래 뒤쪽 마일스톤에 있던 것을 앞으로 당겼다:

| 당겨온 것 | 원래 위치 | 당긴 이유 |
|---|---|---|
| Tauri 전환 1~3단계 | M3 근처 | 알림·뱃지·전역 단축키가 전부 여기 묶여 있다 |
| OS 알림·뱃지 | M2 | "놓치지 않게"는 관제탑의 존재 이유인데 웹에서는 구현 불가 |
| 가상 스크롤·윈도잉 | (m1-result의 알려진 한계) | 세션이 길어지면 바로 체감된다 |

반대로 **Codex 어댑터는 M2로 미뤘다** (원래 M2 그대로 유지).

## 지금 상태 요약

M1은 관제 루프가 도는 것까지 왔다 (G5 실측 완료, [m1-result.md](m1-result.md)).
하지만 아직 **일과 중에 계속 켜둘 수 있는 상태는 아니다.** 막는 것 셋:

| 막는 것 | 지금 무슨 일이 벌어지나 |
|---|---|
| 터미널 2개를 직접 띄워야 함 | `pnpm host` + `pnpm dev`. 껐다 켜는 비용이 커서 "잠깐 열어보기"가 안 된다 |
| host가 죽으면 세션도 죽음 | 기록은 남지만 대화를 못 이어간다. 새 세션을 만들어야 한다 |
| 자리를 뜨면 승인을 놓침 | 브라우저 탭 뒤에 있으면 알 방법이 없다. 관제탑의 존재 이유가 무력화된다 |

셋 다 M1 범위 밖이었고 의도된 것이지만, **이 셋을 해결하기 전에는 Codex든 깃 패널이든 쓸 일이 없다.**
그래서 다음 마일스톤은 기능 추가가 아니라 **상시 가동**으로 잡는다.

## M1.5 — 상시 가동 (다음 작업, 권장)

목표: **앱 아이콘 하나로 뜨고, 껐다 켜도 이어지고, 자리를 비워도 놓치지 않는다.**

### A. 데스크톱 셸 (Tauri 1~3단계)

[platform-abstraction.md §5](../platform-abstraction.md)의 플레이북을 그대로 따른다.
1~3단계까지만 해도 목표가 달성되고, **UI 코드는 한 줄도 안 바뀐다** (설계의 회수 시점).

- **A-1. `apps/desktop` 생성 + 사이드카 수퍼바이즈** — Tauri가 agent-host를 spawn하고,
  포트·토큰을 stdout에서 읽어 UI에 전달. 크래시 감지 시 재시작.
  - 완료: 앱 실행 → 터미널 없이 세션 생성·대화 완주 (레벨 3 S1)
  - 완료: host를 `kill -9` 해도 앱이 자동 재기동하고 UI가 "연결 끊김 → 연결됨"으로 전이 (레벨 4 L4-2)
  - 완료: 앱 종료 시 사이드카가 함께 죽는다 (좀비 프로세스 없음 — `pgrep`으로 확인)
- **A-2. `createTauriPlatform()` = web 구현 재사용** — 전부 WS 위임이라 신규 코드가 거의 없다.
  - 완료: 같은 계약 테스트 스위트가 tauri 구현에서도 통과 (지금 web/mock 2개 → 3개)
  - 완료: **ui 패키지 diff가 0줄** — 설계가 약속한 것이 실제로 지켜졌는지 (`git diff --stat packages/ui`)
- **A-3. system 포트를 Tauri 플러그인으로 교체** — 알림·독 뱃지·전역 단축키·IDE로 열기.
  capability가 true로 바뀌며 UI 기능이 저절로 켜진다 (이미 그렇게 설계돼 있음).
  - 완료: capability를 false로 강제해도 UI가 깨지지 않고 해당 기능만 숨는다 (웹 폴백 회귀)

### B. 놓치지 않기 (알림)

- **B-1. 승인·오류 발생 시 OS 알림** — 클릭하면 해당 세션으로 점프.
  - 완료: 레벨 4 L4-1(자리 비움) 실측. 앱이 포그라운드일 때는 알림을 띄우지 않는다
- **B-2. 독 아이콘 뱃지** — 대기 건수. 승인만 셀지 전부 셀지는 써보고 정한다.
- **B-3. "전부 완료" 알림 1회** — 모든 세션이 일을 마쳤을 때 (product-spec에서 결정한 정책).
- **B-4. 전역 단축키** — 앱이 백그라운드일 때도 ⌘⇧A로 대기 세션 호출.

### C. 끊기지 않기 (복원)

- **C-1. 세션 resume (FR-10)** — host 재시작 시 저장된 external_id로 `resume` 시도.
  성공하면 대화를 그대로 이어가고, 실패하면 지금처럼 "기록 보기 + 새 세션"으로 폴백.
  M0에서 SDK resume은 이미 검증됨 (이전 대화 기억 확인).
  - 완료: 레벨 3 S5 — 재시작 후 "아까 뭐라고 했지?"에 이전 맥락으로 답한다
  - 완료: 레벨 3 S6 — external_id를 일부러 훼손해 resume을 실패시켜도 조용히 죽지 않는다
- **C-2. 승인 규칙 영속 복원** — "항상 허용"이 지금은 세션 메모리에만 있다.
  store의 `approval_rules`와 실제로 연결한다 (테이블은 이미 있음).
- **C-3. 워크스페이스 스냅샷** — 창 레이아웃·포커스 세션·읽음 위치 복원.

### D. 규모 견디기

- **D-1. 대화 가상 스크롤** — 메시지 수백 개 넘어가면 지금 구조는 버겁다.
  `@tanstack/react-virtual`은 이미 설치돼 있고 안 쓰고 있다.
  - 완료: 레벨 3 S8 — 100턴 이상 대화에서 스크롤·스트리밍이 매끄럽다
  - 완료: 스트리밍 중 자동 스크롤이 사용자의 위로 스크롤을 방해하지 않는다 (읽는 중 끌어내리기 금지)
- **D-2. 메시지 윈도잉** — 비포커스 세션 메시지 해제 ([state-management.md §4](../state-management.md) 설계대로).
- **D-3. 성능 실측** — 세션 4개 유휴 상태에서 §7.1 목표 대비 측정 (지금은 host만 쟀다).

### E. 처음 여는 사람 (원래 M1.5 항목, 빠뜨렸던 것)

- **E-1. 첫 실행 경험 (FR-19)** — 세 가지 빈 상태를 실제로 설계한다:
  CLI 미설치(설치 명령 복사), 로그인 안 됨(안내 + 재감지), 프로젝트 0개(첫 등록 → 첫 세션 한 흐름).
  지금은 사이드바에 "등록된 프로젝트가 없습니다" 한 줄뿐이고, `agents.detect`는 RPC로 만들어만 두고
  화면에서 쓰지 않는다. Tauri 앱이 되면 처음 여는 사람이 곧 나 자신이므로 A와 같이 간다.
  - 완료: CLI 경로를 일부러 가려 미설치 상태를 만들어도 앱이 뜨고, 무엇을 해야 하는지 알려준다
  - 완료: Tauri에서는 디렉토리 피커로 프로젝트를 고른다 (경로 타이핑은 웹 dev 폴백)

## M2 — 관제 완성 (그다음)

상시 가동이 되고 나면 그때 폭을 넓힌다.

- **Codex 어댑터** — M0에서 프로토콜을 이미 다 파악했고 타입 생성기도 확인했다.
  어댑터 하나만 추가하면 UI·core·protocol은 그대로 (C3 설계 검증의 실전 시험).

## 짚어둘 결정 사항

1. **Tauri 전환을 M1.5로 당긴 이유** — 원래 로드맵은 M3 근처였지만, 실사용 진입 비용이
   가장 큰 마찰이고 알림·뱃지·전역 단축키가 전부 Tauri에 묶여 있다. 관제탑의 핵심 가치
   ("놓치지 않게")가 웹에서는 구현 불가능하다.
2. **Codex를 M2로 미룬 이유** — 도구가 늘어도 매일 안 켜면 의미가 없다.
   상시 가동이 먼저다. 어댑터 작업 자체는 M0 검증 덕에 위험이 낮다.
3. **남은 열린 질문** — 사용량 비용 추정의 단가 테이블 관리 방식 (M3에서 결정).

## 도그푸딩 시점 (2026-08-15 결정)

M1 직후에 직접 써보는 대신, **M2까지 다 만든 뒤에 실사용하며 개선한다** (사용자 결정).
근거: 지금은 깃 패널·파일 트리·검색·첨부가 없어 "잠깐 열어보기" 이상을 하기 어렵고,
그 상태의 사용 소감은 이미 아는 결론(기능이 없다)만 확인하게 된다.

그래서 마일스톤 끝에 **"직접 사용 후 개선" 페이즈를 하나 둔다**:

- M1.5 → M2를 연속으로 진행 (중간 사람 확인 없음, 자동 게이트만)
- M2 완료 후 **실사용 기간** — 실제 프로젝트로 며칠 굴린다
- 거기서 나온 불만을 백로그로 만들어 **M2.5 개선 페이즈**로 처리
- 그다음 M3 (사용량 대시보드·오케스트레이터)

이 순서의 대가는 "잘못 만든 것을 늦게 안다"는 것이다. 이를 줄이기 위해:
각 페이즈 완료 시 에이전트가 실 세션으로 관제 루프를 한 번씩 돌려 G5와 같은 실측을 남긴다
(M1에서 이 방식으로 결함 3건을 잡았다).

# 검증 프로토콜

M1의 교훈: **단위·E2E 180+16개가 전부 통과하는 상태에서도 실사용 결함 3건이 남아 있었다.**
자동 테스트가 놓친 유형은 셋 다 성격이 뚜렷했다 — 포커스 상태, 죽은 세션, 시각 회귀.
그래서 검증을 5개 레벨로 나누고, **레벨마다 "무엇을 못 잡는지"를 명시**한다.

## 모델·비용 정책 (2026-08-15 결정)

비용은 제약이 아니다 (Max 플랜). 검증에 실 세션을 아끼지 말고 쓴다.
단 **최상위 모델은 검증에 쓰지 않는다** — 검증은 양이 많고 반복되므로 상위 모델을 태울 이유가 없다.

| 용도 | 모델 |
|---|---|
| 기본 검증 세션 (승인 왕복, 상태 전이, 스트리밍) | Claude **haiku** / Codex **기본 모델** |
| 판단이 필요한 검증 (복잡한 다중 턴, 도구 조합) | Claude **sonnet** |
| 최상위 (Claude Fable, Codex 최상위) | **검증에 쓰지 않는다.** 설계·구현 판단이 필요할 때만 |
| 부하 검증 (동시 세션 다수, 긴 대화) | haiku — 양으로 승부하는 구간이라 상위 모델은 낭비 |

실 세션 검증은 **매 페이즈 종료 시 필수**이며, 실행 로그를 `docs/spikes/`에 남긴다.

## 레벨 1 — 단위·계약 (`pnpm test`)

- 대상: core 순수 함수, protocol 스키마, 어댑터 변환, store, EventLog
- 규칙: **core에 새 규칙을 넣으면 반드시 여기서 먼저 테스트한다** (UI에서 if문으로 재구현 금지)
- 계약 테스트는 구현이 늘어날 때마다 대상도 늘린다 (지금 web/mock 2개 → tauri 추가 시 3개)
- **못 잡는 것**: 배선 오류, 포커스·이벤트 순서, 렌더 결과

## 레벨 2 — E2E (`pnpm e2e`, mock platform)

작성 규칙 3가지 — M1에서 결함을 놓친 원인을 그대로 막는다:

1. **실사용 순서를 그대로 재현한다.** 키 입력 전에 `body`를 클릭하지 않는다.
   메시지를 보낸 직후엔 입력창에 포커스가 남아 있는 상태가 정상이다.
2. **비정상 상태를 반드시 한 케이스씩 넣는다.** 죽은 세션에 전송, 연결 끊김, 빈 응답,
   권한 거부, 한도 도달. "행복 경로"만 있는 기능은 미완성으로 본다.
3. **정리 동작까지 검증한다.** 아카이브·중단·거부 후 화면이 실제로 정리되는지.

- **못 잡는 것**: 실 SDK와의 계약 차이, 스타일 붕괴, 성능

## 레벨 3 — 실 세션 스모크 (`pnpm smoke`, 실 host + 실 CLI)

페이즈 종료 시 에이전트가 실행한다. 시나리오 카탈로그 (M1.5에서 필요한 것):

| # | 시나리오 | 통과 기준 |
|---|---|---|
| S1 | 승인 요청 → `y` 허용 → 완료 | 파일이 실제로 생성되고 상태가 `waiting_input`으로 |
| S2 | 승인 요청 → `n` 거부 | 에이전트가 거부를 인지하고 턴을 마침, 파일 미생성 |
| S3 | 승인 요청 → `a` 항상 허용 → 같은 명령 재요청 | 두 번째는 승인 없이 통과 (규칙 적용 확인) |
| S4 | 작업 중 중단(interrupt) | 상태가 `waiting_input`으로 돌아오고 프로세스가 살아 있음 |
| S5 | **host 재시작 후 resume** (M1.5 신규) | 같은 세션에서 이전 대화를 기억한 채 이어짐 |
| S6 | **resume 실패 시 폴백** (M1.5 신규) | "기록 보기 + 새 세션" 안내, 조용한 실패 없음 |
| S7 | 세션 3개 동시 진행 | 이벤트가 세션별로 섞이지 않음, 인박스 정렬 정확 |
| S8 | 긴 대화 (100턴 이상) | 스크롤·메모리 정상, 스트리밍 지연 없음 |

- 실행 로그는 `docs/spikes/<phase>-smoke-log.txt`로 커밋한다 (M1의 g3-smoke-log.txt 방식)
- **못 잡는 것**: 장시간 누수, 시각 회귀

## 레벨 4 — 실사용 조건 재현 (M1.5 신설)

M1에서 가장 크게 빠져 있던 층. **에이전트가 브라우저/앱을 직접 조작해** 사람이 하는 순서를 흉내낸다.

- **L4-1. 자리 비움 시나리오** — 세션 3개를 돌려놓고 앱을 백그라운드로 보낸 뒤,
  승인이 발생했을 때 OS 알림이 실제로 오는지 → 클릭 시 해당 세션으로 점프하는지
- **L4-2. 중단·재개** — host를 강제 종료(`kill -9`)했다가 재시작. 세션 복원, 이벤트 유실 여부,
  UI가 "연결 끊김 → 연결됨"으로 정확히 전이하는지
- **L4-3. 반복 조작** — 인박스에서 10건을 키보드만으로 연속 처리. 커서 위치·자동 이동이 어긋나지 않는지
- **L4-4. 창 크기** — 좁은 창(1024px)·큰 창에서 레이아웃이 깨지지 않는지

## 레벨 5 — 시각 회귀 (M1.5 신설)

Tailwind 소스 탐지 누락으로 **CSS가 통째로 비어도 E2E 16개가 전부 통과**했다. 이 유형을 막는다.

- **L5-1. 스타일 존재 검증** — 빌드된 CSS에 핵심 유틸리티(`bg-void`, `.keycap`)가 있는지 grep.
  없으면 실패 (테스트 1줄이면 되고, 이번 사고를 정확히 잡는다)
- **L5-2. 스크린샷 기준선** — 주요 화면 4개(빈 상태·세션·인박스·승인)를 캡처해 저장.
  변경 시 에이전트가 눈으로 대조하고, 의도된 변경이면 기준선을 갱신한다
- **L5-3. 대비 확인** — 무채색 팔레트라 명도 대비가 곧 가독성이다. 본문·보조 텍스트의 대비비 측정

## 페이즈 종료 체크리스트

각 페이즈는 아래를 전부 만족해야 끝난 것으로 본다:

- [ ] `pnpm verify` 통과 (lint·의존 규칙·타입·단위)
- [ ] `pnpm e2e` 통과, 새 기능마다 **행복 경로 1 + 비정상 1** 이상
- [ ] 레벨 3 시나리오 중 해당 페이즈 관련 항목 실행, 로그 커밋
- [ ] 레벨 4에서 최소 1개 재현 (그 페이즈가 바꾼 실사용 조건)
- [ ] 레벨 5 스크린샷 대조
- [ ] 발견한 결함은 **고치고 회귀 테스트 추가** — 문서에만 적고 넘어가지 않는다
- [ ] 해당 페이즈에서 내린 결정을 결과 문서에 기록 (사람이 나중에 뒤집을 수 있도록)
