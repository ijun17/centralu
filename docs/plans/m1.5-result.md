## 5 defects that measurement caught

The following only surfaced **by actually running it**, even while every automated test passed.

1. **Orphaned sidecar** — spawning through the `pnpm` wrapper killed only the wrapper, leaving the
   grandchild (node) behind still holding the port. In practice, 3 of them were running at once.
   → run tsx directly, kill the whole process group, and self-terminate on stdin EOF.
   Measured with SIGKILL (same as a crash) and confirmed 0 zombies.
2. **Reconnection failed after restart** — even after reviving the sidecar, the port and token had
   changed, so the UI stayed stuck on "disconnected." The auto-restart was pointless on its own.
   → `updateEndpoint` + subscribing to host-status.
3. **A missing argument** — an edit accidentally deleted `.args()`, which killed the host instantly.
   The app came up as a blank screen. The compile warning (`unused variable: args`) was the signal,
   and it got ignored.
4. **A false positive on stdin EOF** — turning on parent-watching based on whether stdin was a TTY
   made the host kill itself instantly when run from a script with stdin set to `/dev/null`.
   → made it an explicit `--watch-parent` flag.
5. **When the resume identifier gets saved** — the SDK only hands over the session id on the first
   init event, not in the creation response. If the host dies before the first turn, resume is
   impossible — the expectation was brought in line with actual behaviour, and the id is now saved
   right after creation too.

## Decisions made during implementation

1. **Matcher computation lives in core, delivery in the UI** — to respect the boundary rule that
   agent-host does not import core, the "always allow" pattern is computed by the UI and sent over
   as an RPC payload.
2. **The directory picker goes through SystemPort** — the ui package importing `@cc/platform/tauri`
   directly would be a boundary violation. Desktop gets the native picker; web dev falls back to a
   path input.
3. **Parent-watching is an explicit flag** — automatic detection (TTY) produced false positives.
   Only the supervisor turns it on.
4. **Notifications are either individual or aggregate, never both** — the same moment never fires twice.

## Known limitations (M2 and beyond)

- No Codex adapter — the protocol and type generator were confirmed in M0; only the adapter itself needs adding.
- No git panel, file tree, code viewer, attachments or search.
- The release build (`tauri build`) is unverified — only dev mode has been checked. Sidecar bundling is for M2.
- L4-1 (OS notification while away) could not be automated — the notification policy has 13 unit
  tests, and the delivery path was only confirmed by reading the code. Whether the banner actually
  appears has to be checked during dogfooding.
  (L4-2 restart, L4-3 repeated operation and L4-4 narrow window all ran and passed)
