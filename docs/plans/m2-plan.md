# M2 실행 플랜 — 관제 완성

> 기준: **에이전트가 무엇을 했는지 앱 안에서 판단할 수 있는가.**
> M1.5까지는 "언제 나를 부르는지"를 풀었다. M2는 "부름에 답하려면 무엇을 봐야 하는가"를 푼다.
>
> 선행: [m1.5-result.md](m1.5-result.md) (상시 가동 완료) · 검증 프로토콜은 [m1.5-plan.md](m1.5-plan.md) 것을 그대로 쓴다.

## 지금 무엇이 막고 있나

M1.5로 앱은 계속 켜둘 수 있게 됐다. 그런데 실제로 쓰려고 하면 **판단할 근거가 화면에 없다**:

| 막는 것 | 지금 벌어지는 일 |
|---|---|
| 무엇이 바뀌었는지 못 본다 | 승인하려면 diff를 봐야 하는데, 앱에는 명령문 한 줄뿐이라 IDE로 나가야 한다 |
| Codex를 못 쓴다 | 사용자가 실제로 두 도구를 쓰는데 앱은 하나만 안다 (FR-7 미완성) |
| 지난 대화를 못 찾는다 | "그거 어디서 얘기했지"가 세션 몇 개만 넘어가면 바로 생긴다 |
| 스크린샷을 못 붙인다 | 화면을 보여주며 지시하는 흔한 흐름이 막힌다 |

M2는 이 넷을 없애 **도그푸딩이 의미 있는 상태**를 만든다.

---

## 순서와 근거

기능 크기순이 아니라 **위험이 큰 것부터** 배치한다.

1. **A. Codex 어댑터** — 설계가 "어댑터 하나만 추가하면 UI·core·protocol은 그대로"라고 약속했다(변경 축 C3).
   이 약속이 틀렸다면 그 사실이 M2 전체 설계에 영향을 주므로 **가장 먼저 검증한다.**
2. **B. 깃 패널** — 관제 가치가 가장 큰 기능. 승인 판단의 근거가 여기서 나온다.
3. **C. 파일 트리 + 코드 뷰어** — 깃 패널이 만든 diff 뷰 기반을 재사용한다.
4. **D. 첨부** — 독립적이고 작다.
5. **E. 검색 + 커맨드 팔레트** — 대화가 쌓여야 의미가 생기므로 뒤에.
6. **F. 배포 빌드** — M1.5의 알려진 한계(미검증)를 닫고 도그푸딩 준비를 마친다.

---

## A. Codex 어댑터 (FR-7 완성)

M0에서 프로토콜·타입 생성기·승인 오버라이드를 이미 확인했다([m0-findings.md](../spikes/m0-findings.md)).
남은 것은 어댑터 구현과 **설계 약속의 실전 검증**이다.

- **A-1. 프로토콜 바인딩 커밋** — `codex app-server generate-ts`로 생성한 타입을 저장소에 넣고,
  생성 결과가 바뀌면 diff로 드러나게 한다 (C4 프로토콜 변동 감지).
  - 완료: 생성 스크립트(`pnpm codex:bindings`) + 현재 버전 바인딩 커밋
  - 완료: 바인딩이 최신인지 확인하는 CI 체크 (달라지면 실패)
- **A-2. CodexAdapter 구현** — stdio JSON-RPC 클라이언트, `initialize`→`initialized` 핸드셰이크,
  `thread/start`(approvalPolicy 오버라이드)·`turn/start`·`turn/interrupt`·`thread/resume`.
  이벤트 변환: `item/agentMessage/delta`→message_delta, `item/started|completed`→tool_call/result,
  `item/*/requestApproval`→approval_request, `turn/completed`→turn_complete,
  `thread/tokenUsage/updated`→usage/context, `account/rateLimits/updated`→limit_reached,
  `thread/name/updated`→session_title, `thread/compacted`→컴팩션 마커.
  - 완료: 계약 테스트 — 녹화한 실제 프로토콜 응답 픽스처 → NormalizedEvent 스냅샷
  - 완료: 승인 decision 6종 매핑 (`acceptForSession`이 '항상 허용·세션'과 대응)
  - 완료: capability 선언 (resume·autoTitle·contextUsage)
- **A-3. 세션 생성 UI에 도구 선택** — 프로젝트 기본 도구, 세션별 선택, 미설치 도구는 비활성.
  - 완료: E2E — 같은 프로젝트에 Claude·Codex 세션을 동시에 띄우고 사이드바에서 구분된다
- **A-4. 설계 약속 검증 (이 페이즈의 핵심 산출물)**
  - 완료: **`packages/{ui,core,protocol}`의 diff가 어댑터 추가 때문에 생기지 않았음을 확인**하고
    결과 문서에 기록한다. 변경이 필요했다면 **무엇이 부족했는지**를 적는다 — 설계 문서를 고칠 근거가 된다.
- **A-5. 실 세션 스모크** (L3) — Codex로 S1~S6 시나리오. 특히 S3(항상 허용)·S5(재개).
  - 모델 정책: Codex 기본 모델 (최상위 모델 금지)

**게이트**: Codex 실 세션으로 승인 왕복 + 재개가 통과해야 B로 넘어간다.

## B. 깃 패널 (FR-4)

승인 판단의 근거를 앱 안에서 만든다.

- **B-1. GitPort 확장** — `status`(staged/unstaged/untracked), `diff(path, staged?)`, `log(limit)`,
  `commitDetail(sha)`, `branches()`, `checkout(branch)`.
  지금은 요약(브랜치·변경 수)만 있다.
  - 완료: 계약 테스트를 web/mock/(tauri) 세 구현에 동일하게 실행
  - 완료: 깃 저장소가 아닌 프로젝트에서 호출해도 안전하게 실패한다
- **B-2. Changes 탭** — 파일 목록 + diff 뷰(CodeMirror merge view, 지연 로드).
  에이전트가 파일을 바꾸면 워처로 갱신(debounce).
  - 완료: E2E — mock diff 렌더, 큰 diff에서 가상 스크롤
  - 완료: **워처가 유휴 CPU를 깨우지 않는다** (D-3 측정 재실행, 프로젝트 4개 등록 상태)
- **B-3. History 탭** — 최근 커밋 로그, 커밋 클릭 시 변경 파일·diff.
  브랜치 그래프는 **선을 그리지 않고** 부모 관계만 표시 (그래프 렌더는 비용 대비 가치가 낮다).
- **B-4. Branches 탭** — 목록·현재 브랜치·체크아웃. 더티 상태면 막지 말고 **결과를 먼저 보여준다**
  (충돌 예상 파일 목록 → 그래도 진행할지).
- **B-5. IDE 줄 점프** — diff·파일 목록에서 ⌘클릭 시 `code -g path:line` (SystemPort는 이미 있다).
  - 완료: E2E — mock SystemPort에 호출이 기록된다
- **B-6. 커밋·스테이징** (product-spec에서 v1.5로 확정한 분량)
  - 완료: 스테이지/언스테이지, 커밋 메시지 입력, 커밋. 푸시는 범위 밖(비목표 유지)
  - 완료: **에이전트가 만든 변경과 내가 만든 변경을 구분해 표시** (FR-5의 "방금 만진 파일" 재사용)

**결정 필요**: git 구현을 Rust `git2`로 옮길지 (platform-abstraction §5의 4단계).
기본 방침은 **옮기지 않는다** — 현재 host 구현으로 B를 완성하고, D-3 측정에서 병목이 확인될 때만 옮긴다.
포트 인터페이스가 같으므로 나중에 옮겨도 UI는 그대로다. (선 최적화 금지)

## C. 파일 트리 + 코드 뷰어 (FR-5, FR-6)

- **C-1. FsPort 구현** — `listDir`(lazy), `readFile`, `watch`. 이미 포트는 정의돼 있고 구현만 없다.
- **C-2. 파일 트리** — lazy 로드, `.gitignore` 필터 토글, 깃 상태 오버레이,
  **에이전트가 최근 만진 파일 하이라이트** (`files_touched` 이벤트가 이미 있다).
  - 완료: 대형 저장소(10k+ 파일)에서 첫 렌더 200ms 이내 — 열어본 디렉토리만 읽는지 확인
- **C-3. 코드 뷰어** — CodeMirror 6 읽기 전용 + Shiki 하이라이트(둘 다 **지연 로드**).
  파일 내 검색, 줄번호, 줄 링크 복사, diff/일반 모드 전환.
  - 완료: **번들 크기 회귀 방지** — 초기 번들에 CodeMirror·Shiki가 포함되지 않음을 테스트로 확인
    (tech-stack의 "뷰어에 편집기를 넣지 않는다" 원칙의 기계 검증)
  - 완료: 대용량 파일(5MB)·바이너리·이미지 처리

## D. 첨부·이미지 붙여넣기 (FR-13)

- **D-1. 입력창 첨부** — 클립보드 이미지 붙여넣기, 드래그앤드롭, 파일 선택. 썸네일 미리보기 후 전송.
- **D-2. 어댑터 전달** — 프로젝트 내 파일은 경로 참조(@멘션), 외부 파일·이미지는 도구 형식으로.
  capability(`attachments`)로 지원 범위를 UI에 반영.
  - 완료: L3 스모크 — 실제 이미지 1장을 붙여 에이전트가 내용을 읽는다

## E. 검색 + 커맨드 팔레트 (FR-21, FR-17 완성)

- **E-1. 대화 전문 검색** — SQLite FTS5 인덱스, 아카이브 포함. 결과에서 해당 위치로 점프.
  - 완료: better-sqlite3의 FTS5 가용성 확인 (없으면 LIKE 폴백을 명시적으로 선택)
- **E-2. 커맨드 팔레트 ⌘K** — 프로젝트·세션·동작·검색 결과를 한 입력창에서.
- **E-3. 단축키 설정 화면** — 변경·충돌 감지 (FR-17 완성).
- **E-4. 승인 규칙 관리 화면** — 저장된 '항상 허용' 목록 조회·삭제.
  M1.5에서 저장은 되지만 **보고 지울 방법이 없다** — "결과를 보이게 한다"는 원칙의 미완성분.

## F. 배포 빌드와 마감

- **F-1. `tauri build` 검증** — M1.5의 알려진 한계를 닫는다. 사이드카(Node) 번들링 방식 결정:
  ① Node 단일 실행 파일(SEA) ② 시스템 Node 요구 ③ Bun 컴파일. **①을 기본 검토.**
  - 완료: 빌드된 `.app`을 **깨끗한 경로에서 실행**해 세션 생성까지 완주
  - 완료: 좀비 프로세스 0 (M1.5와 같은 SIGKILL 실측)
- **F-2. 성능 재측정** (D-3 기준) — 프로젝트 4개 + 세션 4개 + 깃 워처 가동 상태
- **F-3. 전체 회귀** — L1~L5 전부, 실 세션 스모크는 Claude·Codex 양쪽

## 검증 (M1.5 프로토콜 유지)

레벨 정의·모델 정책·E2E 작성 규칙은 [m1.5-plan.md](m1.5-plan.md)의 검증 프로토콜을 그대로 따른다.
M2에서 추가되는 시나리오:

| # | 시나리오 | 레벨 |
|---|---|---|
| S9 | Codex 세션 승인 왕복 (`acceptForSession` 포함) | L3 |
| S10 | Codex 세션 재개 (`thread/resume`) | L3 |
| S11 | 한 프로젝트에서 Claude·Codex 동시 진행 | L3 |
| S12 | 에이전트가 파일을 바꾸는 동안 깃 패널이 갱신된다 | L4 |
| S13 | 이미지 첨부 → 에이전트가 내용을 읽는다 | L3 |
| S14 | 배포 빌드 앱으로 세션 생성 완주 | L4 |

**M1.5에서 배운 것을 반영한 추가 규칙:**

- 프로세스를 새로 spawn하는 코드(Codex CLI)는 **좀비 검사를 반드시 포함한다** (M1.5 결함 1번의 재발 방지).
- 외부 프로세스의 주소·식별자가 바뀔 수 있는 곳은 **재연결 경로를 테스트한다** (결함 2번).
- 컴파일·린트 경고를 무시하지 않는다 (결함 3번은 경고가 이미 알려주고 있었다).

## 알려진 결정 사항

1. **git을 Rust로 옮기지 않는다** (측정으로 병목이 확인될 때까지). 근거: 포트가 같아 나중에 옮겨도 UI 무변경.
2. **브랜치 그래프 선은 그리지 않는다.** 부모 관계 표시로 충분하고, 렌더 비용 대비 가치가 낮다.
3. **푸시는 여전히 비목표.** 커밋·스테이징까지만 (product-spec §1.5 유지).
4. **CodeMirror·Shiki는 지연 로드 고정.** 초기 번들 회귀를 테스트로 막는다.

## M2 이후

M2가 끝나면 **실사용 기간**(도그푸딩)이다. 실제 프로젝트로 며칠 굴리고,
거기서 나온 불만을 **M2.5 개선 페이즈**로 처리한 뒤 M3(사용량 대시보드·오케스트레이터)로 간다.
도그푸딩 때 확인할 것은 m1.5-result.md의 미검증 항목부터 — 특히 **자리 비움 시 OS 알림 배너**.
