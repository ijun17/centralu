## 1. 변경 축 — 이 설계가 견뎌야 하는 변경들

이 프로젝트에서 큰 변경은 처음부터 **예정되어** 있었다. 아키텍처는 이 목록을 상대로 설계되었고, 이 축들 중 어느 하나라도 더 어렵게 만드는 새 결정은 잘못된 결정이다.

| # | 예상 변경 | 시기 | 격리 장치 |
|---|---|---|---|
| C1 | 실행 환경: **브라우저(웹 개발) → Tauri** | M1 이후 | 플랫폼 포트 (→ [platform-abstraction.ko.md](platform-abstraction.ko.md)) |
| C2 | 서비스 구현 이동: git/store 등 **Node(dev) → Rust(prod)** | Tauri 전환 시점, 서비스별로 점진적으로 | 포트 인터페이스는 고정, 구현만 교체 |

## 2. 계층과 의존성 규칙

```
┌────────────────────────────────────────────────────────┐
│  apps  (assembly: web / desktop entry points,          │
│         the only place an implementation is chosen)    │
├────────────────────────────────────────────────────────┤
│  ui        React screens, components, hooks            │
├──────────────┬─────────────────────────────────────────┤
│  core        │  platform (port interfaces + impls)     │
│  pure domain │   ports/ ← what ui sees                 │
│  (no IO)     │   web/ tauri/ mock/ ← only apps know    │
├──────────────┴─────────────────────────────────────────┤
│  protocol   message and event schemas (zod)            │
│             — everyone's shared language               │
└────────────────────────────────────────────────────────┘
   agent-host (separate Node process) ──→ shares protocol only
```

**의존성 규칙 (위반은 리뷰 코멘트가 아니라 lint 에러다):**

| 패키지 | 의존 가능 | 절대 금지 |
|---|---|---|
| `ui` | core, platform**/ports**, protocol, React | platform/web, platform/tauri, `@tauri-apps/*`, fetch/WebSocket 직접 사용 |
| `core` | protocol | React, DOM, 모든 IO (순수 TS만) |
| `platform/ports` | protocol | 구현 코드 |
| `platform/web` `platform/tauri` | ports, protocol | ui, core |
| `agent-host` | protocol, 외부 SDK | ui, core, platform |
| `apps/*` | 전부 (조립을 담당한다) | — |

핵심은 이것이다: **구현을 아는 유일한 곳은 apps 엔트리 포인트다.** 나머지 전부는 인터페이스와 스키마만 안다.

## 3. 사용한 설계 패턴 — 어디에, 왜

패턴은 장식이 아니라 변경 축(C1~C6)에 대한 방어 수단이다. 각 패턴이 어느 축을 막는지 명시한다.

| 패턴 | 적용 위치 | 막는 축 |
|---|---|---|
| **포트와 어댑터 (헥사고날)** | `platform/ports`가 UI에게 유일한 바깥 세계다. 구현은 web/tauri | C1, C2 |
| **퍼사드** | 하나의 `Platform` 객체가 포트 묶음을 제공한다 (`platform.git`, `platform.agents` …) | C1 |
| **의존성 주입** | 부트스트랩에서 Platform을 생성 → 하나의 React Context로 주입. 전역 싱글턴 없음 | C1, 테스트 |
| **어댑터** | `ClaudeAdapter`/`CodexAdapter`가 도구별 차이를 `NormalizedEvent`로 변환한다 | C3, C4 |
| **부패 방지 계층** | 외부 SDK 타입은 어댑터 밖으로 **한 발짝도 나갈 수 없다.** 즉시 protocol 타입으로 변환한다 | C4 |
| **명시적 상태 기계** | 세션 상태(FR-12)는 전이 테이블로 정의된 순수 함수다. UI에서 if 문으로 상태를 추론하는 것은 금지 | C5, 정확성 |
| **이벤트 기반 (pub-sub)** | 어댑터 → 앱 방향은 단방향 이벤트 스트림이다. 폴링 없음 (product spec §7.1) | C6, 성능 |
| **CQRS-lite** | 명령 경로(포트 메서드 호출)와 상태 갱신 경로(이벤트 수신 → 리듀서)를 분리한다. 명령의 낙관적 반영은 최소화 | C5, C6 |
| **리포지토리** | 영속성은 `StorePort` 뒤에 둔다. SQLite 스키마는 구현만 안다 | C2 |
| **파생 상태 (셀렉터)** | 인박스, 카운터, 정렬은 저장하지 않고 세션 상태에서 **계산**한다. 저장하는 것이 동기화 버그의 뿌리다 | C5 |
| **전략** | 정책 분기 — 카드 접기 정책, 인플레이스 배너 승인 판정(도구 종류별) — 는 데이터(설정 테이블)다 | C5 |

금지 안티패턴: 전역 가변 싱글턴, UI 컴포넌트에서의 직접 IO, 이벤트 핸들러 안의 비즈니스 로직(→ core로 옮긴다), 파생 상태 저장.

## 4. 프로세스 토폴로지 — dev와 prod의 차이를 최소화한다

**결정: Agent Host와의 통신은 dev와 prod 모두 localhost WebSocket이다.**

```
[dev machine: browser]                   [production: Tauri]

Vite dev server                        Tauri app (Rust)
   │                                      │ spawn·watch·restart (supervisor)
Browser (ui)                              │ git2/rusqlite/notify/shortcuts (Tauri invoke)
   │  WebSocket ws://127.0.0.1:PORT    Webview (ui)
   ▼                                      │  WebSocket ws://127.0.0.1:PORT (identical!)
agent-host (node, run standalone)         ▼
   ├─ adapters (claude, codex)         agent-host (node, sidecar)
   ├─ dev-services (git/fs/store/usage)   ├─ adapters (claude, codex)
   └─ mcp server                          ├─ usage parser · mcp server
                                          └─ (dev-services replaced by Rust)
```

- **AgentPort 구현은 하나로 유지된다** — dev와 prod가 같은 WS 클라이언트를 쓴다. Tauri의 역할은 통신이 아니라 **프로세스 감독**(spawn, 크래시 감지, 재시작)이다 — 패키지된 앱에서는 키퍼를 통해서(§4.1). stdio 릴레이(Rust를 거치는 이중 직렬화)는 만들지 않는다.
- 보안: 임의 포트 + 시작 시 생성한 토큰으로 하는 핸드셰이크, loopback에만 바인딩. 브라우저/WebView 클라이언트는 명시된 dev/Tauri origin allowlist에도 들어야 한다. `Origin` 헤더가 없는 네이티브 클라이언트도 토큰은 필요하고, literal `Origin: null`은 거부한다.
- dev 모드에서는 git/fs/store를 agent-host 안의 `dev-services` 모듈(Node로 구현)이 제공한다. Tauri 전환 시점에 이 부분만 Rust(invoke)로 바뀌고 **포트는 그대로 유지된다**(C2). 전환의 순서와 방법은 [platform-abstraction.ko.md](platform-abstraction.ko.md) §5에 있다.
- 이 구조 덕분에 M0~M1을 Rust 툴체인 없이 브라우저에서 핫 리로드로 개발하고, Playwright로 E2E를 돌릴 수 있다.

### 4.1 키퍼: 호스트가 창보다 오래 산다 (#280, 옵션 C 1단계)

패키지된 앱에서는 Tauri 앱이 더 이상 호스트의 부모가 아니다. 호스트는 **키퍼**가 쥔다: 같은 Centralu 실행 파일을
`centralu --keeper`로 띄운 것으로, 앱에서 떨어져 자기 세션에서 돈다.

```
Tauri app (window)  ──attach──▶  keeper (centralu --keeper, own session)
   │                 unix socket     │ launch · watch · restart · swap
   │                 <data>/keeper.sock, 0600
   │                                 │
   └── WebSocket ──▶ front door ─────┼─ bytes ─▶ agent-host (node, from <data>/hosts/<build>/)
       ws://127.0.0.1:DOOR           │               │
       (one port and token per       │               │ <data>/children.sock, 0600
        keeper)                      │               ▼   spawn · attach · signal (§4.3)
                                     └─ holds ─▶ claude · codex app-server · terminals · commands
                                                 (each in its own session)
```

| 결정 | 이유 |
|---|---|
| 키퍼는 두 번째 바이너리가 아니라 앱 실행 파일의 한 모드다 | 서명하고 내보낼 것이 하나이고, 서명과 번들 식별자가 같으므로 macOS가 개인정보 권한을 새 프로그램이 아니라 Centralu에 돌릴 것이다(#220). `main()`이 Tauri 앱을 만들기 전에 갈라지므로 키퍼 모드는 창을 열지도 웹뷰를 띄우지도 않는다. |
| 앱이 떼어서 띄운다 (`setsid`, stdin `/dev/null`) | 앱이 끝나든 죽든 바뀌든 키퍼에게는 아무것도 가지 않는다. launchd와 `SMAppService`는 나중 선택지이고 1단계가 아니다. |
| 호스트는 키퍼에 묶인다 (키퍼의 파이프에 `--watch-parent`) | 키퍼가 어떻게 죽든 호스트를 데려간다: 주인 없는 호스트는 생기지 않는다. |
| 모든 호스트는 빌드별 사본 `<data>/hosts/<commit>/`에서 돈다 | 다시 빌드하거나 업데이트하면 번들이 바뀐다. 번들에서 돌던 호스트는 Codex 브리지·`schema.sql`·`app-template/`을 필요할 때 읽어 두 빌드를 섞을 수 있었다(2026-10-03). 아무 호스트도 쓰지 않는 사본은 호스트가 뜨면 지운다. |
| 백그라운드 모드는 설정이고 기본은 꺼짐 | 꺼짐: 마지막 창이 떨어지면 키퍼와 호스트가 멈춘다, 앱을 끄던 그대로. 켜짐: 계속 돌고, 다시 연 앱이 다시 붙는다. 종료 질문이 이것을 따른다: 꺼짐이면 버튼은 "Quit completely" 하나(어차피 끄면 모두 멈춘다), 켜짐이면 "Quit"은 창만 닫고 "Quit completely"는 키퍼·호스트·모든 에이전트·터미널·도는 명령을 멈춘다. #387 전까지 이름은 "Quit and stop agents"였고, 멈추는 것을 덜 말했다. |
| 백그라운드 모드에서 지켜보는 이 없는 키퍼는 창도 활동도 없이 30분이 지나면 끝난다 | 아무도 보지 않는 호스트를 끝낼 무언가가 있어야 한다. 활동(일하거나 기다리는 세션, 터미널, 명령 실행)은 호스트가 stdout에 내는 자기 보고이고, 키퍼는 그 밖에 아무것도 해석하지 않는다. 도는 턴이나 기다리는 승인은 얼마가 걸리든 키퍼를 살려 둔다. |
| 다른 빌드의 창은 도는 호스트에 붙고 바꾸기를 권한다 | 키퍼는 자기 것까지 모든 빌드를 안다. 바꾸기는 키퍼를 창의 빌드로 옮기고(§4.4) 이어서 §4.2의 블루그린 교체를 한다. 잃을 것이 있을 때만 창이 먼저 묻는다. "Apply now"가 띄운 창은 잃을 것이 없으면 저절로 바꾼다(§4.5). |
| 디버그 빌드(`pnpm app:dev`)는 직접 경로를 유지한다 | 거기서는 앱이 호스트의 부모다, 예전 그대로. `CC_USE_KEEPER=1`이면 디버그 빌드도 키퍼를 쓴다. unix가 아닌 대상에는 아직 키퍼가 없다. |

키퍼는 호스트의 오래 사는 자식도 쥔다(§4.3). 그래서 호스트를 다시 띄우거나 바꿔도 그 자식들은 끝나지 않는다.
제어 소켓과 그 프로토콜, 신뢰 규칙은 [agent-host.ko.md](agent-host.ko.md) §4.1과
[security-boundaries.md](security-boundaries.md)에 있다.

### 4.2 정문과 블루그린 교체 (#280, 옵션 C 3단계)

클라이언트는 호스트 자신의 포트를 알지 못한다. 키퍼는 살아 있는 동안 루프백 포트 하나, **정문**(front door)에서
듣고, 들어온 연결을 그때의 호스트로 바이트 그대로 넘긴다. 웹뷰, 브라우저, 모든 Codex 오케스트레이터 브리지가
여기로 붙는다.

| 결정 | 이유 |
|---|---|
| WebSocket 프록시가 아니라 바이트 중계 | 키퍼는 어떤 프로토콜도 해석하지 않는다(#280). 바이트 중계는 호스트 프레임이 바뀌어도 깨지지 않고, 앱 뷰의 HTTP 문도 그대로 지나간다. |
| 토큰은 키퍼가 쥐고 모든 호스트에 넘긴다 (`CC_HOST_TOKEN`) | `hello`와 브라우저의 `Origin`은 여전히 호스트가 직접 검사한다. 토큰과 포트는 재시작과 교체를 거쳐도 같아서, 클라이언트에게 다시 알려 줄 일이 없다. 이것이 없애는 측정된 위험: Codex 브리지는 스레드가 시작될 때 주소와 토큰을 한 번 받고, 도는 codex는 그 브리지를 계속 쥐므로, 새 포트나 새 토큰의 호스트는 모든 브리지를 조용히 끊었다. |
| 준비된 호스트가 없는 동안 새 연결은 거절하지 않고 붙잡는다 (최대 45초) | 곧바로 다시 붙는 클라이언트는 실패하고 물러서는 대신, 다음 호스트가 뜨자마자 그리로 간다. 측정: 교체로 끊긴 클라이언트를 새 호스트가 84–86 ms 뒤에 맞았다. |
| Codex 브리지에는 정문 주소를 준다 | 브리지는 환경을 한 번만 읽는다. 호스트보다 오래 사는 주소만 교체를 견딘다. 브리지는 닫힌 소켓에서 기다리던 호출을 바로 실패시키고 다음 호출에서 다시 붙는다. |
| 앱 뷰의 주소도 정문을 가리키고, HTTP 비밀은 키퍼의 토큰에서 끌어낸다 | iframe은 주소를 그대로 쥐고 있고, 정문 뒤의 다음 호스트가 그 주소를 받아 줘야 한다. 열린 뷰 인스턴스는 계획된 끝에서 다음 호스트로 넘어가고([agent-host.ko.md](agent-host.ko.md) §4.2), 창은 재동기화 뒤 뷰의 주소를 다시 묻고 주소가 바뀌었을 때만 다시 불러온다. |

`switch`는 **블루그린 교체**다 (`keeper/swap.rs`):

1. 키퍼가 새 빌드의 빌드별 사본에서 호스트 B를 `--standby`로 띄운다. B는 번들을 읽고, 도구를 찾고, 저장소를 쓰지
   않고 읽고, 자기가 읽을 수 없는 저장소면 거절하고, 보고한 뒤 기다린다. 잠금을 잡지 않고, 마이그레이션을 돌리지
   않고, 아무것에도 붙지 않는다. 호스트 A는 계속 일한다.
2. 60초 안에 보고가 없거나 B가 끝나면: B를 멈추고 사본을 지운다. A는 건드린 적이 없다.
3. 정문이 새 연결을 붙잡고, A에게 **드레인**하라고 한다: 새 RPC와 도구 호출을 거절하고, 도는 것에는 최대 10초를
   주고, 남은 것은 모델이 다시 시도할 수 있는 오류로 끊고, 떼어 내고(detach), 저장소를 비우고 닫고, #278 잠금을
   놓고 끝난다.
4. B에게 활성화하라고 한다: 잠금을 잡고, 확장(expand) 마이그레이션만 돌리고(무거운 단계와 깨는 단계는 준비된 뒤에
   돈다, [agent-host.ko.md](agent-host.ko.md) §5.1), 시작하고, 듣고, 준비됐다고 알린다.
5. 정문이 B를 가리키고, 아직 A로 중계되던 연결을 닫는다. 클라이언트는 같은 주소로 다시 붙고 B의 새 stream
   epoch로 다시 맞춘다. A의 사본은 지운다.

| 결정 | 이유 |
|---|---|
| 드레인 한도 10초, 그 뒤에는 다시 시도할 수 있는 오류로 끊는다 | 드레인이 필요한 것은 호스트가 직접 처리하는 호출뿐이다: 실제 저장소에서 오케스트레이터 도구는 최대 0.2초, 앱 도구는 최대 5.6초가 걸렸다. Bash와 서브에이전트는 호스트보다 오래 사는 에이전트 프로세스 안에서 돈다. 모든 도구를 기다리는 것은 처음부터 선택지가 아니었다(p99 78초, 최대 4.5시간). |
| B는 A가 드레인하기 전에 자기를 점검하고, 마이그레이션은 그 뒤에만 한다 | 점검이 실패해도 잃는 것이 없다: A는 그대로다. 교체 중에는 확장 단계만 돌리므로 저장소는 A의 빌드가 여전히 읽을 수 있다. |
| A가 드레인한 뒤 B가 실패하면 A의 빌드를 다시 띄운다 | A는 이미 끝났고 잠금을 놓았으니 이어 갈 수 없다. A의 빌드는 잘 돈다고 알려져 있고 저장소도 여전히 읽으며, 그 사본은 교체가 성공할 때까지 남는다. B를 다시 시도하는 쪽도 있었지만, 방금 시작에 실패한 빌드가 지금 뜰 가능성이 더 낮다. 창은 실패와 이전 빌드가 다시 일한다는 것을 보여 주고, 사람은 다시 시도할 수 있다. |
| 모든 단계를 붙은 창에 밀어 준다 (`view.swap`) | 창은 진행과 실패 이유를 보여 주고, 잃을 것이 있을 때만(일하거나 기다리는 세션, 터미널, 명령) 바꾸기 전에 묻는다. |
| 교체의 detach는 에이전트·터미널·명령을 넘겨준다 | 이들은 키퍼의 자식이므로(§4.3) A는 놓기만 하고 B가 평소 시작 과정에서 다시 붙는다: 도는 턴이 교체를 넘어 이어진다. 호스트는 키퍼의 자식 서비스를 가졌을 때만 `keepsAgents: true`를 알린다. 그것이 없는 호스트는 여전히 자식을 멈추고, 창도 그렇게 말한다. |


### 4.3 키퍼가 에이전트·터미널·명령을 쥔다 (#280, 옵션 C 2단계)

호스트는 더 이상 오래 사는 자식을 직접 띄우지 않는다. 키퍼 아래에서는 claude, codex app-server, 터미널, 프로젝트 명령
(개발 서버)을 **키퍼가** 띄운다. 두 번째 사용자 전용 소켓 `<data>/children.sock`을 거친다. 호스트가 죽든 다시 뜨든
교체되든 연결만 놓고, 자식들은 계속 돈다. 다음 호스트가 목록을 읽고 턴 도중에 다시 붙는다. 앱 MCP 프로세스는 호스트에
남고 호스트와 함께 다시 뜬다(소유자 결정 2).

| 결정 | 이유 |
|---|---|
| 모든 자식은 자기 세션에서 돈다 (`setsid`) | 키퍼와 어떤 호스트의 프로세스 그룹에도 속하지 않으므로, 호스트의 종료나 그룹 kill이 닿지 않는다. 전에는 claude와 codex가 호스트의 그룹에 있었다. |
| pty는 키퍼가 직접 연다 (`openpty`, `setsid`, `TIOCSCTTY`) | node-pty는 마스터를 호스트에 두므로, 호스트가 사라지면 화면을, SIGHUP과 함께 셸까지 데려갔다. |
| pty는 쉬지 않고 256 KiB 링으로 비우고, 다음 호스트에 다시 보내 준다 | 출력을 아무도 읽지 않으면 pty 자식은 끝나지도 못한다(#280에서 측정: bash가 5초 넘게 `?Es`에 머물렀다). 링 크기는 터미널 스크롤백이 쥐는 256 KiB와 같다. |
| 에이전트의 stdout은 잃지 않고 버퍼에 담고(64 MiB까지, 그 뒤로는 자식이 기다린다) 줄 단위로 넘긴다 | 그것은 프로토콜이다. 바이트 하나만 빠져도 프레임이 깨진다. claude는 stdout을 읽지 않은 채 60초를 버티는 것이 측정됐다. codex의 `thread/resume` 응답 하나가 한 줄에 23 MB였기에 이 크기다. 죽는 호스트는 이미 자기 소켓에 들어간 것까지만 잃고, 다음 호스트는 줄 경계에서 시작한다. |
| 연결이 닫히는 것은 결코 자식에게 신호를 보내거나 stdin을 닫거나 pty를 닫지 않는다 | 호스트가 에이전트를 두고 떠날 수 있는 이유가 이것이다. Agent SDK는 주인이 끝날 때 자기 프로세스를 kill한다. 그 kill은 키퍼에 보내는 요청이고, 떠나는 호스트는 그것을 보내지 않는다. |
| 종료는 kqueue `NOTE_EXIT \| NOTE_EXITSTATUS`(macOS), pidfd(Linux)로 지켜본다 | 자식이 아닌 프로세스의 종료(macOS에서는 상태까지)도 알려 준다. 다른 키퍼에게서 자식을 넘겨받은 키퍼(§4.4)에게 필요하다. |
| 스레드 하나가 모든 디스크립터를 쥔다 | 자식 표가 평범한 데이터와 날 디스크립터뿐이라, 키퍼 넘겨주기(§4.4)가 두 차례 사이에서 이것을 얼리고 직렬화해 디스크립터를 `SCM_RIGHTS`로 다음 키퍼에 넘긴다. |

**떠나는 방식은 둘이다.** *stop*은 예전의 끝이다: 세션·터미널·명령이 호스트와 함께 멈춘다. 키퍼가 없으면 모든 끝이
이것이고, 키퍼 아래에서는 키퍼가 아주 멈출 때 이것을 청한다(자식 소켓의 `stop`): "Quit completely", "Restart completely", 백그라운드
모드가 꺼진 채 마지막 창이 닫힐 때, 유휴 종료. 호스트가 멈추지 못한 것은 그 뒤에 키퍼가 직접 끝낸다(stdin EOF와
SIGHUP, 그다음 TERM, 그다음 KILL). *detach*는 키퍼 아래의 나머지 모든 끝이다: 크래시, 재시작, 교체의 드레인, 키퍼
파이프가 닫히는 것. 도구에는 아무것도 보내지 않는다: 기다리는 승인을 거절하지 않고, EOF도 신호도 없다.

**다시 붙기**는 다음 호스트의 시작 과정에서 일어난다. 자식마다 호스트가 요청할 때 적어 둔 태그(어느 세션, 터미널,
명령 실행인지)가 붙어 있다. 키퍼는 그것을 저장할 뿐 안을 해석하지 않는다.

| 종류 | 다음 호스트가 넘겨받는 법 |
|---|---|
| claude | `spawnClaudeCodeProcess`가 쥐어 둔 프로세스를 돌려주는 새 `query()`. 측정: 다시 보낸 `initialize`가 기다리던 승인을 즉시 다시 전하고, 도는 턴의 나머지가 그것을 통해 온다. |
| codex app-server | 같은 stdio. 두 번째 `initialize`는 해 없이 거절되고("Already initialized"), `thread/resume`이 기다리던 승인을 같은 요청 id로 다시 보내고, 도는 턴은 resume의 턴에서, resume이 턴을 달라고 하지 않게 된 뒤로는(#342) `thread/turns/list`에서 온다. |
| 터미널, 명령 실행 | 같은 id나 실행 id. 키퍼가 다시 보내 준 링이 스크롤백이나 로그가 된다. 붙은 호스트가 없을 때 끝난 실행은 종료 코드와 함께 돌아온다. |

쥐어 둔 프로세스가 있는 세션은 시작 시 재설정에서도 살아 있는 상태를 지키고, 대화록 따라잡기는 건너뛴다(버퍼에 담긴
출력이 두 번 기록된다). 옛 호스트가 죽을 때 진행 중이던 호스트 자신의 in-process 도구 호출(오케스트레이터, 앱 프록시)은
결코 답을 받지 못한다. 넘겨받는 어댑터가 그 호출을 드러내 놓고 실패시키고 턴을 중단하며, 그러면 풀린다는 것이 측정됐다.
자세한 것은 [agent-host.ko.md](agent-host.ko.md) §4.3에 있다.

### 4.4 키퍼가 스스로를 넘겨준다 (#280, 옵션 C 4단계)

키퍼 업데이트는 아무것도 끊으면 안 된다: 호스트도, 도는 턴도, 터미널이나 개발 서버도, 클라이언트의 연결도. `exec`는
macOS와 Linux에서 pid와 디스크립터를 지키지만 Windows에는 그에 맞는 것이 없다. 그래서 방향은 모든 OS에서 같다:
**새 키퍼를 띄우고, 모든 핸들을 넘기고, 옛 키퍼는 끝난다** (`keeper/handoff/`).

```
키퍼 A (도는 빌드)                                   키퍼 B (새 빌드, 자기 번들에서)
 1  B를 띄운다: centralu --keeper --take-over-fd 3  ──▶  hello
 2  얼린다: 받지 않고, 모든 중계를 세우고,
    호스트 stdout을 멈추고, 자식 표를 얼린다
 3  상태 + 버퍼 + 디스크립터 (SCM_RIGHTS)          ──▶  4  I/O 없이 모두 다시 세운다; 잠금을 쥐었는지 확인
 6  커밋 지점, ready를 받으면: 거두고 commit을 보내 ◀──  5  ready
    아무것도 건드리지 않고 끝난다                  ──▶  7  모든 I/O를 시작하고 호스트를 넘겨받아 일한다;
                                                            바꾸기가 요청됐으면 이어서 호스트를 교체한다
```

**넘어가는 것:** `keeper.lock`(같은 열린 파일 설명이라 `flock`에 빈틈이 없다), `keeper.sock`과 `children.sock`의
리스너, 정문의 리스너와 토큰, 호스트의 stdin과 stdout, 모든 자식의 파이프나 pty 마스터, 자식 소켓의 모든 연결, 정문이
중계하는 모든 연결의 양쪽 소켓, 붙어 있는 모든 창의 연결, 그리고 데이터로: 절대 오프셋이 붙은 모든 버퍼, 반쯤 읽은 요청,
보내지 않은 이벤트, 태그, pid, 종료 상태, 빌드 기록, 설정, 유휴 시계, 마지막 교체.

**살아남는 것과 다시 붙는 것.** 다시 붙는 것은 없다. 호스트는 같은 프로세스이고 아무것도 알아채지 못한다: 파이프와
자식 소켓 연결이 같은 소켓이고, 이제 B가 쥐고 있을 뿐이다. 정문을 지나는 WebSocket, 앱 뷰의 트래픽, Codex 브리지의
연결은 같은 TCP 연결이고 B가 퍼 나른다. 붙어 있는 창은 제어 연결을 그대로 갖고, 그 연결로 B의 다음 상태를 듣는다.
리슨 큐에서 기다리던 연결은 B가 받는다. 돌려보내는 것은 얼리는 바로 그 순간에 들어온 `status` 아닌 제어 요청 하나뿐이고,
"다시 시도하라"는 답을 받으며 앱의 재시도는 B에 닿는다.

| 결정 | 이유 |
|---|---|
| B는 새 빌드의 실행 파일을 **그 번들 안에서**, 붙는 앱이 알려 주는 경로(`current_exe`)로 띄운다. 복사본은 쓰지 않는다 | 키퍼가 앱 자신의 서명된 실행 파일인 것은 macOS가 그것을 Centralu로 여기게 하려는 것이다(#220). 번들 밖 복사본은 다른 프로그램이 된다. 나중에 번들이 바뀌어도 B는 흔들리지 않는다: `tauri build`는 옛 `.app`을 지우고 새로 쓰며(`bundle_project`, tauri-bundler 2.10), `centralu install`은 `rmSync` 뒤 `ditto`를 한다. 그래서 도는 실행 파일의 파일은 덮어써지지 않고 링크만 풀리며 계속 돈다(통합 스크립트는 키퍼 A가 도는 중에 그 실행 파일을 지우고 다시 쓰고, A는 계속 일하다 넘겨준다). 제자리 덮어쓰기에 기대서는 안 된다: 도는 키퍼의 파일을 제자리에서 덮어쓴 시험에서 키퍼는 지켜본 3초 동안 계속 답했는데, 코드가 이미 메모리에 올라 있었기 때문이고, 아직 올리지 않은 페이지는 새 파일에서 온다. 트리 안에 제자리에서 덮어쓰는 곳은 없다. |
| 채널은 B의 디스크립터 3에 놓은 `socketpair`의 한쪽이고, 소켓 파일이 아니다 | 경로가 없어 다른 프로세스는 아예 붙을 수 없다(`0600`보다 강하다). 치울 것도 없다. B는 그래도 상대의 uid를 확인한다. |
| A는 비우지(drain) 않고 **얼린다** | A가 읽고 넘기지 않은 바이트는 A와 함께 사라진다(#280 측정의 규칙: 떠나는 키퍼는 미리 읽지 말거나, 읽은 것을 넘겨야 한다). 얼면 A는 더 읽지 않고, 쥔 것은 모두 스냅숏에 든다. 중계는 두 복사 사이에서, 호스트 리더는 두 줄 사이에서, 자식 표는 두 차례 사이에서 선다. |
| 커밋 지점은 A가 `ready`를 받는 순간이다 | 그 전의 실패(B가 안 뜸, 다시 세우기 실패, B가 죽음, 시간 초과)는 A를 되돌린다: B를 죽이고 녹는다. 닫은 것도(스냅숏은 복제본을 쥔다) 읽은 것도 없으니 멈춘 그 자리에서 이어 간다. 그 뒤로 A는 다시 일하지 않는다. B는 `ready` 뒤 `commit` 없이 채널이 닫히면 A가 죽은 것으로 본다: A가 없으면 모든 것의 유일한 사본을 쥔 자기가 넘겨받고, A가 아직 있으면 끝난다. |
| B는 `ready` 전에 모두 다시 세우지만, `commit` 전에는 읽기도 쓰기도 시작하지 않는다 | 되돌아간 A가 모든 자식과 소켓의 유일한 독자여야 한다. |
| A는 커밋 때 거두고 그 종료 상태를 넘긴다 | B는 자식들의 부모가 아니다. kqueue `NOTE_EXIT \| NOTE_EXITSTATUS`는 자식이 아닌 프로세스의 상태도 준다(#280 측정). 하지만 이미 좀비가 된 자식에 등록하면 `ESRCH`로 실패한다(2026-10-04 측정, Darwin 27). 그래서 얼어 있는 동안 끝난 자식들의 상태는 A에게서 온다. A가 끝나면 launchd(또는 init)가 거둔다. Linux에서는 pidfd가 자식 아닌 프로세스가 끝났음을 알려 주고, 상태는 좀비가 남아 있는 동안 `/proc/<pid>/stat`에서 읽으며, 아니면 모른다(부모 아닌 쪽의 종료 상태는 `PIDFD_GET_INFO`, Linux 6.15 전에는 없다). |
| "이 빌드로 바꾸기"는 키퍼를 먼저 옮기고, 새 키퍼가 호스트를 교체한다. 한 번의 동작이다 | 키퍼를 옮기는 데는 비용이 없으니 따로 물을 것이 없고, 전체 업데이트가 키퍼·호스트·앱이 한 빌드인 채로 끝난다. 키퍼가 먼저이면 빌드를 넘나드는 모든 교환을 새 쪽이 읽는다: B가 A의 스냅숏을 읽고, A의 호스트를 지켜보고, A의 호스트를 비우고 자기 빌드의 호스트를 띄운다. 호스트를 먼저 바꾸면 옛 키퍼가 더 새 호스트를 다루게 된다. |
| 넘겨주기가 실패해도 호스트 바꾸기는 진행한다 | 사람이 바란 것은 호스트 바꾸기이고, 옛 키퍼도 3단계처럼 그것을 할 수 있다(beta.10도 이미 그렇다: `move_keeper`는 되돌려진 넘겨주기 뒤에 언제나 호스트 교체로 넘어간다). 빌드를 건너는 키퍼↔호스트 통신은 키퍼가 해석하지 않는 줄과 자식 태그이므로, 옛 키퍼가 새 호스트를 돌보는 것은 3단계의 경우이지 새 경우가 아니다. |
| 호스트가 창의 빌드에 오르면, 남은 키퍼는 실패가 아니라 안내다 (#387) | 실패하는 넘겨주기의 고침은 **보내는** 키퍼에 있고, 업데이트에서 보내는 쪽은 업데이트가 바꿀 수 없는 옛, 돌고 있는 빌드다. beta.10의 키퍼는 상태가 크면 macOS에서 매번 "Message too long"으로 실패한다(아래 줄). "Switch to this build"를 다시 권하면 실패만 되풀이했고, 두 번째 시도는 창이 이미 자기 빌드의 호스트에 붙어 있는데도 "Could not switch builds"라고 읽혔다. 그래서 호스트는 창의 빌드이고 키퍼는 아니며, 이 빌드로의 마지막 교체가 키퍼가 남은 이유를 말하면(`keeperStaysBehind`, `switch-plan.ts`) 막대는 "Running this build. The background keeper moves to it the next time it restarts."라고 말하고 바꾸기 대신 **Restart completely**를 권한다. 창이 저절로 다시 바꾸지도 않는다. "Could not switch builds"는 호스트가 그 빌드에 닿지 못한 교체에만 남는다. |
| "Restart completely"는 키퍼를 멈추고, 창이 자기 빌드의 키퍼를 띄운다 | "Quit completely"가 쓰는 키퍼의 `stop`이므로 그것이 멈추는 것(호스트, 모든 에이전트 프로세스, 터미널, 도는 명령; 확인 창이 그렇게 말한다)을 멈추지만, 창은 남는다: 붙어 있던 고리가 키퍼의 종료를 보고 자기 실행 파일과 자기 호스트로 키퍼를 띄워 다시 붙는다. 대화는 저장소로 이어진다. 키퍼의 다음 유휴 종료나 종료를 기다리면, 백그라운드 모드에서는 고친 키퍼가 며칠이고 쓰이지 않는다. |
| 자리가 없는 디스크립터 묶음은 자리가 날 때까지, 30초까지 기다린다 | macOS에서 스트림 소켓으로 디스크립터를 실은 `sendmsg`는 8 KiB 송신 버퍼(`net.local.stream.sendspace`)에 묶음만큼의 자리가 없으면 막히지 않고 바로 `EMSGSIZE`로 실패한다. Linux는 막힌다. 일어나는지는 각 묶음 앞의 정확한 바이트 수에 달려 있어서, 충분히 큰 상태(에이전트 4, 터미널 2, 앱 화면 7, 중계 연결 여럿; 2026-10-05)는 실제로 걸렸고 작은 테스트 상태는 한 번도 걸리지 않았다. 묶음은 한 바이트를 싣기 때문에 실패한 시도는 아무것도 보내지 않았고, 다시 보내도 겹치거나 쪼개지지 않는다. 이 한도는 살아 있지만 읽지 않는 새 키퍼에만 의미가 있다(죽은 키퍼는 보내기를 바로 실패시킨다). 그동안 모든 것이 얼어 있으니 영원히 기다리기보다 되돌리는 편이 낫다. `wire.rs`는 디스크립터 앞의 바이트 수를 버퍼 세 개 분량에 걸쳐 훑는다. |
| 스냅숏 형식에는 버전이 있고, 늘어나기만 한다 | 업데이트에서 떠나는 키퍼는 더 오래된 빌드이니, 새 키퍼가 옛 형식을 읽는다. 4단계 이전의 키퍼는 스스로를 넘길 수 없다: 4단계 빌드로 가는 첫 업데이트는 호스트만 교체한다. |

`scripts/keeper-handoff-integration.mjs`로 측정했다(macOS, 디버그 빌드, 도구 호출 중인 claude 턴과 codex 턴, 50ms마다
찍는 터미널, 100ms마다 찍는 개발 서버): 넘겨주기는 테스트가 거는 1.5초 대기 말고 0.5–0.8초 걸렸고, 호스트와 자식의
pid가 그대로 이어졌고, 카운터가 끊기지 않았고, 모든 도구 호출이 한 번씩 기록됐다. 커밋 전에 죽인 넘겨주기는 A가 모든
것을 계속 맡게 남겼다.

검증하지 않은 것: 키퍼가 띄운 키퍼에 대해 macOS가 어느 정체성에 책임을 묻는지(B는 A의 책임 프로세스, 곧 A를 띄운 앱을
물려받는다); Linux에서의 처음부터 끝까지(단위 테스트는 Docker에서 돌렸다); 키퍼가 없는 Windows(`DuplicateHandle`이
핸들을 넘기는 길이 될 것이다).

### 4.5 업데이트 적용: 한 번 누르거나, 한가할 때 저절로 (#352)

§4.1–4.4로 업데이트가 아무것도 끊지 않게 됐지만, 적용하려면 세 단계가 필요했다: 설치, 창을 닫았다 다시 열기,
"Switch to this build" 누르기. "Apply now"는 업데이트 줄에서 이 전부를 한다:

```
창 (옛 빌드)                         키퍼 (옛)                          창 (새 빌드)
 1 호스트가 업데이트를 설치했다:
   npm i -g centralu@<v>, centralu install (디스크의 번들이 바뀐다)
 2 relaunch_info: 디스크의 번들이 다른 빌드다 → "Apply now"
 3 relaunching  ─────────────────▶  창이 없어도 60초 동안 버틴다,
                                    백그라운드 모드가 무엇이든
 4 request_restart: 옛 창이 떨어져 나가 끝나고, Tauri가 같은 실행 파일 경로를 다시 띄운다
                                                                       5 붙는다 ◀── relaunched: true
                                                                       6 잃을 것이 없다 → 바꾼다
                                    7 키퍼 넘겨주기(§4.4), 이어서 호스트 교체(§4.2)
```

| 결정 | 이유 |
|---|---|
| 다시 띄우기는 같은 실행 파일 경로에 대한 Tauri의 `request_restart`다 | `centralu install`은 번들을 바꾼다(`rmSync` 다음 `ditto`). 그래서 도는 프로세스가 띄워진 경로가 이제 새 빌드의 실행 파일을 가리킨다. `tauri::process::restart`(2.11.5)는 번들의 새 `Info.plist`에서 실행 파일 이름을 읽어 그것을 띄운다. `restart`가 아니라 `request_restart`인 것은, 명령은 메인 스레드에서 도는데 거기서 `restart`는 종료 이벤트를, 그와 함께 떨어져 나가기를 건너뛰기 때문이다. |
| "Apply now"는 디스크의 빌드가 창의 빌드와 다를 때만 보인다(`relaunch_info`) | `pnpm app:open`에서는 창이 빌드 결과물에서 돌고, 업데이트는 그것을 건드리지 않으므로 다시 띄워도 같은 빌드가 뜬다. 그래서 줄은 계속 "restart"라고 하고, 이유는 툴팁에 있다. `pnpm app:dev`와 다른 직접 모드 빌드에는 키퍼가 없어서, 다시 띄우면 모든 에이전트가 멈춘다. 이들도 "restart"로 남는다. |
| 앱은 백그라운드 모드에 기대지 않고 키퍼에 다시 띄우기를 알린다(`relaunching`) | 백그라운드 모드가 꺼져 있으면(기본값) 옛 창이 닫히는 것이 "마지막 창이 떠났다"가 되어 모든 것을 멈췄다. 업데이트의 요점이 종료에 관한 설정 하나에 날아간 것이다. 유예는 60초(최대 300초)다: 다시 띄우기는 몇 초면 되고, 백그라운드 모드가 꺼진 키퍼가 실패한 다시 띄우기보다 많이 오래 살면 안 된다. 그 안에 창이 붙지 않으면, 아무것도 알리지 않았던 것처럼 유휴 규칙이 적용된다. 다른 모든 연산처럼 피어 uid를 검사한다. |
| `relaunching`을 모르는 오래된 키퍼는 백그라운드 모드가 켜져 있을 때만 받아들인다 | 켜져 있으면 창이 닫혀도 멈춘 것이 없었다. 꺼져 있으면 다시 띄우기가 모든 턴을 끊을 것이므로, 앱은 거절하고 이유를 말한다. |
| 키퍼는 다음 창에 그것이 다시 띄운 창이라고 알린다(attach 응답의 `relaunched`) | 창이 클릭 없이 바꾸려면 자기가 "Apply now"에서 왔다는 것을 알아야 한다. 두 창을 다 본 것은 키퍼뿐이다. 다음 attach가 유예를 써 버리므로, 나중에 손으로 연 창을 그것으로 착각하지 않는다. |
| 다시 띄운 창은 `switchPlan`이 잃을 것이 없다고 할 때만 저절로 바꾸고, 아니면 바로 묻는다 | "Apply now"를 누른 것은 다시 띄우기에 대한 동의이지, 느린 오케스트레이터 호출을 끊는 것에 대한 동의가 아니다. 방금 누른 사람이므로, 질문을 바에 남겨 두지 않고 지금 묻는다. |
| "Apply updates automatically when idle"(기본 꺼짐): 호스트는 확인이 새 버전을 찾자마자 설치하고, 창은 한가할 때 다시 띄운다 | 설치는 에이전트가 일하는 중에도 안전하다(키퍼와 모든 호스트는 자기 복사본에서 돈다). 적용은 호스트의 유일한 유휴 규칙(`hostBusy`, `agent-host/src/idle.ts`, 키퍼에 보고되고 키퍼에서 창으로 간다)을 기다린다: 일하거나 승인·질문을 기다리거나 백그라운드 작업을 돌리는 세션이 없고, 터미널도, 명령도 없을 때. 턴이 끝난 세션(`waiting_input`)은 한가하다. 2026-10-05까지는 바쁜 것으로 쳐서, 한 번이라도 답한 세션이 있으면 막혔다. 모르면 바쁜 것으로 친다. 그리고 텍스트 칸에 20초 동안 키 입력이 없을 때: 누군가 타이핑하는 손 밑에서 다시 띄우면 충돌처럼 보인다. 이 설정이 켜진 창은 한가할 때 저절로 바꾸기도 하고, 잃을 것이 있으면 묻지 않고 기다린다. |
| 이미 설치된 버전을 돌리는 창에서는 하지 않고, 창마다 한 번만 한다 | 다시 띄운 창도 옛 호스트의 `restart_required`를 본다. 이 검사가 없으면 자기 자신으로 끝없이 다시 띄울 것이다. 실패는 줄이나 바에 남고, 고리로 다시 시도하지 않는다. |

실행해 보지 않은 것: 패키지된 앱에서의 실제 업데이트; 창이 다시 띄운 창에 대해 macOS가 어느 정체성에 책임을 묻는지
(Tauri는 LaunchServices를 거치지 않고 실행 파일을 직접 띄운다); 열린 터미널은 셸이 프롬프트에 있어도 바쁜 것으로
치므로, 자동 모드는 모든 터미널이 닫힐 때까지 기다린다.

## 5. 데이터 흐름 (요약 — 상세는 [state-management.ko.md](state-management.ko.md))

```

                    │

## 7. M0과의 연결

M0 스파이크(product spec §8)는 이 구조를 관통하는 **하나의 수직 슬라이스**다: `agent-host`(ClaudeAdapter 1개, WS 전송) + `protocol`(최소 이벤트 스키마) + 브라우저에서 접속하는 단일 페이지 UI. 이것으로 §4의 토폴로지와 권한 오버라이드 전제가 실제로 성립하는지 확인한 뒤, 나머지를 채운다.

```

### 왜 탭이 아닌가

탭은 **서로 대체 관계인 것들**을 묶는 장치다. 하지만 git 상태는 대화를 대체하는 화면이 아니라, 대화가 주장하는 내용에 대한 **증거**다. 에이전트가 "파일 세 개를 고쳤다"고 말할 때 그것을 확인하는 곳이 여기이므로, 나란히 놓여 있어야 한다. 대체 관계가 아닌 것들을 탭으로 묶은 것이 도그푸딩에서 나온 "git, 파일, 뷰어는 어디서 보나?"를 만들어낸 원인이다.

### 오른쪽 패널 내부: git / files 두 개의 탭

```
┌─ alpha   main        › ─┐   ← press the branch for the switch screen
│ [git] files            │
├────────────────────────┤
│ changed 3        wide  │
│ M src/a.ts             │
│ A src/b.ts             │   ← press for a diff in the overlay
│ ─ push 2               │
│ [commit message ] c  p │
├────────────────────────┤
│ history                │
│ ● fixed inbox ordering │   ← press for the commit in the overlay
│ ○ add session delete ·m│
└────────────────────────┘
```

git 탭은 **서로 다른 두 질문**을 위아래로 배치한다: 위는 "지금 무엇이 바뀌었나", 아래는 "여기까지 어떻게 왔나"다. 커밋과 푸시는 좁은 공간에서도 동작해야 한다 — 확인하고 곧바로 마무리하는 흐름이 끊기면 결국 터미널로 떠나게 된다.

히스토리에는 그래프 선을 그리지 않는다. 340px에서 선을 그리면 제목이 들어갈 자리가 없고, 실제로 알고 싶은 것은 '무엇이 언제 들어왔나'다. 머지만 표시한다.

### 접었을 때: 사라지지 않고 스트립이 남는다

패널을 접으면 32px 세로 스트립이 남는다. `⌘B`를 모른 채 닫아도 돌아갈 길이 눈에 보여야 하고, 스트립은 변경된 파일 수를 유지해서 접힌 상태에서도 "뭔가 바뀌었다"는 것을 읽을 수 있게 한다. 사라진 것과 접힌 것은 다른 것이다.

### 뷰어는 넓은 오버레이다

이 앱에서 뷰어의 주 용도는 사실상 '에이전트가 만든 diff 확인'인데, diff는 340px에서는 읽을 수 없다. 그렇다고 대화의 자리를 차지하면 다 읽은 뒤 되돌아가는 길을 찾아야 한다. 코드를 읽는 것은 깊지만 **짧은** 행위이므로, 덮었다가 esc로 쓸어내는 것이 맞는 메커니즘이다 — 쓸어내면 대화는 스크롤 위치까지 포함해 정확히 그 자리에 그대로 있다.

오버레이는 **가운데와 오른쪽만** 덮는다. 왼쪽까지 덮으면 코드를 읽는 동안 다른 세션이 나를 부르는 것을 놓친다. 그것은 관제탑에서 계기판을 가리는 일이다.
