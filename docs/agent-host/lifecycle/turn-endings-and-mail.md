# Turns that stopped without anyone asking (#698)

A turn can end before its work does, and nothing about the session says so: it rests in `error`, `idle` or
`waiting_input` like any other. On 2026-10-15 the internet dropped twice while several child sessions worked. The
Claude children ended in `error` (the CLI retried `api_retry` ten times, about three minutes, then failed with
`ECONNREFUSED` and `ENOTFOUND`) and sat there until the person sent "continue" by hand; the turns had been opened by
the CLI itself (a Monitor firing), so no report was owed and the Assistant that started them heard nothing. A Codex
child's interrupted turn was reported to its Assistant as "The assigned work finished", and "Quit completely" reset
sessions mid-turn to `idle` with no line in their conversation.

The host now keeps **why the last turn did not finish** on the session (`SessionInfo.interruption`, stored as
`sessions.interruption`, store v53) and sends each change as an `interruption` event. Reading it from the events is
tool-neutral (`sessions/interruptions.ts`):

| Reason | Set when | Cleared when |
|---|---|---|
| `network` | a running turn ends in an error the network caused (`interruptionAfter` with `endedTurn`; a crash, `adapter_crashed`, and an error at rest are not): the error codes (`ECONNREFUSED`, `ENOTFOUND`, ...), Claude's "API Error: No response from API / Can't reach the API server / Connection refused, lost, reset, error, dropped / Request timed out / No internet route / Unable to connect to API / fetch failed" (the wordings read in the CLI's own connection-failure function; "Unable to connect to API: SSL …" is a setting, not the network), the computer sleeping, Codex's "stream disconnected before completion", "failed to lookup address information", "Connection failed: error sending request", "waiting for network" (`isNetworkFailure`; the sentences measured in the real store and host.log). Only the tool's sentence counts, not the stderr tail a crash carries (`failureSentence`); generic words ("connection closed", "network error") count only inside those sentences, since an MCP server or a dev server can say them | the session works again (`working`, output), or a turn ends otherwise |
| `quit` | a start finds the session `working` or `waiting_approval` with no process (a full quit, a reboot, a crash), or a turn an update or a swap cut could not be continued ([continue-after-update.md](continue-after-update.md), #1618, #1966; one that is continued is not marked). A warning line from Centralu is written into the conversation ("Centralu quit or restarted while this turn was running …") | the same |
| `shutdown` | the last host was told the system was ending (a shutdown, restart or sign-out, #1397; `system-end.json`, below). Then a session that was `working` or `waiting_approval` with no process gets this reason instead of `quit` (unless it has rows from more than 2 minutes after that end, `SYSTEM_END_TAIL_MS`: a later host's, of a build that reads no notice), and so does a session in `error` whose newest error, past the `internal` one closing the handle writes for follow-ups still queued, is an `adapter_crashed` stamped from 30 s before the notice (`SYSTEM_END_LEAD_MS`: where the system ends every process at once, the agent may exit before the host asks) to 2 minutes after it. Both are reset to `idle` and get a warning line ("This turn stopped before it finished: the computer shut down, restarted or signed out while it was running …"; the words are `SHUTDOWN_WORDS` in the protocol, the same in the label, the note, the list and the report); a session at rest or one that crashed outside that span is left as it is. With no notice (a quit, any other stop, a host killed with no notice) nothing is guessed: a cut turn stays `quit` and a crash an error. Known: the caller of a delegated turn whose agent crashed in that span keeps the old host's "failed" report, sent before the host went, while the child then reads `shutdown`; it is reported once. `lifecycle/system-end.ts` | the same |
| `interrupted` | a turn ends `waiting_input` with the reason `interrupted_by_tool` (`INTERRUPTED_BY_TOOL`): Codex's `turn/completed {status: "interrupted"}` for a turn no `turn/interrupt` of ours preceded | the same |
| `reconnecting` | the tool has stayed `retrying` for `RECONNECTING_FLAG_MS` (5 minutes): Codex waits for the network without end. Live only, never stored | the activity moves off `retrying` or the turn ends |

| Decision | Why |
|---|---|
| An app request cancelled mid-turn fails its wait before it interrupts the session | Claude's adapter ends the turn as soon as the CLI confirms the interrupt, before the turn's result, so the wait read the cancel as "stopped before it finished" |
| Classify and surface; never resend by itself, except the turns a linked hub's update cut (owner, 2026-10-26, #1618: [continue-after-update.md](continue-after-update.md), "Continuing the turns an update cut"), which the next host continues once with the same sentence | A resent turn can repeat side effects (a push, a comment, a release). Continuing is one message from the person or the asker, the same sentence both ways: "Continue where you stopped. Check what already happened before repeating a step." Auto-resend on reconnect could come later as an opt-in |
| A Codex `interrupted` turn ends as a Stop does (`state_change waiting_input`), not as `turn_complete` | `turn_complete` is "finished": the Assistant was told the work was done. A wait on the turn (`AgentRunWait`) ends on the interrupt, since no `turn_complete` follows it now |
| The Codex adapter tells its own interrupts from Codex's and logs which (`interruptsSent`, "interrupted by a stop from Centralu" / "by Codex"). A Stop that lands while a note's `turn/start` is in flight interrupts the turn the answer names, and counts as ours too (`takeInputTurn`) | The real case could not tell whether the person's Stop, the host or the CLI sent it |
| The person's Stop, and an Assistant's `agent_session stop`, set nothing | They know; flagging their own act would be noise |
| Only `retrying` starts the `reconnecting` clock, never silence | A session polling CI with 15–40 s sleeps looked frozen and was not; long builds look the same |
| A report owed for the turn names the reason first ("stopped before finishing: a network error ended its turn", "its tool interrupted the turn") and how to go on | "The assigned work failed" made the asker redo or abandon work that only needed a "continue" |
| Who hears of a stop is the mailbox's stop notice alone (`StopNotices.sessionsStopped`, [mailbox.md §10.6.1](../../plans/mailbox.md)): each sender of what the session left unanswered (the cut turn's questions, its open tasks) is told and woken; the session that started it (a delegation's caller nobody waits for now, else `askedBy`) is told once, woken only from a turn. A call still waiting reads the stop from its own answer | The 2026-10-15 case, and an `ask_project` turn whose session has no `askedBy`. Owner (2026-11-10, #1948): a session owed a reply is woken, any other sleeping one reads the notice at its next wake. One notice per stopped turn; another needs another turn, so two sessions cannot wake each other in a loop |
| Every report and every word Centralu gives a session about its request (a start that did not start, a note or a queued request that did not go) goes through `tellSession` (#428): never while the host hands over or quits, never to a session that is gone | A quit used to report each running child as "failed: Centralu is shutting down" in its caller, which the next start then told again as a `quit` stop, and a report could wake a sleeping caller on the way out |
| A `quit` is told at the next start by the same stop notice, in one write for every session it cut: the sender of each open task or cut question is told and woken, the starter told quietly. **No session that is itself stopped by a quit** is woken: it reads the notice once the person continues it | The start drops the report marks of the turns it cut, so the task's sender would never hear otherwise. A restart wakes no session that needs nothing (owner, 2026-11-10). An Assistant the same quit cut would be resumed at launch with nobody there, and that turn would clear its own "stopped" mark before the person saw it |
| The Assistant's list (`list_sessions`, and `read_session` with no id for a reader) and `agent_session status` add "stopped: network error", "stopped: Centralu quit during its turn", "stopped: its tool interrupted the turn" or "reconnecting to its API for N min" to the row. No filter argument | The row already says it, and an argument rides in every request's tool definitions (docs/tool-cost.md). `agent_session list` (#690) names such a child `stopped` and leaves the reason to `status`: it is a list for cleaning up, where what matters is that the child's work is not over |
| The screen shows it beside the state: the inbox row's word and **Continue**, the sidebar mark's ring (only while the stopped turn's answer is unread, #1549) and tooltip, a line above the composer (product-spec FR-15) | The state alone looks the same for a stopped turn and a finished one; Continue is the one message that goes on |
| `CLAUDE_CODE_MAX_RETRIES` is left as the CLI sets it | Its three minutes outlast most drops; a longer budget would hold a turn hostage through a long outage |

## The mailbox's delivery in the host (#1347)

`MailDelivery` (`mail/delivery.ts`) starts once the host is ready and **stops first** when it leaves, before the sessions are let go of
(`lifecycle/shutdown.ts`), so a host handing over wakes no session the next one takes. A delivery already waiting for a session to
wake checks again before it sends (`deliverMail`'s `leaving`). It writes a heartbeat (`mail.heartbeat`) with each 60 s sweep, except
while the person has not answered for a crowd of sleeping sessions, so that a restart asks again. A host that was off, or away without
stopping, more than 30 minutes wakes a sleeping session only for mail that needs it (§7.9); plain news it held back starts no turn of its own
when the person only opens the session, and goes with the next mail that wakes it (#1951). The sweep also runs the mailbox's retention
and moves on the work of a session that left without telling the mailbox. Sleeping sessions are resumed two at a time.

A wake is delivered when the tool says it took the input (`takeInput`, `sessions/session-events.ts`); a tool silent for 90 s counts as
having taken it, because sending it again could run the work twice. If that tool then **fails** the input (a session closed with it
queued, a rejected `turn/start`), the delivery makes the mail unread and undelivered again and holds it `failed` for the person (Inbox:
Retry): a failure told that late does not prove the tool never ran it, so nothing sends it again by itself. A failure after the tool
took it is not acted on. The tool keeps the wake in its own record as a user turn; the host writes no user row for it, so the catch-up and the import
that read the record back leave the wake out (`mail/wake-text.ts`, used by `stripInjectedBlocks`): the `✉` line the delivery
wrote is its only trace in the conversation, and `read_session` and `recall` never show it as the person's message.

**Mail without threads (M3a, #1684, docs/plans/mailbox.md §7 to §9).** The host's mail is messages in `mail` and `mail_recipients`, wired
once in `mail/host-mail.ts` (`hostMail`, used by `main.ts` and by the tests): the message service (`mail/messages.ts`), the one reach module
(`mail/reach.ts`: who may write to whom, project trust, the one hold), the turns and guards (`mail/turns.ts`), the delivery, and the `mail` tool,
whose advertised schema is still the version-1 one: each old action is mapped onto the service (`reply` answers a message, `handled` is `done`,
`read` reads a message and its chain, `send` sends a new message, `update` and `close` are refused `removed`). After the ready line, before
delivery starts, `afterReady` moves the thread mail an older build left pending (once, in one transaction, `Store.movePendingThreadMail`), then
brings the task rows in step with the old report paths (`takeOverFromEarlierBuild`, §9.5). The person's window still reads the thread tables
until the person's host methods move to the service (M3a-person, in the same release).

**Delegations write tasks; the old report paths stay the truth until M8** (§9, D18). Each place a session gives another work calls
`ChildOwnership.delegated` once the old path delivered it, and `delegationRecorder` writes a `task` from the caller to the child, delivered and
read, caused by the turn the caller is in; the child's turn the task started is that task's (`MailTurns.attach`). A script's or the RPC's first
message is a task from the person. Before a delegation out of a session's untrusted project starts anything, the tool asks
`MailHooks.refusesDelegation` (§7.4): it answers S15, starts nothing, and records the call so trusting the project tells the caller once (S16).
`ChildReports` still decides when a report is due (report marks, paused reports, queued requests, linked reports); `reportRecorder` writes
Centralu's report on the turn's task (§9.2) and answers `ReportedAs` per §9.3: a turn that ended for good settles the task and every other open
task of the pair delivered before the turn began; a pause (`paused`, or `waiting` on work handed on that the old paths still owe, or not yet
delivered) leaves it open, wakes the owner the first time and is quiet after; an update's cut that goes on is the old path's to say. The end of
the Assistant's turn on a session's request is S12 to the asker, and settles the requests that turn carried. A call that returned the answer
is the report, written as told. At each ready a report mark with no task gets one, and a task no old path owes any more is settled
(`oldOwes`, `ChildOwnership.oldOwes`).

**Turns** (§8.2). The delivery begins a turn with its work message (a task, or for the Assistant one asker's request) and the message that
started it (the person's words when the wake carries them, else its first item); what the turn sends records that starter as its cause and
A turn the person or the CLI started has no cause. A turn continued after a restart or an update (kept by the keeper,
or cut by an update's stop and continued, `HostTenure.keptInTurn`) writes no new row: its open row is read back with its starter, work and
asker, so neither count below counts it again. Nothing holds or defers mail for how much of it there is (#2014): past 20 mail-started turns an
hour between two sessions, counted from the store since the person's last word to either, or past 120 on the host, the delivery writes the
person one notice in the Inbox, once per clock hour each (`warnIfRunning`), and the mail goes on. An Assistant made takes the role's unsettled mail another session held, the one before it in the trash included (`roleMoved`, §7.7); a
trashed session's watched rows are settled `gone` and their senders told (`partyGone`), except what was sent to the role, which waits for the next.

**The first message is the script's, not the person's** (3.8b). Only words the person typed may pass as theirs, and a script's first message can carry outside words (a CI log, an issue title). So `createSession` over the limited credential stores it, and announces it as `user_message`, with `fromScript: { credential }`, where `credential` is what the connection called itself in its hello (`RpcContext.label`, cut by the transport, never checked), made plain by `scriptLabel` (no quote, bracket, angle bracket or line break; `unnamed` when it said nothing). It is written by the host from the connection, never from a field of the call: a window's call has none, and a field in the params is ignored. The session reads it under a header of Centralu's (`scriptMessageFrame`: "sent by the script <label> the person set up; the person did not type it"), every line behind `> `, not stamped `origin: human`. The screen draws it as the script's (its label, drawn as the agent's bubble, like an app's message), not as the person's bubble; `read_session` gives the line `fromScript`, `recall` marks it `[script "<label>"]`, a handoff record and an Assistant's memory do not take it for the person's; the session is not named from it. The person's task carries the label as a fact (`facts.fromScript`), so `mail read` says a script wrote it, not the person, the Inbox draws it under the script's label and its subject names the script; the sender stays the person, so reports still land in the Inbox. A call the person allowed on a card keeps the label (`HostRequests` passes it on). The label is the script's own claim: every process of the user holds the one limited credential, so any script may call itself anything, another script's name or `Centralu` included. It stands in quotes in every sentence of Centralu's (`the script "<label>"`), says who the script says it is and nothing more, and grants nothing. A later `agents.send` by a script is marked the same way, from the calling connection (`TurnInputs.send`'s `fromScript`): stored and announced as the script's, under the same header, not stamped `origin: human`, not naming the session, and with no `intent` (a script cannot take over a report another session is owed); it is the work's turn, not the person's own, so a thread the person owes is reported when it ends. `apps.askBuilder` and `apps.sendError` from a script are marked the same way (#1468), and the builder's header says a script sent it, not that the person wrote it; `read_session`'s card in the window names the script or the app on such a line. A linked machine never sees the script's connection, only the hub's own link, so it would store the text as the person's: the hub refuses a script's text call to a machine (`SCRIPT_TEXT`, links/routes.ts) and says to run the script on that machine. A `dev:live` page holds the limited credential, so what it sends is labelled a script's; it is not a Centralu window, and only development builds run it.

The end of the first turn that is the work's (`reportToPersonIfOwed`, for a turn no one else is owed and the person did not start) is a report in the person's thread: Centralu's
words (`personReportLine`: how the turn ended, a count of tasks, nothing of the session's words), the session's last response as its own relayed message beside them, the
`failed` kind as a fact; the thread goes to `review`, so the turns after it are the person's own and are not reported. A turn that left the session's own background work
running is a pause: the thread stays `running`, the same count of tasks is said once, and the turn that work's end starts is the report. A turn a quit cut (the next start found the session mid-turn with no process) is reported as the `quit` it was, and the thread goes to `review`. A pause whose background work ends with no turn after it is settled as a report mark's is (#1463, `settlePausedReport`, 60 s): the person is told the work ended, with its last answer, and the task is reported. The pause is kept with a caller's, by kind (`ChildOwnership.personPausedReports`, the app setting `person_report_paused:<session>`), so a quit or a crash does not leave the task paused for good: the next start reports the work as ended, each task stopped with the process, and a deleted session's pause goes with it (`forgetTurns`). A first message that throws after the session started withdraws the person's task (`ChildOwnership.firstMessage`): no work began. Also not done: a session started on a linked machine has no thread.
