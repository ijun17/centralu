## 1. 개요

### 1.1 문제

에이전틱 코딩 도구를 실제 업무에 쓰다 보면 결국 **여러 프로젝트 × 여러 세션**을 동시에 돌리게 된다. 현재 워크플로에서 아픈 지점:

- 터미널 탭이 수십 개로 불어나고, **어느 세션이 내 입력을 기다리는지** 알 방법이 없다.
- 에이전트가 바꾼 파일을 보려면 프로젝트마다 따로 IDE를 열거나 `git status`를 실행해야 한다.
- 도구별(Claude Code / Codex) 사용량과 컨텍스트 상태가 흩어져 있어 전체 그림이 잡히지 않는다.
- 이를 위해 IDE를 여러 개 띄우면 머신이 감당하기 어려울 만큼 RAM과 배터리를 잡아먹는다.

문제의 핵심은 여러 세션을 한 번에 볼 수 없다는 것이 아니라 **터미널 탭이 흩어져 있다는 것**이다. 이 구분이 화면 설계(§5)의 출발점이다.

### 1.2 이 제품은 무엇인가

**Centralu**는 "에이전트 관제탑"이다. 코드를 *작성하는* 도구가 아니라 — 코드를 쓰는 에이전트들을 한 화면에서 **관찰하고, 개입하고, 관리하는** 도구다.

관제탑의 본질은 **모든 것을 보여주는 것이 아니라, 지금 봐야 할 것을 골라내는 것**이다.

**제품 철학 — 모든 기능 결정을 시험하는 기준:**

> **Centralu는 통제하지 않는다. 통제를 가능하게 한다.** 에이전트의 자율성이나 사용자의 워크플로를 제한하지 않는다; 지금 무슨 일이 일어나고 있는지, 무엇이 내 판단을 기다리고 있는지를 정확히 보여준다. **막지 말고, 보이게 하라.** 그리고 이 시스템에서 가장 비싼 자원은 토큰이 아니라 **인간의 주의력**이다.

기능을 추가하거나 바꿀 때마다 이 기준에 비추어 묻는다: 이것은 강제인가 가시성인가, 인간의 주의력을 아끼는가 낭비하는가?

3가지 핵심 가치:

1. **놓치지 않는다** — 어느 세션이 내 응답을 기다리는지, 얼마나 급한지 즉시 안다
2. **즉시 개입한다** — 승인과 응답을 키보드로 빠르게 처리하고 다음 대기 항목으로 넘어간다
3. **가볍게 유지한다** — IDE 여러 개 대신, 유휴 상태에서 거의 아무것도 소모하지 않는 앱 하나

### 1.3 핵심 사용 루프 (이 제품이 지탱해야 하는 실제 행동)

```
come back to the desk
  → check the inbox: "2 waiting for approval · 3 waiting for a response"
  → handle the urgent ones (approvals) first, in sequence, from the keyboard
  → for the ones waiting on a response, read the result (mark read) then give the next instruction or end it
  → when it is all empty, leave the desk (the agents keep working)
```

모든 화면·단축키·알림 설계는 이 루프가 얼마나 빨리 도는가로 판단한다. 지표는 "얼마나 많이 보여주는가"가 아니라 **"루프 한 바퀴가 얼마나 빠른가"**다.

### 1.4 설계 원칙

1. **관찰과 조작의 분리** — 관찰(상태 파악)에는 공간이 거의 필요 없다(상태 점, 배지, 카운터). 조작(대화 읽기, 승인, 지시)에는 많은 공간이 필요하다. 따라서 관찰은 밀도 높은 사이드바와 인박스에, 조작은 전체 폭의 포커스 뷰에 둔다.
2. **긴급도의 구분** — "에이전트가 막혀 있다(승인 대기)"와 "턴이 끝났다"는 서로 다른 정보다. 절대 같은 배지로 합치지 않는다.
3. **키보드 우선** — 제어 루프의 모든 동작(세션 간 이동, 승인, 인박스 순회)은 마우스 없이 가능해야 한다. 마우스보다 느린 GUI는 터미널보다 못하다.
4. **상태와 읽음 상태는 별개** — "이 세션이 대기 중인가"와 "내가 결과를 봤는가"는 독립적인 축이다.

### 1.5 Non-goals

범위가 새는 것을 막기 위해, v1이 명시적으로 **하지 않는** 것:

- 코드 **편집** (뷰어만 제공; 편집은 IDE의 일)
- ~~터미널 에뮬레이터 (에이전트 대화는 raw 터미널이 아니라 구조화된 GUI)~~ — **2026-08-26 철회.**
  근거 패널에 Terminal 탭이 생겼다. 이 항목이 지키려던 것은 여전히 유효하다 — **에이전트 대화**는
  PTY 래핑이 아니라 구조화된 GUI다 — 하지만 그 옆의 프로젝트 터미널은 대화의 대체물이 아니라
  프로젝트를 관찰하는 일의 일부로 판명되었다. 아래 그리드 항목과 같은 이유로, 삭제하지 않고 기록으로 남긴다.
- 고급 git 조작 (rebase, cherry-pick 등 — 읽기 중심; commit/staging은 나중에)
- ~~원격/클라우드 실행 (로컬 머신의 로컬 프로젝트만)~~ — **2026-10-05 좁혀짐 (#82).**
  프로젝트는 사람이 SSH로 닿는 다른 머신에 있을 수 있다. 그 머신은 자기만의 독립된 호스트(자기 저장소, 자기 에이전트
  로그인, 자기 파일)를 `centralu serve`로 돌리고, 앱은 SSH 로컬 포워드를 통해 그것과 이야기한다. 켜야 쓰는 모드이고
  신뢰하는 한 사람을 위한 것이다: 호스트는 양쪽 모두 루프백에서 듣고, 공개 포트에 드러나는 것은 결코 없으며, 공유
  서버나 다중 사용자 서버는 없다. **클라우드 실행은 여전히 비목표다**: Centralu는 자기 인프라에서 에이전트를 돌리지
  않는다. 만드는 방법: [agent-host.ko.md](agent-host.ko.md) §4.7.
- Claude Code와 Codex 이외의 도구 (어댑터 구조만 확장 가능하게 설계)
- ~~**동시 분할 그리드 뷰**~~ — **2026-08-20 철회.** 이미 만들어졌고, **experimental** 표시를 달고 출시된다(§5.4).
  이 항목은 삭제하지 않고 유지한다: 그리드가 화면에 떠 있는데 이 문서만 "만들지 않는다"고
  말하던 시기가 있었고(issue #25), 그 불일치가 어디서 왔는지가 이 목록에서 사라져서는 안 된다.

## 2. 확정된 기술 방향

| 항목 | 결정 | 근거 |
|---|---|---|
| 앱 셸 | **Tauri 2.x** (Rust 코어 + 네이티브 webview) | "가벼움" 요구사항. Electron보다 메모리·에너지 사용이 크게 낮다 |
| 지원 에이전트 (v1) | **Claude Code, Codex CLI** | 사용자의 결정. 어댑터 인터페이스를 통해 나중에 확장 가능 |
| 연동 방식 | **SDK/프로토콜 기반** (PTY 래핑 아님) | 상태 감지(대기 중인가), 컨텍스트 사용량, 승인 요청을 구조화된 이벤트로 정확하게 수신 |
| 에이전트 어댑터 실행 | Node.js 사이드카 프로세스 | Claude Agent SDK(TypeScript)와 Codex 프로토콜 클라이언트를 Node에서 실행, Tauri가 감독 |
| 프런트엔드 | **React** (확정) | 유휴 에너지는 프레임워크가 아니라 렌더 정책(§7.1)이 결정한다. 생태계와 에이전트 주도 개발 친화성이 분명한 장점 |
| 로컬 저장소 | SQLite (앱 데이터 디렉터리) | 워크스페이스/세션/사용량 캐시 영속화, 재시작 시 복원 |

**연동 상세:**

- **Claude Code** → Claude Agent SDK (TypeScript). 스트리밍 메시지, 세션 resume, 도구 호출 이벤트, 권한 요청 콜백(`canUseTool`), 토큰/컨텍스트 정보를 구조화된 형태로 제공한다.
- **Codex CLI** → `codex app-server` JSON-RPC (stdio) 프로토콜. 대화 스트림, 승인 요청, 세션 관리를 프로그래밍 방식으로 처리한다. (버전 간 프로토콜 차이는 어댑터 내부에서 흡수한다.)
- 두 도구 모두 **공통 어댑터 인터페이스** 뒤에 숨긴다. → §6.2

**⚠ 승인 이벤트의 전제 조건 — M0에서 검증됨, 승인 UI 성립:**
사용자가 CLI를 전역 bypass(자동 승인)로 설정해 두면 승인 요청 이벤트가 **아예 발생하지 않는다**. Centralu의 승인 UI가 의미를 가지려면, 세션 생성 시의 권한 프리셋(FR-7)이 전역 설정을 세션 단위로 덮어쓸 수 있어야 했다. **M0에서 가능함을 확인했다** — Claude Agent SDK는 세션별 `permissionMode`/`canUseTool`을 받고, Codex는 스레드별 승인 정책을 받는다 — 따라서 Centralu에서 만든 세션은 전역 설정과 무관하게 선택한 프리셋대로 동작한다.

## 3. 용어

| 용어 | 정의 |
|---|---|
| 프로젝트 | 등록된 로컬 디렉터리 하나. git 저장소일 수도, 아닐 수도 있다 |
| 세션 | 에이전트 대화 인스턴스 하나. 프로젝트에 속하며 도구(Claude Code/Codex), 모델, 권한 설정을 가진다 |
| 어댑터 | 특정 에이전트 도구를 공통 인터페이스로 감싸는 모듈 |
| 오케스트레이터 세션 | `kind: 'orchestrator'`인 세션 — 앱의 모든 세션을 조회하고 지시할 수 있다. 정확히 하나이며 어느 프로젝트에도 속하지 않는다. 프로젝트의 지휘석은 워크트리 매니저이고, 그것은 역할이 아니라 워크트리 자식이 있다는 관계로 정해진다 (FR-11, #69) |
| 워크스페이스 | 등록된 프로젝트 목록 + 레이아웃 + 열린 세션들의 전체 상태 (복원의 단위) |
| 인박스 | 프로젝트 구조를 무시하고 "지금 내 개입을 기다리는 항목"만 보여주는 트리아지 뷰 |
| 읽음/안읽음 | 세션 상태와 독립: 마지막으로 본 이후 새 내용이 있는가 |
| 아카이브 | 세션 프로세스는 종료되고 목록에서 치워지지만, 대화 기록은 보존되는 상태 |

## 4. 기능 요구사항 상세

### 4.1 원래의 14개 요구사항 구체화 (FR-1 ~ FR-14)

`FR-n`은 원래 요구사항 번호에 대응한다.

#### FR-1. 멀티 프로젝트 관리 (사이드바 + 포커스 뷰)

- "한 창에 4개 이상의 프로젝트"는 **한 창에 4개 이상을 등록하고 빠르게 오갈 수 있는 것**으로 충족된다. 동시 분할 표시(그리드)도 존재하지만 **실험적 기능**이다; 이 요구사항을 충족하는 것은 그리드가 아니라 사이드바다(§5.4).
- 왼쪽 사이드바: 전체 프로젝트/세션 트리를 항상 밀도 높게 표시 — 프로젝트명, 브랜치, 변경 파일 수, 세션별 상태 점과 안읽음 표시. **관찰에는 이것으로 충분하다.**
- 오른쪽 포커스 뷰: 선택된 세션 하나가 전체 폭을 차지 — 대화, 파일, git, 뷰어 탭이 실제로 볼 수 있는 크기로 나온다.
- 프로젝트 등록: 디렉터리 선택 또는 드래그 앤 드롭. 최근 프로젝트 목록을 유지한다.
- 전환은 키보드로: ⌘1~9로 프로젝트 점프, j/k로 세션 간 이동 (→ FR-17).

#### FR-2. 워크트리 강제 안 함 + 동시 세션 안전장치

- **원본 디렉터리에서 직접 작업하는 것이 기본이다.** Git 워크트리는 만들지도, 요구하지도 않는다.
- git 저장소가 아닌 디렉터리도 프로젝트로 등록할 수 있다 (git 패널만 비활성화).
- **동시 세션은 데이터 손실 위험이다** (한 에이전트가 다른 에이전트의 변경을 덮어쓴다). 대응은 차단이 아니라 **가시성 + 복구**:
  - 세션 생성 대화상자 **안의 인라인 경고** (모달 없음, 추가 클릭 없음): "이 디렉터리에서 N개 세션 실행 중 — 같은 파일을 수정하면 변경이 유실될 수 있음". 읽고 계속 진행한다. (모달로 흐름을 끊는 것은 "막지 말고, 보이게 하라" 위반)
  - 실행 중에는 프로젝트 헤더에 "동시 세션 N개"를 상시 표시.
  - 두 세션이 **실제로 같은 파일을 수정한 것**이 감지되면(도구 호출 이벤트 기반) 경고 배지 + **복구 경로**: 도구 호출 이벤트에 남은 변경 전 내용으로 "이 파일의 이전 상태 보기"를 제공한다. Claude Code의 파일 체크포인트를 복구에 쓸 수 있는지는 M0에서 확인한다. 감지되는 시점엔 이미 늦었으므로, 경고보다 복구가 더 도움이 된다.
- (낮은 우선순위 옵션) 세션 생성 시 "워크트리에서 실행" 체크박스 — 원하는 사람에게는 격리를 제공. **2026-08-19 구현 완료.**
  - 위치는 **저장소 바깥** (`<data folder>/worktrees/<project>/<session>`). 저장소 안에 두면
    `.gitignore`에 한 줄을 추가해야 하고(우리가 사용자의 파일을 편집), 그러지 않으면 `git status`가 지저분해진다.
  - 브랜치는 `centralu/<first 8 chars of session id>`. 세션 이름은 생성 시점에 존재하지 않거나(자동 이름은 나중에 도착)
    공백과 유니코드가 섞여 있어 브랜치 이름으로 쓸 수 없다.
  - **git 저장소가 아니면 새로 만들지 않고 이유를 말한다.** 조용히 원본 디렉터리로 폴백하면
    사용자는 격리되었다고 믿고 두 세션을 같은 파일에 겨눈다 — 이 옵션을 켠 이유가 정확히 그것이다.
  - **resume과 앱 재시작은 같은 워크트리로 돌아온다** (경로를 DB에 보관).
  - 삭제할 때는 **묻는다**: 커밋되지 않은 변경 수와 경로를 보여주고, 체크박스를 요구한 뒤 삭제한다.
    에이전트가 몇 시간 동안 한 작업이 거기 놓여 있을 수 있다.

#### FR-3. GUI 에이전트 대화

- 채팅 스타일 UI: 사용자 메시지 / 에이전트 응답 (스트리밍 마크다운) / 도구 호출 카드 (기본 접힘, 펼치면 상세).
- 도구 호출 카드: 명령, 파일 경로, diff 요약을 구조화해 표시. raw 출력은 펼쳤을 때만. **접기 기본값은 도구 종류에 따라 다르다**: 읽기 중심 도구(Read/Grep/읽기 중심 Bash)는 접힘 — 연속으로 20개가 나와도 대화가 묻히지 않는다. 파일 변경(Edit/Write)은 diff 요약이 펼쳐진 상태가 기본. 설정에서 도구별로 조정 가능. (대화 뷰 가독성의 절반은 이 정책이다)
- 네이티브 서브에이전트를 띄운 카드(Claude Code의 `Agent`, Codex의 `spawnAgent`)에는 접힌 **서브에이전트의 걸음(Subagent's steps)** 칸이 있다. 펼치면 서브에이전트가 한 일 — 그 글, 추론, 도구 카드를 대화의 것과 같은 모양으로 — 을 보여 주고, 실행 중이면 이후의 걸음이 오는 대로 붙는다. 대화 자체에는 결코 나오지 않는다: 다른 행위자의 걸음이 부모의 것 사이에 끼면 누가 무엇을 했는지 구분할 수 없었다 (#98). 걸음을 남기기 전에(#222) 돈 에이전트는 기록된 것이 없다고 말한다.
- 세션 제어: 중단, 재시도, 새 세션, 세션 이름 변경 (자동 이름은 FR-18).
- 메시지 입력: 여러 줄, 첨부(FR-13), 슬래시 명령 패스스루 (도구가 지원하는 경우).

**승인 인터랙션 상세 (가장 자주 쓰는 인터랙션 — 사용성이 여기서 결정된다):**

- **키보드 우선**: 승인 요청에 포커스가 있으면 `y` 허용 / `n` 거부 / `a` 항상 허용. 마우스 불필요. 버튼도 함께 표시.
- **"항상 허용"의 범위와 표현력**: 누르는 순간 범위를 보여준다 — 기본은 **세션 범위**, 수정 키(⌥a)로 프로젝트 범위. 어느 범위로 저장됐는지를 승인 카드에 기록한다. 패턴 규칙(예: `npm test*`)을 허용하되, 등록할 때 **현재 세션 히스토리에서 그 패턴에 매칭되는 명령 목록을 미리보기**로 보여준다. 전체 규칙은 설정에서 조회·삭제할 수 있다. 표현력을 제한하는 대신 결과를 보이게 한다.
- **포커스되지 않은 세션의 승인 요청**: 상단 바의 인박스 숫자가 나른다 — 몇 개가 기다리는지 말하고, 목록이 이름을 대고, 누르면 그 세션에 내려앉아 카드에서 y/n/a로 답한다. 창 상단을 가로지르는 전역 배너가 있었다(그 자리에서 허용하되, 띠가 충분히 못 보여주는 요청 — 파일 편집·다중 파일·잘린 긴 명령 — 은 "needs review"로 돌려보내는 규칙과 함께). 2026-09-10에 걷어냈다: 뜨고 사라질 때마다 **창 전체가 밀려서**, 읽던 줄과 누르려던 버튼이 같이 움직였다. 방해하는 일을 밀어내는 알림은 아껴 준 점프보다 비싸다.
- **승인 큐**: 승인이 여러 개 쌓이면 인박스(FR-15)에서 순서대로 처리한다. 하나를 처리해도 그 세션에 머물고, `⌘⇧A`로 다음 대기 세션으로 간다.
- 승인 요청 카드는 판단에 필요한 것을 요약한다: 전체 명령, 또는 파일 경로 + diff 미리보기.

#### FR-4. Git 상태 GUI

오른쪽 **근거 패널**에 위치하며, 탭은 **Git / History / Files / Terminal**이다 (실제 구현 기준 — 원래의 "3탭 git 패널"이 사용 중에 재편됨):

- **Git (changes)**: staged/unstaged/untracked 파일 목록; 파일을 클릭하면 diff 뷰. 에이전트가 파일을 바꾸면 실시간 갱신.
- **History**: git 패널 안의 스트립이 아니라 별도 탭 — 내장 스트립은 패널이 분할될 때 겹침을 일으켰고 제대로 된 그래프에 쓸 높이를 낼 수 없었다 (도그푸딩, 2026-08-26). 브랜치 레인이 있는 커밋 로그; 커밋을 클릭하면 변경 파일과 diff를 표시.
- **Branches**: 패널 헤더에서 연다 — 로컬 브랜치 목록, 현재 브랜치 표시, dirty 상태여도 체크아웃을 막지 않는다; **영향받을 파일을 먼저 보여준 뒤 진행할지 묻는다** (M2 결정: '막지 말고, 보이게 하라').
- **IDE로 점프**: diff나 파일 목록에서 해당 파일의 해당 줄을 기본 편집기로 연다. 왕복 비용을 줄이는 핵심 디테일.
- 구현: agent-host의 `git` CLI 래퍼 (M2에서 확정 — Rust git2로의 이전은 측정으로 병목이 확인될 때까지 보류).
- v1은 **읽기 중심**이다. commit/staging/push는 **v1.5로 확정** — 읽기 패널(M2)이 끝난 직후 같은 패널에 추가한다. rebase, cherry-pick 같은 고급 조작은 계속 non-goal.

#### FR-5. 프로젝트 파일 트리

- 탐색기 스타일 트리. **lazy-load** (연 디렉터리만 읽는다 — 큰 저장소에서도 가볍다).
- `.gitignore` 기반 필터 토글 (기본: ignored 숨김).
- Git 상태 오버레이 (M/A/U를 **글리프**로 표시 — 무채색 팔레트 결정에 따라 색을 쓰지 않는다).
- 에이전트가 최근 수정한 파일 강조 ("에이전트가 방금 만진 파일" 추적).
- **외부 변경을 감지한다** (issue #34, 2026-08-25 출시): 펼쳐진 디렉터리에만 비재귀 감시를 걸고
  300ms 간격으로 플러시 — 저장소 전체를 폴링하지 않고도 에이전트와 편집기가 디스크에 한 일을 트리가 따라간다.

#### FR-6. 코드 뷰어 (읽기 전용)

- 파일 클릭 → 구문 강조된 읽기 전용 뷰. 파일 내 검색, 줄 번호, 줄 링크 복사.
- diff 모드와 일반 모드 토글.
- 큰 파일은 가상 스크롤; 바이너리/이미지는 미리보기 또는 안내.
- 편집 없음 (non-goal). "IDE에서 열기" 버튼 (FR-4의 줄 단위 점프와 같은 메커니즘).

#### FR-7. 프로젝트별·세션별 도구 선택

- 세션 생성 대화상자에서 선택: **도구** (Claude Code / Codex) → **모델** → **권한 프리셋** (safe/normal/auto-approve) → 시작 프롬프트.
- **권한 프리셋은 CLI의 전역 설정을 세션 단위로 덮어쓴다** (M0에서 검증 — §2 참조). 사용자의 전역 bypass 설정과 무관하게, Centralu에서 만든 세션은 선택한 프리셋대로 동작한다.
- 모델·effort 메뉴는 도구가 노출하는 도구별 노브도 함께 다룬다: Claude effort 단계, **Codex `model_verbosity`** (issue #54, 2026-08-25 출시 — 실제 실행에서 출력 길이가 달라지는지 측정한 뒤 노출).
- 프로젝트별 기본값 저장 ("이 프로젝트는 기본이 Codex + gpt-5.x").
- 한 프로젝트 안에서 서로 다른 도구의 세션을 동시에 돌릴 수 있다 (예: Claude Code로 구현 + Codex로 리뷰).

#### FR-8. 가벼움 (핵심 비기능 요구사항 → 수치 목표는 §7)

- 구조는 Tauri + 가벼운 프런트엔드 + Node 사이드카 1개. 에이전트 CLI 프로세스는 세션이 있는 동안만 존재한다.
- 포커스 뷰 구조 자체가 성능에도 유리하다: 화면에 렌더해야 하는 세션이 하나뿐이므로 상시 렌더 부하가 그리드보다 낮다. 포커스되지 않은 세션은 상태와 안읽음 갱신을 위한 이벤트만 받는다.
- 파일 워처 디바운스, 폴링 대신 이벤트 구동.
- 목표 요약: 유휴 시 CPU ~0%, 앱 자체 메모리 수백 MB 미만. §7.1 참조.

#### FR-9. 에이전트 사용량 + 한도 상태

**출시된 것은 비용 대시보드가 아니라 한도 윈도우 뷰다.** 사용량 패널은 도구별 **구독 한도 윈도우**를 보여준다 — Claude의 5시간 + 주간 윈도우, Codex의 주간 윈도우 — 배열로 렌더하므로 도구에 새 윈도우가 생겨도 UI 변경이 필요 없다. 추가 결제 크레딧은 범위 밖이다.

- **한도 도달은 일급 상태다** (실사용에서 자주 만난다): 세션이 rate limit에 걸리면 세션 상태를 `limited`로 표시하고, 도구가 제공하는 한에서 **예상 리셋 시각**을 세션 헤더와 인박스에 보여준다.
- 원래의 주간 **비용** 대시보드(일별 막대, 프로젝트/모델별 분해, 추정 비용)는 미결로 남는다. 만들 경우 조사 결과는 여전히 유효하다: SDK로는 주간 집계가 불가능하므로(턴별 사용량만 제공, 구독 계정에는 plan-limit API 없음) **로그 파싱이 유일한 경로**다 — `~/.claude/projects/**` JSONL과 `~/.codex/sessions/**` token_count 이벤트를 SQLite에 증분 파싱으로 캐시. 그에 드는 시간이 가치가 있는지는 확정된 약속이 아니라 도그푸딩 시기의 판단이다.

#### FR-10. 재시작 시 복원

- 종료 시 워크스페이스 스냅숏 저장: 프로젝트 목록, 레이아웃, 프로젝트별로 열린 세션 ID·도구·이름·읽음 위치.
- 재시작 시:
  - UI와 레이아웃은 즉시 복원
  - 대화 기록은 로컬 로그/SQLite에서 즉시 로드 (먼저 읽기 전용으로 표시)
  - 세션 프로세스는 **resume이 가능한 곳에서는 resume** (Claude Agent SDK resume, `codex resume`); 불가능하면 "기록만 보기 + 새 세션 시작"을 제안
- 프로세스가 죽을 때 진행 중이던 에이전트 턴은 중단된다는 것을 명시한다 (복원은 "턴을 잇는 것"이 아니라 "대화를 잇는 것"이다).
  데스크톱 앱에서는 이제 프로세스가 호스트와 함께 죽지 않는다(#280 2단계): 키퍼가 에이전트·터미널·프로젝트 명령을
  쥐므로, 호스트가 죽거나 다시 뜨거나 빌드가 바뀌어도 도는 턴은 계속 가고 다음 호스트가 거기에 다시 붙는다 — 기다리던
  승인이 돌아오고, 터미널은 화면을 지키고, 개발 서버는 계속 돈다. 호스트가 죽을 때 돌던 Centralu 자신의 도구
  (오케스트레이터, 앱 도구) 호출만 잃는다. 그 턴은 그 이름을 밝힌 오류와 함께 멈추고, 사람은 메시지를 다시 보낼 수 있다.
- 크래시 안전성: 스냅숏은 종료 시가 아니라 상태가 바뀔 때마다 저장한다.
- **백그라운드 모드** (#280, 결정 1 — 설정이고 기본은 꺼짐). 꺼짐: 앱을 끄면 호스트와 에이전트가 멈춘다, 예전처럼.
  켜짐: 앱을 닫거나 꺼도 호스트와 도는 턴이 계속 가고, 앱을 다시 열면 복원할 것 없이 그대로 다시 붙는다 — 기다리던
  승인은 여전히 기다리고 있다. 종료 대화상자는 이 설정을 따른다: 꺼짐이면 버튼은 **Quit completely** 하나이고, 켜짐이면
  **Quit**은 창만 닫고 모두 계속 돌게 두며 **Quit completely**는 그래도 키퍼·호스트·모든 에이전트·터미널·도는 명령을 멈춘다. 지켜보는 이 없는
  호스트는 창도 없고 도는 것도 없이 30분이 지나면 스스로 멈춘다. 다른 빌드로 다시 연 앱은 그렇다고 말하고 자기
  빌드로 호스트를 바꾸자고 권한다. 바꾸기는 블루그린 교체다(#280 3단계): 새 빌드가 도는 호스트 옆에서 뜨고, 도는
  호스트는 자기가 직접 처리하는 호출을 마칠 시간을 최대 10초 받고, 창은 잠깐 뒤 다시 붙는다. 막대는 단계마다 보여
  주고, 실패하면 이유와 지금 어느 빌드가 일하는지 보여 준다. 잃을 것이 있을 때만(일하거나 기다리는 세션, 터미널,
  명령) 먼저 묻고, 무엇을 잃는지 말한다: 도는 턴·터미널·명령은 바꾸기를 넘어 이어지고(2단계), 10초가 지나도록 도는
  오케스트레이터나 앱 도구 호출만 멈추며 에이전트에게 다시 시도하라고 알린다. 같은 바꾸기가 먼저 키퍼(호스트와
  에이전트를 쥐고 있는 백그라운드 프로세스)를 새 빌드로 옮긴다(#280 4단계): 키퍼는 가진 것을 모두 새 빌드의 키퍼에게
  넘기고 끝나며, 이것은 아무것도 멈추지 않고 창이 다시 붙을 일도 만들지 않는다. 열려 있는 앱 뷰는 바꾸기 내내 계속
  동작한다. 호스트는 같은데 키퍼만 뒤처져 있으면 같은 막대가 뜨고, 이때 바꾸기는 아무것도 묻지 않는다. 키퍼가 옮겨
  가지 못해도 호스트 바꾸기는 그대로 진행된다. 호스트가 창의 빌드에 오르면 막대는 바꾸기를 다시 권하지 않는다(옛 키퍼는
  매번 같은 식으로 실패한다, #387): 이 창이 자기 빌드로 돌고 키퍼는 다음에 다시 시작할 때 옮겨 간다고 말하고,
  **Restart completely**를 권한다. 이것은 에이전트·터미널·도는 명령이 멈춘다고 말한 뒤 키퍼를 이 빌드로 다시 띄우고 창을
  다시 붙인다. "Could not switch builds"는 호스트가 그 빌드에 닿지 못한 바꾸기에만 남는다. 데스크톱
  전용이고 키퍼가 필요하다 ([architecture.ko.md](architecture.ko.md) §4.1–4.4).
- **업데이트 적용** (#352). 업데이트가 설치되면 업데이트 줄이 **Apply now**를 내민다: 앱이 새 버전으로 스스로를 다시
  띄우고, 키퍼는 백그라운드 모드가 무엇이든 다시 띄우는 동안 호스트와 모든 에이전트를 쥐고 있으며, 새 창은 잃을 것이
  없으면 키퍼와 호스트를 자기 빌드로 저절로 바꾼다(잃을 것이 있으면 바로 묻는다). **Apply updates automatically when
  idle**(설정 → Updates, 기본 꺼짐)은 새 버전을 찾자마자 설치하고, 일하거나 승인·질문을 기다리는 세션이 없고, 돌고
  있는 터미널이나 명령이 없고, 아무도 타이핑하지 않을 때 적용한다. 저절로 바꾸는 것은 앞으로만 간다: 도는 빌드보다
  옛 빌드의 창(나중에 연 백업 앱)은 저절로 바꾸지 않고, 그 바는 옛 빌드라고 말하며 손으로 되돌아가기를 내민다.
  데스크톱 전용이고 키퍼가 필요하다. 그 밖의 곳과
  업데이트가 바꾸지 않은 빌드(`pnpm app:open`)에서는 줄이 예전처럼 다시 시작하라고 말한다
  ([architecture.ko.md](architecture.ko.md) §4.5).
- **에이전트 CLI 업데이트** (#297). 세션마다 자기 Claude Code나 Codex 프로세스를 돌리고, 그 프로세스는 띄울 때의 CLI
  버전을 그대로 쥔다. 키퍼가 있으면 프로세스는 앱을 몇 번 다시 열어도 살아남는다. 설치된 CLI가 더 새것이면 세션
  헤더가 조용히 그렇다고 말하고("Claude Code 2.1.290 installed — this session runs 2.1.282"), 옆에 앱 전체에 대한 동작
  하나, **Update idle sessions**를 둔다. 이것은 idle 세션을 모두 설치된 버전으로 다시 띄우고 바쁜 세션은 그대로 둔다.
  **Move idle sessions to a newly installed agent CLI**(설정 → Updates, **기본 켜짐**)는 세션이 완전히 idle해지고 — 턴이
  없고, 기다리는 승인이나 질문이 없고, 돌고 있는 백그라운드 작업이 없고 — 1분 동안 조용하면 같은 일을 스스로 한다.
  대화는 resume으로 이어지고, 대화 안의 한 줄이 세션이 옮겨졌다고 말한다. 설치된 버전은 10분마다, 그리고 창이 포커스를
  얻을 때 읽는다([agent-host.ko.md](agent-host.ko.md) §4.6).

#### FR-11. 오케스트레이터 세션 (2026-08-25 구현, issues #13 · #30 — 이 절은 실제로 만들어진 것을 기술한다)

- **Kind는 null 체크가 아니라 명시적 마커다**: 세션은 `kind: 'orchestrator'`이거나 일반 세션이다.
  오케스트레이터는 **정확히 하나**이고 어느 프로젝트에도 속하지 않는다 — 앱의 모든 세션에 닿는다
  (모든 도구 호출을 `inScope` 술어가 지킨다).
- 오케스트레이터는 사이드바 버튼의 **왕관 아이콘**으로 표시한다 (무채색 규칙 유지: kind는 형태로, 긴급도는 밝기로).
- **폐기 (2026-09-01): 프로젝트 오케스트레이터, 그리고 승격·강등(`sessions.setKind`).** #13은 대화 하나가 모든
  프로젝트의 컨텍스트를 담을 수 없다는 이유로 3단 계층(중앙 > 프로젝트 > 세션)을 만들었다. 그 뒤 워크트리
  매니저(#69)가 다른 방향에서 같은 자리를 가져갔다 — 프로젝트의 세션들을 지휘하는 세션. 그런 자리가 둘인 것은
  개념이 하나 많았다: 만든 사람조차 도그푸딩에서 둘을 헷갈렸고, 승격 줄은 한 번도 쓰이지 않았다. 남는 것은 값을
  하는 한 쌍이다 — 전부를 가로지르는 오케스트레이터 하나, 그리고 프로젝트마다 **관계에서 나오는**(워크트리 자식이
  있으면 매니저다) 매니저. 스키마 v26은 프로젝트를 가진 채 표식이 남은 세션에서 그 표식을 지운다 — 이 단계가
  없으면 프로젝트 단계를 걷어내는 것이 그 세션들을 조용히 중앙 범위로 **넓히는** 일이 된다.
- 호스트는 오케스트레이터 세션에 **선별된 도구**(세션 조회, 대화 읽기, 지시 전송,
  `create_session`, `update_session_settings`)와 **컴파일 시점에 내장된 앱 가이드**(overview/sessions/orchestrator/approvals/
  settings/updates)를 노출한다 — 런타임에 `docs/`를 읽지 않고 컴파일 시점에 내장하는데, 런타임 문서 읽기는
  한 단계 옆의 AGENTS.md류 인젝션 표면이기 때문이다.
- **평범한 세션도 가벼운 읽기 전용 묶음을 받는다**(#320, 2026-10-05 소유자 결정, 기본 켜짐): 자기 프로젝트의
  다른 세션 목록과 대화(`read_session`, id 없이 부르면 목록), 그 프로젝트의 지난 대화 검색(`recall`), 앱 가이드
  (`app_guide`). 다른 프로젝트의 세션은 볼 수 없고, 보내기·만들기·제안은 오케스트레이터에 남으며, 역할을 바꾸는
  지침도 함께 가지 않는다. 모든 세션의 모든 턴에 실리므로 크기를 재서 줄였다: 후보 넷을 오케스트레이터 문구 그대로
  붙이면 요청마다 입력 +672토큰, 출시본은 +192토큰(측정과 근거는 agent-host.md §1.1). 설정 → 오케스트레이터의
  "Let sessions look at their own project"로 끈다.
- **평범한 세션이 다른 프로젝트에 일을 맡길 수 있다**(#371 B, 2026-10-05 소유자 결정): `ask_project({ project, task })`가
  그 프로젝트에 보이는 세션을 새로 띄우거나(또는 다시 쓰고) 그 프로젝트의 폴더·지침·도구·권한으로 일을 시킨 뒤, 턴이
  끝나기를 기다려 답을 돌려준다 — 서브에이전트의 결과가 돌아오는 것처럼. 동의는 프로젝트 쌍마다다: X가 Y에 처음 맡길 때
  호출한 세션에 카드가 선다(이번만 허용 / 이 쌍은 항상 / 거절). "항상"은 기억되고 설정 → Permissions에서 철회한다. 맡겨진
  세션은 그 프로젝트의 권한 안에서 코드를 바꿀 수 있고, "asked by" 표시와 되돌아가는 링크가 붙는다. 호출한 쪽 대화에는
  그 세션으로 가는 작은 카드가 남는다. 답이 이름 붙인 파일 중 대상 프로젝트 안의 것만 호출한 세션이 읽을 수 있게 되고,
  그보다 넓게는 열리지 않는다. 호출한 쪽의 Stop은 맡겨진 턴도 멈춘다. 맡겨진 세션은 세 번째 프로젝트에 다시 맡길 수
  없다. 자세한 것은 agent-host.md §1.2.
- **다른 프로젝트의 앱, 필요할 때만**(#371 A, 2026-10-05 소유자 결정): 평범한 프로젝트 세션은 다른 프로젝트가
  나눠 둔 앱이나 사람의 사용자 폴더 앱을 찾아, 그 도구가 필요한 동안 붙이고 뒤에 뗀다(`find_apps`, `attach_app`,
  `detach_app`). 그래서 그 도구는 그 밖에는 문맥을 차지하지 않는다. 나누기는 프로젝트 앱마다 사람이 고르고(설정 →
  앱, 또는 앱 머리. 기본은 꺼짐), 다른 프로젝트의 앱을 쓰는 것은 프로젝트 쌍마다 한 번 묻는다(이번만, 늘, 거절.
  "늘"은 설정에서 거둔다). Claude는 같은 턴에 도구를 받고, Codex 세션은 다음 턴부터 받는다. 자세한 것은 apps.md §9.4.
- **권한 프리셋은 오케스트레이터의 settings 도구 스키마에서 의도적으로 표현할 수 없다** — 오케스트레이터가
  다른 세션의 승인 뒷문을 조용히 넓힐 수 있어서는 안 된다.
- 설정 변경은 `settings_changed` 이벤트 + 토스트로 드러나서,
  오케스트레이터가 무엇을 바꾸는 순간 인간이 그것을 본다.
- 오케스트레이터가 보낸 지시는 대상 세션의 대화에 표시된다 (2026-08-26 구현): 말풍선 위의 출처 라벨과
  점선 테두리 — 팔레트 규칙에 따라 색이 아니라 형태로. 오케스트레이터 자신의 채팅에 오는 워커 완료 보고에도
  같은 마커가 붙는다. 스티키 배너에는 출처 이름이 접두로 붙는다.
- **폐기 (2026-08-27): 세션별 "오케스트레이터 지시 거부" 토글.** v0.4에서 안전장치 한 문장의 나머지 반쪽으로 적혔을
  뿐, 요청된 적도 아쉬웠던 적도 없다. 오케스트레이터를 만들고 그 범위를 정하는 사람과 이 스위치를 내릴 사람이 같은
  사람이라, 자기 관제탑의 지시를 거부하는 상황이 뒤에 없다. 어댑터에 적용한 규칙과 같다 — 설계 문장이 한때 다른
  것과 짝지어 놓았다는 이유가 아니라, 실제 사례가 관찰될 때 만든다. (여러 사람이 함께 쓰는 구성이라면 달라지지만,
  이 앱은 그런 앱이 아니다.)

#### FR-12. 대기 상태 표시 — 두 단계의 긴급도, 분리 (제어의 심장)

세션 상태 머신:

```
idle → working → (waiting_approval | waiting_input | limited | error) → working → …
```

| 상태 | 의미 | 긴급도 | 표시 |
|---|---|---|---|
| `working` | 에이전트 턴이 진행 중 | — | ⚙ 회전 |
| `waiting_approval` | **에이전트가 막혀 있다.** 내가 뭔가 누르지 않으면 아무 일도 일어나지 않는다 | **긴급** | 🔴 (+ 경과 시간) |
| `waiting_input` | 턴이 끝났다. 다음 지시가 없어도 해로울 것이 없다 | 긴급 아님 | 🔵 |
| `limited` | 사용량 한도에 막혀 리셋 시각을 기다리는 중 | 정보성 | ⏳ (+ 예상 리셋) |
| `error` | 프로세스 오류 등 | 긴급 | ⛔ |

- **`waiting_approval`과 `waiting_input`은 절대 같은 배지로 합치지 않는다.** 색, 아이콘, 정렬, 알림 정책 모두 분리한다.
- 전역 카운터도 분리한다: **"승인 2 · 응답 대기 3"** (합산된 "대기 5"는 금지).
- 표시 계층: ① 세션 행 상태 점 (사이드바) → ② 프로젝트 집계 → ③ 분리된 전역 카운터 (창 상단 고정) → ④ 독 아이콘 배지 / OS 알림 — 기본값: 승인과 오류는 즉시 알림, 응답 대기는 배지만. 대신 **모든 세션이 작업을 마쳤을 때(전부 대기/유휴) "all done" 알림 하나** — 자리를 비운 사람에게 필요한 신호는 개별 세션의 종료가 아니라 이것이다. (설정 가능)
- **"다음 대기 항목으로 가기"** 단축키: 승인 → 오류 → 응답 대기의 우선순위로 순회한다 (→ FR-17).
- 대기 경과 시간을 표시한다 ("3분째 대기 중").

#### FR-13. 파일 첨부 / 이미지 붙여넣기

- 클립보드에서 입력창으로 **이미지 붙여넣기** (스크린샷 워크플로), 파일 **드래그 앤 드롭**, 파일 선택 버튼.
- 프로젝트 안의 파일은 경로 참조(@path 멘션)로 전달; 외부 파일과 이미지는 도구가 지원하는 형태로 어댑터를 통해 전달한다.
- 전송 전 첨부 미리보기 (썸네일). 도구별 지원 차이는 어댑터가 보고하고 비활성화된 UI로 반영한다.

#### FR-14. 컨텍스트 사용량 표시

- 세션 헤더의 컨텍스트 게이지: 사용 토큰 / 컨텍스트 윈도우 (%). 스트리밍 usage 이벤트로 갱신.
- 임계값 경고 (예: 80%에서 게이지 색 변경 + "곧 압축/성능 저하가 올 수 있음" 툴팁).
- 압축(요약)이 일어나면 대화 뷰에 마커 표시.
- 도구가 세션 안에서 새 대화를 시작하면(Claude Code의 `/clear`, #304) 마커를 표시하고, 도구가 새 대화의 크기를 알려
  줄 때까지 게이지를 비운다.
- 도구가 정확한 수치를 주지 않으면 추정치임을 명시한다 (≈와 함께 표시).
- **도구가 자기 사용자에게 하는 말이 대화에 닿는다** (#304): 훅이 프롬프트를 막은 이유, 설정·폐기 예정 경고, 시작하지
  못한 MCP 서버, 도구가 스스로 바꾼 모델과 그 이유. 대화의 마커 모양으로 조용한 한 줄씩, 도구 자신의 말 그대로 보이며
  아무것도 끼어들지 않는다(토스트도, 대화상자도 없다). 시작할 때마다 반복되는 경고는 세션당 한 번만 보인다. 도구가 바꾼
  모델은 표시된 모델에 반영된다. 도구가 실패한 API 호출을 재시도하는 동안 세션은 "재시도 중"으로 보인다.
- **그 줄마다 누가 말하는지, 어떤 종류인지, 누가 움직여야 하는지 말한다** (#342): "Codex · config warning · for you".
  Centralu가 알아보는 알림이면 쉬운 한 줄 설명(Codex가 무시한 설정을 한 줄에 하나씩, 그리고 조용하게 하는 법)이 먼저 오고
  도구 자신의 말은 눌러서 펼친다. 사람이 아니라 Centralu에게 하는 알림(떠나는 중인 API)도 대화에 남되 "for Centralu"로
  표시되어, 사람이 할 일이 없음을 알 수 있다.

### 4.2 사용성 리뷰에서 추가된 요구사항 (FR-15 ~ FR-19)

#### FR-15. 인박스 (트리아지 뷰) — 핵심 사용 루프의 입구

- 프로젝트 구조를 **무시하고**, 지금 내 개입을 기다리는 항목만 모으는 단일 목록.
- 정렬: 긴급도 우선 (승인 → 오류 → 응답 대기); 같은 긴급도 안에서는 대기 시작 시각 오름차순.
- 각 항목: 세션 이름, 프로젝트, 대기 종류, 경과 시간, 마지막 내용 한 줄 미리보기.
- 항목 선택 → 해당 세션의 포커스 뷰로 점프. 처리(승인/응답)가 끝나도 **그 세션에 머문다** — 방금 보낸 것을 에이전트가 어떻게 받는지 보이게. 다음 대기 항목으로는 `⌘⇧A`(FR-17)로 간다. *(2026-10-02 변경: 예전에는 자동으로 다음 항목으로 간다고 적혀 있었다. FR-20으로 보관의 `d` 키와 `afterHandled` 경로가 없어진 뒤로 그렇게 하는 것은 없었고, 소유자는 그대로 두기로 했다 — 답을 보내는 순간 화면이 바뀌는 것은 예측하기 어렵다.)*
- ~~**`d` (dismiss)**~~ — **2026-09-02 폐기.** 세션을 아카이브했고, 그게 아카이브의 유일한 입구였는데 출구가 없었다: "이건 답 안 하겠다"는 뜻이 세션을 앱에서 지웠다. 인박스는 *상태*의 뷰라, 정직하게 비우는 방법은 상태를 바꾸는 것 — 즉 답하는 것뿐이다. FR-20 참고.
- 인박스 열기/닫기 단축키 하나 (기본 `⌘I`). 앱 시작 시 대기 항목이 있으면 인박스를 먼저 보여준다.
- FR-1의 사이드바가 "지도"라면 인박스는 "할 일 큐"다. 책상에 돌아왔을 때의 진입점은 인박스다.
- §1.3 루프의 입구이므로 **M1 범위다**. 목록 하나라서 구현 부담도 작다 — 사이드바보다 먼저 필요할 수도 있다.

#### FR-16. 읽음/안읽음

- 세션 상태(working/waiting)와 **독립적으로**, "마지막으로 본 이후 새 내용이 있는가"를 추적한다.
- 세션별로 `last_read_seq`를 저장. 읽음 처리 조건: 포커스 뷰에서 스크롤이 최신에 도달했을 때, **또는 세션에 포커스된 채 3초가 지났을 때** — 짧은 응답은 스크롤이 생기지 않아, 보조 조건이 없으면 영원히 안읽음으로 남는다.
- 사이드바 세션 행에 안읽음 표시 (굵기/점). "에이전트가 5분간 혼자 일하고 끝냈다"는 `waiting_input` + **안읽음** — "결과를 확인하지 않은 세션"을 놓치지 않으려면 두 축이 모두 보여야 한다.
- 인박스의 응답 대기 항목 중에서는 안읽은 것을 앞에 놓는다.

#### FR-17. 키보드 전용 조작

전체 제어 루프가 마우스 없이 돌아야 한다. v1 기본 단축키:

| 동작 | 키 |
|---|---|
| 다음 대기 항목으로 가기 (우선순위 순회) | `⌘⇧A` (잠정) |
| 인박스 열기/닫기 | `⌘I` |
| 프로젝트 점프 | `⌘1`~`⌘9` |
| 프로젝트 내 세션 간 이동 | `j` / `k` (입력창에 포커스가 없을 때) |
| 승인 허용 / 거부 / 항상 허용 | `y` / `n` / `a` (⌥a: 프로젝트 범위) |
| 커맨드 팔레트 (프로젝트·세션·액션 검색) | `⌘K` |

#### FR-18. 자동 세션 이름

- "Session 1, Session 2"는 프로젝트가 4개를 넘으면 식별이 불가능해진다. 첫 프롬프트 기반의 **자동 제목**을 기본으로 한다.
- Claude Code는 이미 자체적으로 세션 제목을 생성하므로 그대로 받는다. Codex처럼 지원하지 않는 도구는 첫 사용자 메시지 앞부분을 잘라 초기 이름으로 쓴다.
- 수동으로 이름을 바꾸면 자동 갱신을 멈춘다.

#### FR-19. 첫 실행 경험 (온보딩)

**오케스트레이터 먼저** (#63, 2026-08-27 — 폴더 먼저 흐름을 대체한다). 목표는 효율이
아니라 습관 형성이다: 첫 실행에서 오케스트레이터에게 물어보는 경험을 겪지 않은 사람은
나중에도 누르지 않고, 앱에 대한 질문은 제작자가 아니라 오케스트레이터에게 가야 한다.
정확히 두 정거장, 위저드 없음:

1. **소개 화면** (정말 처음인 설치본 — 프로젝트도 세션도 0개 — 에 딱 한 번): 앱이
   무엇인지 한 줄, 오케스트레이터의 역할 설명 한두 문장(눈에 띄게), 큰 에이전트 카드
   두 장 (Claude Code / Codex). **카드가 곧 도구 감지 표시다**: 준비된 도구는 활성
   카드, 안 된 도구는 어둡게 비활성 + "Not connected" + 상태별 처방(설치 명령 vs
   로그인 명령 — 앱이 로그인 플로를 대신하지 않는다) + 재감지 버튼. 준비된 카드를
   클릭하면 오케스트레이터가 돌 도구를 저장하고("나중에 바꿀 수 있다"를 화면에 적는다)
   통과한다. 프로세스는 **뜨지 않는다**.
2. **보통의 오케스트레이터 세션 화면**, 빈 상태. 대화 메시지가 0개인 동안 행동 지향
   추천 질문 3개(프로젝트 만들기 / 오케스트레이터의 능력 / 다중 세션 관제)를 큰
   카드로 보여주고, 탈출구("그냥 폴더 고르기" → 네이티브 피커 → 세션 생성 창)를 항상
   함께 둔다. 질문 클릭은 **즉시 전송**이고, 그 클릭(또는 입력창의 첫 마디)이 비로소
   오케스트레이터 프로세스를 띄운다 (지연 기동). 추천 질문은 온보딩 상태 머신이 아니라
   메시지 수의 함수이며, 입력창·사이드바·그리드는 내내 전부 쓸 수 있다.

프로젝트 생성 질문의 답은 행동으로 끝난다: 오케스트레이터의 `propose_project` 도구는
제안 카드를 띄울 뿐이고, 카드의 유일한 힘은 **사람의 네이티브 피커를 여는 것**이다 —
도구 스스로 폴더를 등록하는 길은 없다 (제안-후-사람-확인; §FR-11 보안 노트 참조).

#### FR-20. 세션 아카이브 — **폐기 (2026-09-02)**

아카이브를 걷어냈다: 플래그도, RPC도, 오케스트레이터의 `archive_session` 도구도, `d` 키도.
스키마 v28이 컬럼을 지운다 — 이제 숨겨진 세션은 없다.

실제로 만들어진 것은 아래 설계의 **절반**이었다: 들어가는 문(인박스의 `d`)만 있고
나오는 문(프로젝트별 Archive 목록·팔레트·제자리 재개)이 하나도 없었다. 그래서
"Dismiss"라고 적힌 키가 세션을 사이드바·팔레트·인박스에서 통째로 치웠고, 돌아올 길이
없어 삭제와 구별되지 않았다. 게다가 에이전트도 `archive_session`으로 같은 일을 할 수 있었다.

명분은 "인박스 비우기"였는데, 그게 바로 범주 오류다. 인박스는 세션 *상태*의 뷰이고
"답 안 하겠다"는 에이전트가 가질 수 있는 상태가 아니다 — 그래서 그 키에게는 세션을
집합에서 빼는 것 말고 쥘 레버가 없었다. 이제 인박스를 비우는 방법은 답하는 것이고,
그건 인박스가 존재하는 이유 그 자체다.

기록 보존도 아카이브가 필요한 이유가 아니었다: 세션 삭제 창이 이미 "대화는 Claude/Codex에
남아 있고 **+ → Past conversations**로 다시 꺼낼 수 있다"고 말하고, host 테스트가 그 약속을
지킨다. 사이드바가 정말 붐비게 되면(워크트리 세션이 유력하다) 그 답은 붐비는 자리에서
찾는다(병합된 자식 접기) — 전역 숨김 상태가 아니라.

**2026-09-30부터 숨기되 남기는 세션이 다시 있다: 휴지통이다 (FR-22, #204).** 여기서 폐기한
모양을, 아카이브에 없던 것을 갖춰 다시 만들었다. 나오는 길이 들어가는 길과 같은 변경에 들어갔다
(설정에서 목록·읽기·되살리기·영구 삭제). 삭제는 키 하나가 아니라 창이고, 그 창이 세션이 어디로
가고 어떻게 돌아오는지 말한다. 에이전트와 앱은 휴지통에서 세션을 꺼내지도 영구 삭제하지도 못한다.
휴지통은 사람 말고는 아무것도 비우지 않는다.

---

이하 폐기 전 설계 (기록용):

- 아카이브 = 에이전트 프로세스 종료 + 사이드바와 인박스에서 제거. **대화 기록은 SQLite에 보존된다.**
- 아카이브된 세션은 프로젝트별 "Archive" 목록과 커맨드 팔레트에서 볼 수 있다. resume이 가능하면 그 자리에서 resume한다 (활성으로 복귀).
- FR-10(재시작 시 복원)은 **활성 세션만** 복원한다 — 아카이브는 복원 범위 밖이다.
- 진입점: 인박스에서 `d`, 세션 헤더 버튼, 커맨드 팔레트.

#### FR-21. 대화 내용 검색

- M1: 커맨드 팔레트(⌘K)에서 세션 이름과 프로젝트 검색.
- M2: 대화 **내용**의 전문 검색 (SQLite FTS) — 며칠에 걸쳐 세션 4개를 굴리면 "그 얘기 어디서 했더라"는 반드시 나온다.
- **내용은 오간 말이다**: 사람의 말, 에이전트의 답과 추론. 도구 호출과 그 출력은 검색하지 않는다 ([#221](https://github.com/ijun17/centralu/issues/221)). 그때까지는 명령이 색인됐는데, 색인 81,816행 중 55,131행이었고 236.2MiB 저장소의 124.5MiB 색인 대부분이었다 (실제 저장소의 사본, 2026-09-30). 명령의 출력은 한 번도 색인된 적이 없다. 빼도 오간 말을 찾는 검색은 잃은 것이 없고(표본 질의 397개가 모두 같은 메시지를 돌려줬다), 색인은 36.6MiB, 저장소는 145.4MiB가 됐다. 세션이 무엇을 실행했는지는 검색이 아니라 `read_session`으로 읽는다.
- **네이티브 서브에이전트의 걸음도 검색하지 않는다, 그 글까지** ([#222](https://github.com/ijun17/centralu/issues/222)). 서브에이전트가 찾은 것에 대한 부모 자신의 보고가 대화에 있고, 검색이 찾는 것은 그것이다.
- 휴지통의 세션(FR-22)은 사람의 검색에도 에이전트의 `recall`에도 **나오지 않는다**. 휴지통에 넣을 때 색인 행을 지우고, 되살릴 때 다시 만든다.

#### FR-22. 세션 휴지통 (2026-09-30, [#204](https://github.com/ijun17/centralu/issues/204))

세션을 지우면 휴지통으로 간다. 대화가 이 기계를 떠나는 것은 사람이 **설정 → 휴지통**에서
영구 삭제할 때뿐이다(하나씩, 또는 한 번에). 이유는 소유자의 것이다: 대화는 중요한 데이터이고,
예전에는 삭제 창의 클릭 한 번이 되돌릴 길 없이 대화를 없앴다.

- **휴지통에 가는 것**은 예전 삭제가 없애던 전부다: 세션 행, 메시지, 승인 규칙, 커밋 연결
  (`commit_sessions`), 그 세션을 가리키는 앱 실행 기록(토큰 수 포함), 첨부, 인수인계 노트
  (`<데이터>/handoff/<프로젝트 id>/<세션 id>.md`). 검색 색인만 예외다 — 남기지 않고 지운다.
  그래서 모든 검색에서 빠지고, 차지하던 것의 큰 절반이 풀린다(#96 실측: 137MB 가운데 색인이 71MB).
- **DB 밖의 파일은 제자리에 둔다.** 삭제 창의 두 선택은 영구 삭제할 때 무엇이 함께 가는지를 정한다:
  - *도구의 대화 파일*(Claude JSONL, Codex rollout)은 도구가 두는 자리에 그대로 있다. 도구의
    파일이고 도구의 배치이며, 그 배치를 아는 것은 도구 자신의 삭제뿐이다. 제자리에 두면 두 번째
    돌아오는 길도 된다(도구와 **+ → Past conversations**에 그대로 있다). 그사이 살아 있는 세션이
    같은 대화를 다시 꺼냈다면, 영구 삭제는 그 파일을 남긴다.
  - *워크트리*는 제자리에, git에 등록된 채로 있다. 워크트리 폴더를 옮기면 git의 기록이 아무것도
    가리키지 않게 되고(`git worktree list`가 prunable이라 부르고, `prune`이나 `gc`가 기록을 지운다),
    Claude는 대화를 작업 디렉토리로 찾으므로 되살린 세션이 자기 기록도 잃는다.
- **휴지통에 있는 동안 닿지 않는 곳**: 사이드바, 인박스, 팔레트, 그리드, 프로젝트 화면(§5.5), 대화 검색(FR-21),
  오케스트레이터의 `list_sessions` / `recall` / `read_session`, 앱의 `host_data` `sessions.list`,
  설정의 승인 규칙 목록. 세션을 읽는 저장소의 모든 질의는 휴지통을 어떻게 하는지 말해야 하고,
  말하지 않는 질의가 생기면 host 시험이 실패한다.
- **나오는 길**은 설정 → 휴지통이다: 세션마다 이름, 프로젝트, 지운 시각, 크기, 함께 갈 것을
  보이고, 읽고(읽기 전용), 되살리고, 영구 삭제하고, 휴지통을 비운다. 전체 크기를 보인다 —
  휴지통을 스스로 비우는 것은 없기 때문이다.
- **되살린 세션은 그대로 돌아온다**: 같은 id, 메시지, 규칙, 커밋 연결, 앱 실행 기록, 다시 만든 색인.
  살아 있을 때만 참인 상태(working, 승인 대기)는 재시작 뒤처럼 idle로 돌아온다. 그사이 프로젝트가
  지워졌다면 폴더를 **같은 프로젝트 id로** 다시 등록한다 — 워크트리 폴더, 인수인계 노트, 세션과 함께
  남은 행이 다시 맞물린다. 그 폴더가 새 id로 다시 추가돼 있으면 거기로 간다. 폴더까지 없으면
  되살리기를 거절하고 폴더가 어디 있었는지 말한다. 세션은 휴지통에서 계속 읽을 수 있다.
- **프로젝트를 지우면 그 세션들은 휴지통으로 간다** — 없애지 않는다. 클릭 한 번이 낼 수 있는 가장 큰
  손실이었다. 그때는 도구 파일과 워크트리에 대해 아무도 묻지 않았으므로, 휴지통을 비워도 그것들은
  남는다. 프로젝트 자신의 행(프로젝트 범위 규칙, 사용량 합계, 앱에 한 답)은 예전처럼 프로젝트와 함께 간다.
- **영구 삭제는 사람만 한다.** 휴지통에는 UI의 RPC로만 닿는다. 에이전트의 도구와 앱의 중개에는 그
  동사가 없다. 에이전트는 세션을 휴지통에 넣을 수는 있지만(병합이 증명된 워크트리를 치우는 매니저의
  정리가 그렇다) 꺼내지는 못한다.
- 스키마 v39가 `sessions.deleted_at`(살아 있는 세션은 NULL)과 `sessions.trash`(JSON: 어디서 왔는지,
  영구 삭제할 때 무엇을 함께 지우는지)를 더한다. 휴지통의 세션에는 `project_id`가 없다. 프로젝트는
  `trash`에 있고, 그래서 프로젝트를 지워도 외래키가 세션을 함께 데려가지 않는다. 이후의 마이그레이션은
  휴지통의 세션에 속한 행을 고려해야 한다.
- 다루지 않는 것: 휴지통 세션의 첨부도 모든 첨부와 같은 500MB 상한 아래에 있고, 그 세션을 가리키는
  앱 실행 기록도 앱 실행 기록의 보관 기간 아래에 있다.

## 5. 화면 구성

### 5.1 메인 레이아웃: 사이드바 + 포커스 뷰

관찰(왼쪽, 밀도 높게)과 조작(오른쪽, 전체 폭)의 분리. 그리드가 아니다.

```
┌──────────────────────────────────────────────────────────────────┐
│ ⌘ Centralu    [🔴 2 approvals · 🔵 3 awaiting]  [usage] [＋]     │
├────────────────┬─────────────────────────────────────────────────┤
│ ▾ project A    │  auth refactor (Claude · main · ctx 42%)        │
│   🔴 auth ref  │ ┌───────────────────────────────────────────┐   │
│   ⚙ fix tests  │ │                                           │   │
│ ▾ project B    │ │   conversation stream (full width —       │   │
│   🔵 API rev • │ │   it can actually be read)                │   │
│ ▾ project C    │ │  ┌─ approval request ─────────────────┐   │   │
│   ⏳ migration │ │  │ Bash: npm run build                │   │   │
│ ▾ project D    │ │  │ [y allow] [n deny] [a always]      │   │   │
│   ⚙ gen docs   │ │  └────────────────────────────────────┘   │   │
│                │ └───────────────────────────────────────────┘   │
│  (• = unread)  │  [input box + attachments]                      │
│                │  [conversation | files | git | viewer]          │
└────────────────┴─────────────────────────────────────────────────┘
```

- 사이드바: 프로젝트/세션 트리, 상태 점 (🔴 승인 / 🔵 응답 대기 / ⚙ 작업 중 / ⏳ 한도 / ⛔ 오류 / 👑 오케스트레이터), 안읽음 점, 브랜치와 변경 수 요약. 접을 수 있다.
  - **어떤 프로젝트가 열려 있는지** (2026-10-01). 프로젝트 묶음(이름 줄, 세션, 앱)과 다음 묶음 사이를 가는
    구분선이 나눈다. 포커스 뷰가 어떤 프로젝트의 화면(§5.5)이나 그 프로젝트의 세션을 보여 주거나, 앱 화면이 그 프로젝트의 앱을 보여 주는 동안(2026-10-03), 그 프로젝트의
    묶음 전체에 선택된 Grid·Orchestrator 버튼의 surface-hover가 더 옅게 깔리고, 그 안에서 열린 줄은 더 강한 자기 표시(ink-muted
    막대)를 유지한다 — 프로젝트 화면이면 이름 줄, 세션이면 그 세션의 줄, 앱이면 그 앱의 줄. 줄 표시만으로는 "이 줄"만 말한다. 색조는 누구의
    줄인지를 말하고, 접힌 프로젝트(#205)에는 이것 말고 표시할 자리가 없다. 그리드, 오케스트레이터, 프로젝트가 없는 세션, 사용자 폴더의 앱은
    아무것도 칠하지 않는다 — 어느 것도 프로젝트가 아니다. 두 겹 모두 색만 바꾸므로, 선택해도 어떤 줄도 움직이지 않는다.
- 포커스 뷰: 세션 하나가 전체 폭. 하단 탭으로 파일 트리/git/뷰어 전환 — 전체 폭에서는 각 탭이 실제로 쓸 만한 크기가 된다.
  - **백그라운드 작업** ([#290](https://github.com/ijun17/centralu/issues/290)). 에이전트가 턴 뒤에서 작업을 돌리면 —
    서브에이전트, 백그라운드 셸, MCP 작업 — 세션 헤더가 실행 중인 것을 세고("2 background", 도구가 ambient라고 하는
    것은 세지 않는다) 목록을 연다: 작업마다 종류와 설명, 턴을 멈추면 어떻게 되는지("stops with the turn" /
    "survives Stop"), 도구가 할 수 있는 곳에서는 그 작업만 멈추는 Stop. 끝난 작업은 어떻게 끝났는지(done, failed,
    stopped)와 함께 사람이 지울 때까지 목록에 남고, 에이전트의 행은 그 띄운 카드가 간직한 걸음을 연다(#222).
    사이드바 행도 같은 수를 단다.
  - **중지 버튼은 무엇을 멈추는지 말한다.** 턴이 도는 동안 Stop 옆에, 도구마다 측정한 대로 중단이 백그라운드 작업에
    무엇을 하는지 적는다: "Also stops 1 background task · 1 background task keeps running". Claude는 턴과 함께
    백그라운드 서브에이전트를 멈추고 셸은 계속 돌게 두며, Codex는 자식 에이전트를 계속 돌게 둔다. 이 배경의 사고
    (2026-10-04): 메시지를 고쳐 쓰려고 중단했더니 백그라운드 서브에이전트 둘이 멈췄고, 네 시간 동안 화면 어디에도
    그 말이 없었다.

### 5.3 보조 화면

- **사용량 대시보드**: 주간 막대 차트(일별), 도구/모델/프로젝트별 분해, 추정 비용, 한도 윈도우 상태.
- **세션 생성 대화상자**: 도구 → 모델 → 권한 프리셋 → 시작 프롬프트. 동시 세션 경고 포함 (FR-2).
- **설정**: 도구 경로/감지 상태, 기본 프리셋, 알림 정책(상태별), 단축키, **테마** — Dark, Light, 시스템 따르기, 쪽마다 고르는 테마(프리셋: Dark, Light, High contrast dark, High contrast light), 신호는 칠하지 않는 선택적 강조색, 그리고 데이터 폴더의 파일로 된 사용자 테마(설정에서, 손으로, 에이전트가 고칠 수 있고 바로 반영된다). 테마가 긴급함의 순서를 깨면 경고한다 (#312, [themes.ko.md](themes.ko.md)), **외관 — 5단계 텍스트 스케일** (2026-08-26; OS 디스플레이 배율처럼 화면 전체를 스케일하되, 최소 폭과 그리드 열 계산은 실제 픽셀에 고정), **본문 글꼴과 코드 글꼴**(짧은 목록이나 설치된 아무 글꼴을 이름으로. 늘 앱 자신의 글꼴 앞에 붙어서 한글은 대체 글꼴을 지킨다. 터미널은 코드 글꼴을 따른다) **과 줄 높이**(Compact, Normal, Relaxed. 고정 행 화면은 자기 행을 지킨다), 테마와 함께 화면 설정에 담기고 앱 화면에도 건네진다 (#312, [themes.ko.md](themes.ko.md)), **휴지통** — 지운 세션을 읽고 되살리거나 영구 삭제하는 곳, 전체 크기와 함께 (FR-22), **백그라운드** — 앱을 꺼도 에이전트가 계속 도는지 (FR-10, 데스크톱 전용), **업데이트** — 지금 도는 버전과 최신 버전, Check now, 자동 확인, 설치, Apply now, 한가할 때 자동 적용 (기본 꺼짐; FR-10, 데스크톱 전용). 설치된 에이전트 CLI와, idle 세션을 새로 설치된 CLI로 옮기기 (기본 켜짐; FR-10, #297).

### 5.4 그리드 뷰 (**experimental**)

원래 v1에서 제외되어 있었다. 이유는 세 가지였다:

1. 14인치 화면에서 2×2는 패널당 ~600×400px — 대화 스트림, 입력창, 탭을 넣으면 어느 것도 제대로 볼 수 없다.
2. "다음 대기 항목으로 가기" 루프(한 번에 하나씩 처리)와 인터랙션 모델이 충돌한다.
3. 멀티 프로젝트 요구사항은 사이드바(상시 관찰) + 키보드 전환(즉시 조작)으로 충족된다.

**2026-08-20: 결정이 바뀐다.** 그리드는 이미 만들어져 돌아가고 있었다 — 그런데 이 문서만
"만들지 않는다"고 말하고 있었고, 화면에도 아무 표시가 없었다 (issue #25). 제거하는 대신 **experimental 표시를 달고 출시한다.**

셋 중 **1과 2는 그대로 유효하다.** 죽은 이유가 아니라 살아 있는 이유로서 여기 유지한다:

- **1** — 폭에서 열 수를 계산하는 것(`columnsFor`)으로 패널이 최소 폭 아래로 떨어지는 것은 막았다.
  하지만 그리드에는 **오른쪽 근거 패널이 없다**: 화면이 이미 나뉘어 있는데 거기서 레인을 하나 더
  떼어내면 쓸 수 없는 폭이 남는다. 대화는 볼 수 있지만 "그게 정말 그랬나"는 볼 수 없다.
- **2** — ⌘⇧A(다음 대기 항목으로 가기)는 세션을 고르고 **화면을 포커스 뷰로 되돌린다.**
  한 번에 하나를 처리하는 루프와 여러 개를 동시에 보여주는 화면은 아직 화해하지 못했다.
- **3** — 여전히 참이다. FR-1을 충족하는 것은 사이드바이고, 그리드는 그 위에 얹힌 **또 하나의 보는 방식**이다.

그래서 표시는 화면 안이 아니라 **사이드바의 Grid 버튼**에 붙는다 (#1의 오케스트레이터와 같은
처방: ink-faint 텍스트 + 점선 테두리, 색도 밝기도 쓰지 않는다). 다만 이유는 다르다 — #1은
모르고 누르는 것을 막으려던 것이지만, 그리드는 자유롭게 누를 수 있고 되돌릴 수 있다. 비싼 것은
그 안에서 보내는 시간이며, 그리드가 열려 있는 동안에도 사이드바는 가려지지 않으므로 표시 하나가 **누르기 전과
사용 중 내내**를 모두 커버한다.

표시가 화면을 얼려버린 것은 아니다: 표시가 붙은 이후로 그리드에는 패널을 같은 DOM 노드로 옮기는
드래그 재정렬(대화 스크롤이 살아남는다), 회전하는 working 테두리(§7.1의 측정 비용에 포함됨),
텍스트 스케일 아래에서도 버티는 실제 픽셀 열 계산이 더해졌다. **Experimental은 빌드 품질이 아니라
위의 미해결 반론 두 가지를 가리킨다.** 대형 모니터 사용자를 위한 옵션으로 v2에서 재검토한다.

**그리드 위의 앱 (2026-10-04, [#288](https://github.com/ijun17/centralu/issues/288)).** 앱의 사이드바 줄도
세션의 줄처럼 그리드에 떨어뜨릴 수 있고, 그 패널은 같은 방식으로 옮기고 뺀다.

| 결정 | 이유 |
|---|---|
| 프로젝트의 앱이든 사용자 폴더의 앱이든 **어떤 앱이든**, 그리드나 Grid 버튼에 떨어뜨리면 손 아래 패널의 앞이나 뒤, 또는 맨 끝에 선다; 이미 올라 있는 것은 그리로 옮겨지고, 여백에 떨어뜨리면 제자리에 남는다 | 그리드는 프로젝트를 가로질러 손으로 고른 목록이다; 이 규칙들은 세션으로 이미 손에 익었다. |
| **올린 것만** — 그리드는 앱을 스스로 더하지 않고, 앱 목록에 있는 앱만 받는다 | 그리드는 고른 목록으로 남는다. 드롭은 데이터에서 다시 읽으므로, 스크립트나 경합이 화면이 그릴 수 없는 앱을 올리지 못한다. |
| 패널은 **태그 붙은 참조**다 — `{ kind: 'session', sessionId }` 또는 `{ kind: 'app', projectId \| null, appId }` — 하나의 순서로 (`grid_layout`, v42; `grid.get` / `grid.set`, protocol.ko.md §3) | 세션 id와 앱 id는 겹칠 수 있고, 앱은 프로젝트와 함께여야 그 앱이다 (두 프로젝트가 각자 `slider`를 가질 수 있다). 참조는 패널의 정체성만 담으므로, 원격 모드와 함께 그리드가 클라이언트로 옮겨 갈 때 (#82) 클라이언트가 그대로 가질 수 있다. 지금 없는 세션이나 앱은 그리지 않되 목록에는 남는다; 앱 패널은 프로젝트와 함께 떠난다. |
| **자기만의 화면** — 앱의 `home`으로 열리고 프로젝트 화면처럼 패널 위에 얹히지만 (apps.ko.md §6.2), 앱 화면과 프로젝트 화면이 함께 쓰는 고정 화면과는 따로다 | 소유자 결정: 같은 앱이 여러 곳에 동시에 설 수 있고, 자리마다 자기 화면, 프로세스는 하나다 (런타임의 프로젝트·앱당 인스턴스 하나). 그리드의 ×가 프로젝트 화면에 두고 온 화면을 내려서는 안 된다. |
| 머리글: 앱 이름, 말로 된 상태, Open (앱 화면), ×. 신뢰하지 않은, 확인 전의, 잘못된, 멈춘 앱은 패널 안에서 이유를 버튼과 함께 말한다 — 빈 프레임은 없다 | 앱 화면이 하는 대답과 같다; 패널은 자리가 좁을 뿐이다. |
| ×는 **teardown을 먼저** 보내고 화면을 닫는다; 그리드를 떠나 다른 화면으로 가면 화면을 **가리고** 문서는 남긴다, 프로젝트 화면처럼 | 화면이 사라지는 모든 길은 teardown을 먼저 보낸다 (apps.ko.md §6.2). 내리지 않고 가리는 것은 프로젝트 화면의 규칙이라, 패널은 두고 간 모습 그대로 돌아온다. |
| 무엇이든 끄는 동안 앱 패널마다 자기 화면 위에 **투명한 덮개**를 얹는다; 화면은 보이는 채로 남고, 끌리는 패널의 화면은 패널과 함께 흐려진다. 덮개는 끌기를 떨어뜨리거나 끝내면, 또는 끌기가 창 밖으로 나가면 걷힌다 | WebKit에서는 프레임의 pointer-events가 무엇이든 끌기가 프레임 안으로 들어간다: 앱 화면을 가로질러 옮긴 줄이나 패널은 앱 안에 떨어진다 (Playwright의 WebKit에서 측정, #288). 덮개는 프레임 위에 놓인 페이지의 요소라 끌기가 페이지에 닿는다. 화면을 가려도 같았지만(#294) 끄는 내내 화면이 비었다 — 손에서 먼 화면까지 (#296). |
| 앱 패널 수에 **상한이 없다** | 하나마다 host의 화면 인스턴스 하나와 페이지의 프레임 하나(샌드박스 프록시와 그 안의 앱 문서)가 들고, 그리드를 떠나도 남는다 — 고정 화면과 같은 비용이다. 그리드에는 사람이 올린 것만 있고, 패널마다 이미 최소 폭이 필요하다. |

**앱 패널의 크기 (2026-10-05, [#306](https://github.com/ijun17/centralu/issues/306) C안).** 그리드 위의 앱 패널은
칸을 하나보다 많이 차지할 수 있다 — 열 × 행, 예를 들어 2 × 1. 세션 패널은 언제나 1 × 1이다. 이것을 부른 것은 주인의
그리드다: 세션 몇 개와 프로젝트 보드, 한 칸에서는 너무 좁다.

| 결정 | 이유 |
|---|---|
| **사람이 정한다**, 두 곳에서: 놓인 패널 하나는 패널의 **머리글**에서 (작은 "2×1"이 칸 고르개를 연다), 앱 하나는 **설정 → 앱**에서 ("Size on the grid"). 앱은 매니페스트에서 하나를 **권할** 수 있다 (`view.span`, apps.ko.md §1.1) | 주인의 결정: 크기는 앱이 아니라 사람의 설정이다. 앱은 자기에게 맞는 것만 안다; 보드는 2 × 1을 권한다. |
| 우선순위: **놓인 패널의 선택 > 설정의 값 > 앱의 권장 > 1 × 1** | 두 단계 모두에서 사람이 앱보다 앞선다. 설정은 자기 선택이 없는 모든 놓임의 기본값이라 새로 놓은 패널은 거기서 시작한다; 고르개의 "Use the default"는 한 단계 내려가고, 어디에 닿는지 이름을 댄다. |
| 놓인 패널의 선택은 **그 놓임에** 저장되고 (`grid_layout.span_cols`/`span_rows`, v43; `GridPanel.span`), 설정의 값은 작업 공간 스냅샷에 (`appSpans`, 앱을 키로) | 머리글의 선택은 그 패널에 대한 것이다: 패널을 빼면 잊는다. 앱마다의 값은 UI만 읽는 보는 방식이고, host의 표가 키로 삼지 않는 앱에 대한 것이다 (사용자 폴더의 앱에는 프로젝트가 없다). |
| 각 변은 **1에서 4**. 열 수는 여전히 너비에서 고르고 (최소 너비 아래의 패널은 없다) 그리드는 여전히 스크롤하지 않는다: 맞는 열 수 가운데 빈 칸이 가장 적은 것, 크기를 셈에 넣고; 같으면 열이 적은 쪽 (core의 `grid/span.ts`의 `arrangeGrid`) | 1 × 1 패널의 열을 이미 고르던 규칙을 넓힌 것이다 — 그래서 아무도 크기를 정하지 않은 그리드는 칸 하나하나까지 전과 같다 (단위 테스트가 둘을 붙잡는다). 세션 하나와 2 × 1 보드는 세 열짜리 한 줄에 선다 — 보드가 세션 위에 서고 옆에 구멍이 나는 대신. |
| 패널은 **순서대로, 저마다 왼쪽 위부터 맞는 첫 자리에** 놓인다 | 결정적이다: 같은 창의 같은 목록은 언제나 같게 나온다. 넓은 패널 뒤의 1 × 1 패널은 넓은 패널이 채우지 못한 구멍을 비워 두지 않고 채운다. |
| 창이 담지 못하는 크기는 창이 담는 만큼으로 **잘린다** (모든 열, 그리고 그리드가 가질 수 있는 만큼의 행) — 빠지지는 않는다; 단추가 점선이 되고 창이 담는 크기를 말한다. 창이 넓어지면 다시 자란다 | 모든 패널이 보이는 채로 남는다. 단추보다 작은 패널이 말없이 서 있는 것보다 말하는 편이 낫다. 이미 그리드 전체를 덮는 패널은 표시하지 않는다: 창이 허락하는 만큼 크다. |
| 끌어서 순서 바꾸기는 그대로다; 미리보기는 새 순서를 같은 열 수에 채운다 | 떨어뜨려도 화면은 바뀌지 않는다 (#53). 크기가 있으면 미리보기가 확정된 순서보다 한 줄 더 또는 덜 필요할 수 있다 — 끄는 도중 칸의 높이가 바뀌는 유일한 경우다. |

### 5.5 프로젝트 화면 (2026-09-30, [#203](https://github.com/ijun17/centralu/issues/203))

사이드바에서 프로젝트 이름을 누르면 그 프로젝트의 화면이 열린다 (이름은 여는 자리이고, 옆의 화살표가
그 프로젝트의 줄을 접는다, #205). 이 화면은 **프로젝트가 가진 모든 것 — 세션과 앱 — 을 패널로** 보이고,
그리드처럼 늘어놓고 옮긴다.

| 결정 | 이유 |
|---|---|
| **모든 것이 저절로 선다**; 손으로 올려야 하는 것은 없다 | 이 화면은 "이 프로젝트"이지 그중에서 고른 것이 아니다. 채워지기를 기다리는 화면은 처음 열 때 비어 있는데, 그때가 바로 스스로를 설명해야 하는 유일한 순간이다. |
| 새 패널은 **맨 끝에** 선다; 아무도 옮기지 않은 패널은 옮긴 패널 뒤에 사이드바 순서대로 선다 | 누군가 만든 배치의 한가운데로 끼어드는 패널은 그 뒤의 모든 패널을 민다. |
| 패널은 **숨길** 수 있다 (×, 세션은 계속 돈다); 숨긴 패널은 패널들 위에 이름으로 남고, 이름으로 되돌리면 맨 끝에 선다 | 숨기기는 지우기가 아니고, 흔적 없이 사라진 패널은 숨긴 것을 아무도 기억하지 못한다. 예전 자리는 그 뒤로 바뀐 화면의 기억일 뿐이다. |
| **그 프로젝트의 사이드바 줄을 여기에 떨어뜨릴 수 있다** — 세션을 그리드에 떨어뜨리듯, 세션과 앱 모두. 숨긴 것은 떨어뜨린 자리에 돌아오고 (손 아래 패널의 앞이나 뒤, 여백이면 맨 끝), 보이는 것은 그리로 옮겨지며, 여백에 떨어뜨리면 제자리에 남는다. 순서는 옮긴 패널처럼 기억한다 | 원하는 자리로 패널을 되돌리는 일이 두 동작(되돌리고, 끌고)이 아니라 한 동작이 되고, 그 동작은 그리드가 이미 손에 가르쳐 두었다. 여백 규칙은 이미 올라 있는 세션에 대한 그리드의 규칙이다. |
| **이 프로젝트의 것만**: 다른 프로젝트의 세션이나 앱, 그리고 오케스트레이터는 끄는 동안 이미 거절된다 — 드롭 커서가 없다 — 그래도 도착한 드롭은 무시한다 | 이 화면은 프로젝트 하나, 통째다; 다른 프로젝트의 패널이 끼면 고른 목록이 되고, 그건 그리드의 일이다. 거절은 손을 놓기 전에 보여야 한다, 아니면 드롭이 고장으로 읽힌다. 페이지는 드롭 전까지 끌리는 것의 타입은 읽어도 데이터는 못 읽으므로, 프로젝트를 타입 하나에 담는다 (`application/x-cc-of-project.<id>`); 드롭은 데이터를 다시 확인하고, 앱은 프로젝트를 담은 키로 맞춘다 — 두 프로젝트가 같은 id의 앱을 하나씩 가질 수 있다. |
| **프로젝트마다, 재시작을 넘어** 기억하는 것은 옮긴 순서와 숨긴 목록뿐이고, 작업 공간 스냅샷에 사이드바 접힘과 나란히 둔다 | 한 프로젝트를 보는 방식이고, UI만 읽고 쓴다; host는 여기에 따라 아무것도 하지 않는다. 그리드의 표(`grid_layout`)가 주는 것 — 세션이나 프로젝트와 함께 패널이 떠나는 것 (#288부터는 앱도 담는다) — 은 여기서는 패널을 있는 것에서 끌어내는 데서 오므로, 지킬 패널 목록은 없고 그 위에 얹은 손만 있다. 프로젝트를 지우면 그 배치도 지운다. |
| 휴지통의 세션(FR-22)은 패널이 되지 않는다; 되살린 세션은 맨 끝으로 돌아온다 | 패널은 세션 목록에서 끌어내고, 휴지통의 세션은 거기 없다 — 기억한 순서가 그 이름을 담고 있어도 아무것도 서지 않는다. |
| **앱의 패널은 그 앱의 고정 화면이다** (apps.ko.md §6.2): 같은 인스턴스, 같은 프레임; Open은 앱 화면으로 가고; ×는 teardown을 먼저 보내고 화면을 닫는다. 무엇이든 끄는 동안 패널이 자기 화면 위에 투명한 덮개를 얹고 화면은 보이는 채로 남는다 — 그리드와 같다 (§5.4) | 옮겨진 iframe은 문서를 잃고, 인스턴스 하나에는 프레임이 하나여야 한다. 그래서 화면을 패널 안에 그리지 않고 패널 위에 얹는다 — 이 화면, 앱 화면, 세션 사이를 오가도 문서는 하나다. 머리글의 Runs·Secrets·Versions·Builder는 패널에 자리가 없는 옆 판을 여는 것이라 앱 화면에 남는다. 여기에 앱을 보이면 그 앱이 열린다(host가 `home`을 부른다) — 신뢰와 가져오기 확인은 언제나처럼 그 안에서다. WebKit에서는 프레임의 pointer-events가 무엇이든 끌기가 프레임 안으로 들어간다 (Playwright의 WebKit에서 측정): 앱 화면 위에 떨어뜨린 줄은 앱 옆이 아니라 앱 안에 떨어지고, 머리글이 아니라 옆에서 앱 화면으로 옮겨 온 세션 패널은 화면에 아예 닿지 않았다 (#288). 프레임 위의 덮개가 둘 다 페이지에서 받는다; 화면을 가려도 받았지만 끄는 내내 화면이 비었다 (#296). |
| 앱의 패널은 세션의 패널과 **같은 손짓**을 받는다: 사이드바에서 떨어뜨리기, 머리글로 순서 바꾸기, 같은 드롭 규칙과 표시 (손 아래 패널의 `data-drop`), 그리고 키보드 순서의 자리 — 머리글에서 Tab을 누르면 그 화면으로 들어가고, 나오면 머리글로 돌아온다 | 화면은 문서에서 모든 패널 뒤에 선다 (패널 안이 아니라 위에 얹히므로). 그래서 자리가 포커스를 넘겨주지 않으면 Tab은 화면을 건너뛰고 마지막 패널 뒤에야 닿는다 (#288). |
| **그리드는 그리드대로다** | 여전히 프로젝트를 가로질러 손으로 고른 목록이고, 세션과 함께 앱도 담는다 (§5.4). 세션이나 앱은 둘 모두에 있을 수 있다; 그리드 위의 앱은 이 화면의 것과 따로 자기 화면을 가진다. 세션 패널을 Grid 버튼에 떨어뜨리면 사이드바 줄처럼 그리드에 오른다. |
| 그리드와 달리 **근거 패널이 옆에 남는다** | 프로젝트 하나, 저장소 하나: §5.4의 반론 1이 여기에는 해당하지 않는다. 열 수는 남은 폭에서 계산하므로(`columnsFor`) 어느 쪽이든 패널이 최소 폭 아래로 내려가지 않는다. |

패널은 그리드의 부품을 같이 쓴다: `SessionPane`, 열 수 계산, 온전한 픽셀 트랙과 working 링(#208), 그리고
입력창 접기와 링 멈추기 설정. 보이는 패널에서 끝난 세션은 카드가 아니라 바람을 받는다. 패널은 세션 포커스를
가져가지 않으므로 패널에 입력해도 화면을 떠나지 않는다; §5.4의 반론 2는 여기서도 유효하다 — ⌘⇧A와
인박스는 포커스 뷰를 연다. 아무것도 없는 프로젝트는 그렇다고 말하고 새 세션을 권한다; 패널을 모두 숨긴
프로젝트는 빈 그리드의 말투로 사이드바에서 세션과 앱을 끌어오라고 한다.

## 6. 시스템 아키텍처

### 6.1 프로세스 구조

실제 구현에서 Rust 셸은 처음 그림보다 **얇아졌고** Node 호스트가 **더 많이 소유한다** — 셸은 감독하고,
호스트가 일하며, UI는 dev와 prod에서 동일한 WebSocket 하나로 호스트와 대화한다
(상세는 [architecture.ko.md](architecture.ko.md)):

```
┌─────────────────────────── Tauri app (Rust) ──────────────────────────┐
│  · window/tray/notifications      · attaches to the keeper            │
└──────────────────────────────┬────────────────────────────────────────┘
                               │ unix socket (attach, host info, stop, switch)
┌──────────────────────────────┴────────────────────────────────────────┐
│  keeper — the same executable as `centralu --keeper`, detached         │
│  · launches, watches, restarts and swaps the host · per-build copies  │
│  · hands itself, and everything it holds, to a new build's keeper     │
│  · the front door: one stable port and token, relayed to the host     │
└──────────────────────────────┬────────────────────────────────────────┘
                               │ the UI talks to the host over WebSocket
                               │ (same protocol dev and prod), through
                               │ the keeper's front door in the app
┌──────────────────────────────┴────────────────────────────────────────┐
│                      Node sidecar (Agent Host)                        │
│  · ClaudeAdapter (Claude Agent SDK)   · CodexAdapter (app-server RPC) │
│  · common event normalisation         · orchestrator tools (FR-11)    │
│  · git CLI wrapper (FR-4)             · file tree IO + dir watchers   │
│  · SQLite (~/.centralu/store.db — sessions, messages, workspace)      │
└──────┬──────────────────────────┬─────────────────────────────────────┘
       │                          │
  Claude Code sessions       Codex sessions   (processes exist only while sessions do)
```

### 6.2 공통 어댑터 인터페이스 (확장의 심장)

```ts
interface AgentAdapter {
  createSession(opts: { cwd, model?, permissionPreset?, resumeId? }): SessionHandle
  send(sessionId, input: { text, attachments?: Attachment[] }): void
  respondApproval(sessionId, requestId, decision: 'allow'|'deny'|'always',
                  scope?: 'session'|'project'): void
  interrupt(sessionId): void
  dispose(sessionId): void
  // The adapter → app direction is normalised into a single event stream:
  // message_delta | tool_call | tool_result | approval_request
  // | turn_complete | usage_update | context_update | state_change
  // | limit_reached | session_title | error
  events: EventStream<NormalizedEvent>
}
```

- UI는 `NormalizedEvent`만 안다. 도구별 차이(승인 메커니즘, 사용량 형식, resume 메커니즘)는 어댑터 내부에서 흡수한다.
- 어댑터는 **capability 선언**을 제공한다: `{ approvals: boolean, contextUsage: 'exact'|'estimate', resume: boolean, autoTitle: boolean }` — UI는 이를 바탕으로 기능을 켜고 끈다 (예: 승인을 덮어쓸 수 없는 도구는 승인 UI를 숨김).
- v2에서 Gemini CLI 등을 추가한다는 것은 새 어댑터 하나를 쓰는 것, 그 이상이 아니다.

### 6.3 데이터 모델 (SQLite)

- `projects(id, path, name, default_tool, default_model, sidebar_order, …)`
- `sessions(id, project_id, tool, external_session_id, name, auto_named, state, is_orchestrator, verbosity, last_read_seq, created_at, deleted_at, trash, …)` — `kind`는 `is_orchestrator`에서 온다. 이 앱의 유일한 오케스트레이터만 그 표식을 갖는다 (FR-11). `deleted_at`은 세션이 휴지통에 있는 동안 적혀 있고(FR-22, v39), 모든 목록이 이 칸으로 거른다
- `messages(session_id, seq, role, kind, payload_json, ts)` — 복원용 대화 캐시 (+ FTS5 인덱스, M2). 한 행은 스트리밍 델타가 아니라 **메시지 하나**다 (#66): 스트리밍 중에는 열린 메시지의 행을 제자리에서 갱신하고(주기 flush), 닫힐 때 한 번 색인한다. 행이 닫히는 곳은 기록되는 이벤트, 턴의 끝, 답과 추론 사이의 전환, 그리고 열린 행과 다른 메시지를 가리키는 조각(`messageId`, #212: codex는 사이에 아무것도 기록되지 않은 채 두 말을 연달아 할 수 있다)이다. 읽기는 델타 시절의 행도 병합하므로 마이그레이션 전 데이터도 같게 동작한다. 도구 호출은 통째로 남는다 (#221, v40): `summary`(카드)에 더해 도구가 받은 `input`과 출력 전체 `output`. 이 둘은 저장소만 가진다 — 독자는 기록을 이름으로 묻지 않는 한 카드를 받고, 색인에는 `text`와 `reasoning` 행만 들어간다 (FR-21; [security-boundaries.md](security-boundaries.md#tool-output-in-the-store)). v40 전에 쓴 행에는 카드만 있다.
- `subagent_messages(session_id, parent_call_id, seq, role, kind, payload_json, ts)` — 네이티브 서브에이전트가 한 일을 띄운 호출 아래에 남긴다 (#222, v41): 글, 읽을 수 있는 추론, 그리고 통째의 도구 호출과 결과를 `messages`와 같은 payload 모양으로. `messages`에 칸을 더하지 않고 표를 따로 둔다 — 그래야 대화를 읽는 모든 독자(기록 페이지, 안 읽음, 인계 기록과 인계 노트, `read_session`, `recall`, 오케스트레이터의 기억)가 지금 읽는 것을 읽는 것만으로 건너뛴다. 유일한 독자는 띄운 카드 하나를 지목한다. `seq`는 그 띄운 호출 안에서 센다. 그래서 서브에이전트는 대화의 안 읽음 표시를 움직이지 않는다. 색인하지 않는다. 행은 세션의 것이다: 휴지통이 지니고, 영구 삭제가 지운다. v41 전의 서브에이전트 실행은 채워 넣지 않는다.
- `grid_layout(panel_key, kind, session_id?, project_id?, app_id?, position, span_cols?, span_rows?)` — 그리드에 올린 것, 순서대로 (§5.4): 세션이나 앱 하나, `session:<id>` / `app:<프로젝트 id | _user>/<앱 id>`를 키로 삼아 패널은 한 번만 오른다 (v42, #288). 세션 패널은 세션과 함께 cascade되고 휴지통으로 갈 때 떠난다; 앱 패널은 프로젝트와 함께 떠난다. `span_cols`/`span_rows`는 사람이 앱 패널의 머리글에서 고른 크기이고, 고르지 않았으면 둘 다 NULL이다 (v43, #306)
- `grid_panels(session_id, position)` — #288 이전의 그리드, 세션 id 하나에 한 줄. v42가 그 줄들을 `grid_layout`에 한 번 옮겨 적고, 한 빌드 이전의 host를 위해 그대로 두었다 (agent-host.ko.md §5.1); 이 빌드는 휴지통으로 간 세션을 빼는 것 말고는 더 읽거나 쓰지 않는다. 지우는 것은 나중의, 깨뜨리는 단계다
- `approval_rules(scope, project_id?, session_id?, matcher, decision, created_at)` — "항상 허용" 규칙
- `usage_facts(date, tool, model, project_id, input_tokens, output_tokens, cache_tokens, cost_est)` — 증분 집계. 만들지 않았고, 테이블은 나중 릴리스에서 지운다([agent-host.ko.md](agent-host.ko.md) §6)
- `workspace(id, layout_json, updated_at)` — 스냅숏

## 7. 비기능 요구사항

### 7.1 성능·에너지 목표 ("가벼움"의 수치화)

| 지표 | 목표 |
|---|---|
| 유휴 시 CPU (세션 4개 유휴) | ≈ 0% (측정치 < 1%) |
| 앱 메모리 (프로젝트 4개, 세션 4개, 에이전트 프로세스 제외) | < 400MB |
| 콜드 스타트 → 워크스페이스 복원 완료 | < 3s |
| 스트리밍 중 UI 프레임 | 60fps 유지 (가상화 리스트) |
| 에너지 | macOS 활성 상태 보기의 에너지 영향을 "낮음"으로 유지 (스트리밍 중 제외) |

달성 방법: 이벤트 구동(폴링 없음), **포커스 뷰 단일 렌더**(포커스되지 않은 세션은 상태와 안읽음만 갱신), lazy 파일 트리, 워처 디바운스, 가상화된 대화 리스트.

**2026-08-26 측정** (perf 스위트, `pnpm perf` — WebKit, 프로덕션 엔진): 유휴 브라우저 프로세스 CPU
0.1–0.2%, React 커밋 0회; 세션이 *working*일 때 3.3% (포커스) / 4.0% (그리드, 패널 4개). working
수치는 그날까지 24.4% / 32.9%였다 — 스피너가 등록된 커스텀 프로퍼티를 통해 conic-gradient의 각도를
애니메이션하고 있었고, 이는 매 프레임 메인 스레드에서 리페인트한다; 지금은 미리 래스터화한 플레이트를
transform으로 회전시키며, 컴포지터가 소유한다. 이 교훈을 여기 기록하는 이유는 §7.1 원칙의
상시 부하 버전이기 때문이다: **아무 일도 없을 때 화면이 하는 일이 곧 배터리 청구서다.** perf 스위트
(`e2e/perf-idle.spec.ts`, `e2e/perf-grid.spec.ts`)는 판정이 아니라 숫자를 출력한다.

### 7.2 기타

- **오프라인/장애 내성**: 어댑터 프로세스 크래시 시 세션 상태를 `error`로 옮기고 + 원클릭 재시작. 앱 크래시 시 스냅숏에서 복원.
- **보안**: API 키를 직접 다루지 않는다 — 각 CLI 자체의 로그인(키체인)을 그대로 쓴다. 앱 DB에 시크릿을 저장하지 않는다.
- **플랫폼**: macOS 우선(개발 머신), 구조는 크로스 플랫폼 유지(Tauri).
- **언어**: 한국어 우선 UI, 문자열을 분리해 영어 추가가 쉽도록.

### M4 (진행 중) — 앱: 도구를 만든 자리가 곧 쓰는 자리 (상세는 [plans/apps-plan.md](plans/apps-plan.md))

M3 뒤의 독립된 마일스톤이고, M3는 그대로 둔다 (2026-09-25 결정). 목표: 에이전트가 하던 일에 쓸 도구를 **화면과 함께** 만든다.
사람은 만든 자리에서 눌러 쓰고, 같은 자리에서 고쳐 달라고 한다. 에이전트는 같은 도구를 함수처럼 부른다. 화면과 함수를 두 벌
만들지 않고 도구는 하나다. 판정은 C 끝의 도그푸딩이다: 예전에 만들었지만 설치와 설정 장벽 때문에 쓰이지 않던 도구 하나를
이 방식으로 다시 만들고, 비개발자가 설명 없이 연다.

앱은 MCP 서버이고 앱의 화면은 MCP Apps 화면이다. 표준이 닿는 데까지는 표준 그대로다 — 코드가 실제로 하는 일은
[apps.ko.md](apps.ko.md)에 있다.

들어가는 것:

- **A. 런타임** — 매니페스트, 프로젝트 안(`.centralu/apps/`, 저장소와 함께 커밋)이나 사용자 폴더의 앱, 처음 필요할 때
  띄우고 쉬면 내리기, 공개 범위와 실행 기록을 지나는 하나의 호출 경로, Claude·Codex 세션에 붙이기, 승인한 MCP 서버를 앱으로
  흡수, 모든 앱의 한 목록, #92와 함께 쓰는 프로젝트 신뢰
- **B. 화면** — 자기를 부른 도구 카드 아래의 대화 안 화면(규격 본래의 자리이고, 다른 호스트용 앱이 도는 자리), 메인 영역의
  고정 화면(호스트가 앱의 home 도구를 부른다), 불투명 출처의 샌드박스 프록시, 열린 화면에 보내는 바뀜 알림, 뜨는 동안의
  스켈레톤과 실패의 이유, 실행 기록 패널
- **C. 만들기 루프** — 새 앱 버튼과 `create_app`, 앱마다 만드는 세션, 사람 대신 만드는 세션이 자기 앱을 시험하는 `check`,
  만드는 세션의 턴 끝에 다시 띄우기, 화면 아래의 "여기를 고쳐 줘" 입력줄, 사람이 눌러야만 만드는 세션에 가는 오류
- **D. 중개** — 앱이 호스트를 거쳐 사람의 에이전트, 다른 앱의 도구, 호스트 데이터를 부탁한다. 처음 쓸 때의 능력 승인, 사슬과
  빈도의 상한, 사슬을 따라가는 취소와 기록

가볍게: **E. 건네기의 로컬 절반** — git 밖 앱의 스냅샷, 가져올 때의 확인 화면, `centralu://` 딥링크. 프로젝트와 함께
커밋된 앱은 이미 팀과 나뉜다.

빠지는 것: 팀 서버(권한, 배포, 중앙 실행 기록 — 유료 경계), 앱 마켓, 앱이 스스로 깨어나는 일(타이머, 감시 — 중개는 실행이
시작하지 않은 호출을 거절한다). 그 밖에 앱 서버 자체의 프로세스 샌드박스, 화면을 찍어 만드는 세션에 넘기기.

내장 컨트롤 앱(오케스트레이터 화면의 레일과 그 작업·반장, #80/#81)은 새 형식으로 옮기지 않고, 그 밑의 컴파일된 앱 틀과 함께
걷어냈다([#372](https://github.com/ijun17/centralu/pull/372), [#97](https://github.com/ijun17/centralu/issues/97)에서 정했다. 2026-10-05 소유자 결정: 레일은 거의 보지 않고 세션은 그리드에서
돌린다. 오케스트레이터의 세션을 보여 주는 화면이 필요하면 외부 앱으로 만든다). 인박스(FR-15)는 상단 바에 남는다.

## 10. 미결 질문 (다음에 결정할 것)

1. 사용 비용 추정용 단가 테이블의 유지 방식 (하드코딩 vs 로컬에서 갱신 가능한 테이블)

### 종결된 질문 (v0.4에서 결정)

- Git commit/staging → **v1.5에 들어간다** (읽기 패널이 끝난 직후, 같은 패널의 확장으로). rebase 같은 고급 조작은 계속 non-goal.
- 주간 사용량 데이터 소스 → **로그 파싱 유지** (SDK는 자기 세션의 턴별 사용량만 주고, 주간 집계나 plan limit API가 없음을 확인 — FR-9 참조).

- 프런트엔드 → **React**. 유휴 에너지는 렌더 정책(§7.1)이 결정하므로 프레임워크의 가벼움은 결정 요인이 아니다; 생태계와 에이전트 주도 개발 친화성이 우선.
- 오케스트레이터 `create_session` → **제안 카드 + 인간 확인** (조회/읽기/전송 세 도구는 자동).
- "항상 허용" 규칙 → **패턴 허용 + 등록 시 매칭 미리보기 + 설정의 규칙 관리**. 표현력을 제한하는 대신 결과를 보이게 한다.
- `waiting_input` 알림 → **기본은 무음(배지만), 모든 세션이 작업을 마치면 "all done" 알림 하나**.
