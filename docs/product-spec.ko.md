## 1. 개요

### 1.1 문제

에이전틱 코딩 도구를 실제 업무에 쓰다 보면 결국 **여러 프로젝트 × 여러 세션**을 동시에 돌리게 된다. 현재 워크플로에서 아픈 지점:

- 터미널 탭이 수십 개로 불어나고, **어느 세션이 내 입력을 기다리는지** 알 방법이 없다.
- 에이전트가 바꾼 파일을 보려면 프로젝트마다 따로 IDE를 열거나 `git status`를 실행해야 한다.
- 도구별(Claude Code / Codex) 사용량과 컨텍스트 상태가 흩어져 있어 전체 그림이 잡히지 않는다.
- 이를 위해 IDE를 여러 개 띄우면 머신이 감당하기 어려울 만큼 RAM과 배터리를 잡아먹는다.

문제의 핵심은 여러 세션을 한 번에 볼 수 없다는 것이 아니라 **터미널 탭이 흩어져 있다는 것**이다. 이 구분이 화면 설계(§5)의 출발점이다.

### 1.2 이 제품은 무엇인가

**Centralu**는 "에이전트 관제탑"이다. 코드를 *작성하는* 도구가 아니라 — 코드를 쓰는 에이전트들을 한 화면에서 **관찰하고, 개입하고, 관리하는** 도구다.

관제탑의 본질은 **모든 것을 보여주는 것이 아니라, 지금 봐야 할 것을 골라내는 것**이다.

**제품 철학 — 모든 기능 결정을 시험하는 기준:**

> **Centralu는 통제하지 않는다. 통제를 가능하게 한다.** 에이전트의 자율성이나 사용자의 워크플로를 제한하지 않는다; 지금 무슨 일이 일어나고 있는지, 무엇이 내 판단을 기다리고 있는지를 정확히 보여준다. **막지 말고, 보이게 하라.** 그리고 이 시스템에서 가장 비싼 자원은 토큰이 아니라 **인간의 주의력**이다.

기능을 추가하거나 바꿀 때마다 이 기준에 비추어 묻는다: 이것은 강제인가 가시성인가, 인간의 주의력을 아끼는가 낭비하는가?

3가지 핵심 가치:

1. **놓치지 않는다** — 어느 세션이 내 응답을 기다리는지, 얼마나 급한지 즉시 안다
2. **즉시 개입한다** — 승인과 응답을 키보드로 빠르게 처리하고 다음 대기 항목으로 넘어간다
3. **가볍게 유지한다** — IDE 여러 개 대신, 유휴 상태에서 거의 아무것도 소모하지 않는 앱 하나

### 1.3 핵심 사용 루프 (이 제품이 지탱해야 하는 실제 행동)

```
come back to the desk
  → check the inbox: "2 waiting for approval · 3 waiting for a response"
  → handle the urgent ones (approvals) first, in sequence, from the keyboard
  → for the ones waiting on a response, read the result (mark read) then give the next instruction or end it
  → when it is all empty, leave the desk (the agents keep working)
```

모든 화면·단축키·알림 설계는 이 루프가 얼마나 빨리 도는가로 판단한다. 지표는 "얼마나 많이 보여주는가"가 아니라 **"루프 한 바퀴가 얼마나 빠른가"**다.

### 1.4 설계 원칙

1. **관찰과 조작의 분리** — 관찰(상태 파악)에는 공간이 거의 필요 없다(상태 점, 배지, 카운터). 조작(대화 읽기, 승인, 지시)에는 많은 공간이 필요하다. 따라서 관찰은 밀도 높은 사이드바와 인박스에, 조작은 전체 폭의 포커스 뷰에 둔다.
2. **긴급도의 구분** — "에이전트가 막혀 있다(승인 대기)"와 "턴이 끝났다"는 서로 다른 정보다. 절대 같은 배지로 합치지 않는다.
3. **키보드 우선** — 제어 루프의 모든 동작(세션 간 이동, 승인, 인박스 순회)은 마우스 없이 가능해야 한다. 마우스보다 느린 GUI는 터미널보다 못하다.
4. **상태와 읽음 상태는 별개** — "이 세션이 대기 중인가"와 "내가 결과를 봤는가"는 독립적인 축이다.

### 1.5 Non-goals

범위가 새는 것을 막기 위해, v1이 명시적으로 **하지 않는** 것:

- 코드 **편집** (뷰어만 제공; 편집은 IDE의 일)
- ~~터미널 에뮬레이터 (에이전트 대화는 raw 터미널이 아니라 구조화된 GUI)~~ — **2026-08-26 철회.**
  근거 패널에 Terminal 탭이 생겼다. 이 항목이 지키려던 것은 여전히 유효하다 — **에이전트 대화**는
  PTY 래핑이 아니라 구조화된 GUI다 — 하지만 그 옆의 프로젝트 터미널은 대화의 대체물이 아니라
  프로젝트를 관찰하는 일의 일부로 판명되었다. 아래 그리드 항목과 같은 이유로, 삭제하지 않고 기록으로 남긴다.
- 고급 git 조작 (rebase, cherry-pick 등 — 읽기 중심; commit/staging은 나중에)
- 원격/클라우드 실행 (로컬 머신의 로컬 프로젝트만)
- Claude Code와 Codex 이외의 도구 (어댑터 구조만 확장 가능하게 설계)
- ~~**동시 분할 그리드 뷰**~~ — **2026-08-20 철회.** 이미 만들어졌고, **experimental** 표시를 달고 출시된다(§5.4).
  이 항목은 삭제하지 않고 유지한다: 그리드가 화면에 떠 있는데 이 문서만 "만들지 않는다"고
  말하던 시기가 있었고(issue #25), 그 불일치가 어디서 왔는지가 이 목록에서 사라져서는 안 된다.

## 2. 확정된 기술 방향

| 항목 | 결정 | 근거 |
|---|---|---|
| 앱 셸 | **Tauri 2.x** (Rust 코어 + 네이티브 webview) | "가벼움" 요구사항. Electron보다 메모리·에너지 사용이 크게 낮다 |
| 지원 에이전트 (v1) | **Claude Code, Codex CLI** | 사용자의 결정. 어댑터 인터페이스를 통해 나중에 확장 가능 |
| 연동 방식 | **SDK/프로토콜 기반** (PTY 래핑 아님) | 상태 감지(대기 중인가), 컨텍스트 사용량, 승인 요청을 구조화된 이벤트로 정확하게 수신 |
| 에이전트 어댑터 실행 | Node.js 사이드카 프로세스 | Claude Agent SDK(TypeScript)와 Codex 프로토콜 클라이언트를 Node에서 실행, Tauri가 감독 |
| 프런트엔드 | **React** (확정) | 유휴 에너지는 프레임워크가 아니라 렌더 정책(§7.1)이 결정한다. 생태계와 에이전트 주도 개발 친화성이 분명한 장점 |
| 로컬 저장소 | SQLite (앱 데이터 디렉터리) | 워크스페이스/세션/사용량 캐시 영속화, 재시작 시 복원 |

**연동 상세:**

- **Claude Code** → Claude Agent SDK (TypeScript). 스트리밍 메시지, 세션 resume, 도구 호출 이벤트, 권한 요청 콜백(`canUseTool`), 토큰/컨텍스트 정보를 구조화된 형태로 제공한다.
- **Codex CLI** → `codex app-server` JSON-RPC (stdio) 프로토콜. 대화 스트림, 승인 요청, 세션 관리를 프로그래밍 방식으로 처리한다. (버전 간 프로토콜 차이는 어댑터 내부에서 흡수한다.)
- 두 도구 모두 **공통 어댑터 인터페이스** 뒤에 숨긴다. → §6.2

**⚠ 승인 이벤트의 전제 조건 — M0에서 검증됨, 승인 UI 성립:**
사용자가 CLI를 전역 bypass(자동 승인)로 설정해 두면 승인 요청 이벤트가 **아예 발생하지 않는다**. Centralu의 승인 UI가 의미를 가지려면, 세션 생성 시의 권한 프리셋(FR-7)이 전역 설정을 세션 단위로 덮어쓸 수 있어야 했다. **M0에서 가능함을 확인했다** — Claude Agent SDK는 세션별 `permissionMode`/`canUseTool`을 받고, Codex는 스레드별 승인 정책을 받는다 — 따라서 Centralu에서 만든 세션은 전역 설정과 무관하게 선택한 프리셋대로 동작한다.

## 4. 기능 요구사항 상세

### 4.1 원래의 14개 요구사항 구체화 (FR-1 ~ FR-14)

`FR-n`은 원래 요구사항 번호에 대응한다.

#### FR-1. 멀티 프로젝트 관리 (사이드바 + 포커스 뷰)

- "한 창에 4개 이상의 프로젝트"는 **한 창에 4개 이상을 등록하고 빠르게 오갈 수 있는 것**으로 충족된다. 동시 분할 표시(그리드)도 존재하지만 **실험적 기능**이다; 이 요구사항을 충족하는 것은 그리드가 아니라 사이드바다(§5.4).
- 왼쪽 사이드바: 전체 프로젝트/세션 트리를 항상 밀도 높게 표시 — 프로젝트명, 브랜치, 변경 파일 수, 세션별 상태 점과 안읽음 표시. **관찰에는 이것으로 충분하다.**
- 오른쪽 포커스 뷰: 선택된 세션 하나가 전체 폭을 차지 — 대화, 파일, git, 뷰어 탭이 실제로 볼 수 있는 크기로 나온다.
- 프로젝트 등록: 디렉터리 선택 또는 드래그 앤 드롭. 최근 프로젝트 목록을 유지한다.
- 전환은 키보드로: ⌘1~9로 프로젝트 점프, j/k로 세션 간 이동 (→ FR-17).

#### FR-2. 워크트리 강제 안 함 + 동시 세션 안전장치

- **원본 디렉터리에서 직접 작업하는 것이 기본이다.** Git 워크트리는 만들지도, 요구하지도 않는다.
- git 저장소가 아닌 디렉터리도 프로젝트로 등록할 수 있다 (git 패널만 비활성화).
- **동시 세션은 데이터 손실 위험이다** (한 에이전트가 다른 에이전트의 변경을 덮어쓴다). 대응은 차단이 아니라 **가시성 + 복구**:
  - 세션 생성 대화상자 **안의 인라인 경고** (모달 없음, 추가 클릭 없음): "이 디렉터리에서 N개 세션 실행 중 — 같은 파일을 수정하면 변경이 유실될 수 있음". 읽고 계속 진행한다. (모달로 흐름을 끊는 것은 "막지 말고, 보이게 하라" 위반)
  - 실행 중에는 프로젝트 헤더에 "동시 세션 N개"를 상시 표시.
  - 두 세션이 **실제로 같은 파일을 수정한 것**이 감지되면(도구 호출 이벤트 기반) 경고 배지 + **복구 경로**: 도구 호출 이벤트에 남은 변경 전 내용으로 "이 파일의 이전 상태 보기"를 제공한다. Claude Code의 파일 체크포인트를 복구에 쓸 수 있는지는 M0에서 확인한다. 감지되는 시점엔 이미 늦었으므로, 경고보다 복구가 더 도움이 된다.
- (낮은 우선순위 옵션) 세션 생성 시 "워크트리에서 실행" 체크박스 — 원하는 사람에게는 격리를 제공. **2026-08-19 구현 완료.**
  - 위치는 **저장소 바깥** (`<data folder>/worktrees/<project>/<session>`). 저장소 안에 두면
    `.gitignore`에 한 줄을 추가해야 하고(우리가 사용자의 파일을 편집), 그러지 않으면 `git status`가 지저분해진다.
  - 브랜치는 `centralu/<first 8 chars of session id>`. 세션 이름은 생성 시점에 존재하지 않거나(자동 이름은 나중에 도착)
    공백과 유니코드가 섞여 있어 브랜치 이름으로 쓸 수 없다.
  - **git 저장소가 아니면 새로 만들지 않고 이유를 말한다.** 조용히 원본 디렉터리로 폴백하면
    사용자는 격리되었다고 믿고 두 세션을 같은 파일에 겨눈다 — 이 옵션을 켠 이유가 정확히 그것이다.
  - **resume과 앱 재시작은 같은 워크트리로 돌아온다** (경로를 DB에 보관).
  - 삭제할 때는 **묻는다**: 커밋되지 않은 변경 수와 경로를 보여주고, 체크박스를 요구한 뒤 삭제한다.
    에이전트가 몇 시간 동안 한 작업이 거기 놓여 있을 수 있다.

#### FR-3. GUI 에이전트 대화

- 채팅 스타일 UI: 사용자 메시지 / 에이전트 응답 (스트리밍 마크다운) / 도구 호출 카드 (기본 접힘, 펼치면 상세).
- 도구 호출 카드: 명령, 파일 경로, diff 요약을 구조화해 표시. raw 출력은 펼쳤을 때만. **접기 기본값은 도구 종류에 따라 다르다**: 읽기 중심 도구(Read/Grep/읽기 중심 Bash)는 접힘 — 연속으로 20개가 나와도 대화가 묻히지 않는다. 파일 변경(Edit/Write)은 diff 요약이 펼쳐진 상태가 기본. 설정에서 도구별로 조정 가능. (대화 뷰 가독성의 절반은 이 정책이다)
- 세션 제어: 중단, 재시도, 새 세션, 세션 이름 변경 (자동 이름은 FR-18).
- 메시지 입력: 여러 줄, 첨부(FR-13), 슬래시 명령 패스스루 (도구가 지원하는 경우).

**승인 인터랙션 상세 (가장 자주 쓰는 인터랙션 — 사용성이 여기서 결정된다):**

- **키보드 우선**: 승인 요청에 포커스가 있으면 `y` 허용 / `n` 거부 / `a` 항상 허용. 마우스 불필요. 버튼도 함께 표시.
- **"항상 허용"의 범위와 표현력**: 누르는 순간 범위를 보여준다 — 기본은 **세션 범위**, 수정 키(⌥a)로 프로젝트 범위. 어느 범위로 저장됐는지를 승인 카드에 기록한다. 패턴 규칙(예: `npm test*`)을 허용하되, 등록할 때 **현재 세션 히스토리에서 그 패턴에 매칭되는 명령 목록을 미리보기**로 보여준다. 전체 규칙은 설정에서 조회·삭제할 수 있다. 표현력을 제한하는 대신 결과를 보이게 한다.
- **포커스되지 않은 세션의 승인 요청**: 전역 알림 배너(창 상단)에 요청을 표시하고, **배너에서 바로 y/n 승인을 허용**한다. 다만 배너의 정보만으로 판단할 수 없는 요청 — 파일 편집(diff를 봐야 함), 다중 파일 조작, 잘려나가는 긴 명령 — 은 승인 버튼 대신 **"needs review"**를 표시하고, Enter로 해당 세션에 점프해 거기서 승인한다. 기준은 도구 종류별 기본값(Bash: 전체 명령이 보이면 그 자리에서 승인 가능 / Edit·Write: diff 확인 필요 → 점프)이며 설정에서 조정 가능. 이것은 강제가 아니라 **정보가 부족하다고 알려주는 것**이다.
- **승인 큐**: 승인이 여러 개 쌓이면 인박스(FR-15)에서 순서대로 처리 — 하나를 처리하면 자동으로 다음 승인으로 이동한다.
- 승인 요청 카드는 판단에 필요한 것을 요약한다: 전체 명령, 또는 파일 경로 + diff 미리보기.

#### FR-4. Git 상태 GUI

오른쪽 **근거 패널**에 위치하며, 탭은 **Git / History / Files / Terminal**이다 (실제 구현 기준 — 원래의 "3탭 git 패널"이 사용 중에 재편됨):

- **Git (changes)**: staged/unstaged/untracked 파일 목록; 파일을 클릭하면 diff 뷰. 에이전트가 파일을 바꾸면 실시간 갱신.
- **History**: git 패널 안의 스트립이 아니라 별도 탭 — 내장 스트립은 패널이 분할될 때 겹침을 일으켰고 제대로 된 그래프에 쓸 높이를 낼 수 없었다 (도그푸딩, 2026-08-26). 브랜치 레인이 있는 커밋 로그; 커밋을 클릭하면 변경 파일과 diff를 표시.
- **Branches**: 패널 헤더에서 연다 — 로컬 브랜치 목록, 현재 브랜치 표시, dirty 상태여도 체크아웃을 막지 않는다; **영향받을 파일을 먼저 보여준 뒤 진행할지 묻는다** (M2 결정: '막지 말고, 보이게 하라').
- **IDE로 점프**: diff나 파일 목록에서 해당 파일의 해당 줄을 기본 편집기로 연다. 왕복 비용을 줄이는 핵심 디테일.
- 구현: agent-host의 `git` CLI 래퍼 (M2에서 확정 — Rust git2로의 이전은 측정으로 병목이 확인될 때까지 보류).
- v1은 **읽기 중심**이다. commit/staging/push는 **v1.5로 확정** — 읽기 패널(M2)이 끝난 직후 같은 패널에 추가한다. rebase, cherry-pick 같은 고급 조작은 계속 non-goal.

#### FR-5. 프로젝트 파일 트리

- 탐색기 스타일 트리. **lazy-load** (연 디렉터리만 읽는다 — 큰 저장소에서도 가볍다).
- `.gitignore` 기반 필터 토글 (기본: ignored 숨김).
- Git 상태 오버레이 (M/A/U를 **글리프**로 표시 — 무채색 팔레트 결정에 따라 색을 쓰지 않는다).
- 에이전트가 최근 수정한 파일 강조 ("에이전트가 방금 만진 파일" 추적).
- **외부 변경을 감지한다** (issue #34, 2026-08-25 출시): 펼쳐진 디렉터리에만 비재귀 감시를 걸고
  300ms 간격으로 플러시 — 저장소 전체를 폴링하지 않고도 에이전트와 편집기가 디스크에 한 일을 트리가 따라간다.

#### FR-6. 코드 뷰어 (읽기 전용)

- 파일 클릭 → 구문 강조된 읽기 전용 뷰. 파일 내 검색, 줄 번호, 줄 링크 복사.
- diff 모드와 일반 모드 토글.
- 큰 파일은 가상 스크롤; 바이너리/이미지는 미리보기 또는 안내.
- 편집 없음 (non-goal). "IDE에서 열기" 버튼 (FR-4의 줄 단위 점프와 같은 메커니즘).

#### FR-7. 프로젝트별·세션별 도구 선택

- 세션 생성 대화상자에서 선택: **도구** (Claude Code / Codex) → **모델** → **권한 프리셋** (safe/normal/auto-approve) → 시작 프롬프트.
- **권한 프리셋은 CLI의 전역 설정을 세션 단위로 덮어쓴다** (M0에서 검증 — §2 참조). 사용자의 전역 bypass 설정과 무관하게, Centralu에서 만든 세션은 선택한 프리셋대로 동작한다.
- 모델·effort 메뉴는 도구가 노출하는 도구별 노브도 함께 다룬다: Claude effort 단계, **Codex `model_verbosity`** (issue #54, 2026-08-25 출시 — 실제 실행에서 출력 길이가 달라지는지 측정한 뒤 노출).
- 프로젝트별 기본값 저장 ("이 프로젝트는 기본이 Codex + gpt-5.x").
- 한 프로젝트 안에서 서로 다른 도구의 세션을 동시에 돌릴 수 있다 (예: Claude Code로 구현 + Codex로 리뷰).

#### FR-8. 가벼움 (핵심 비기능 요구사항 → 수치 목표는 §7)

- 구조는 Tauri + 가벼운 프런트엔드 + Node 사이드카 1개. 에이전트 CLI 프로세스는 세션이 있는 동안만 존재한다.
- 포커스 뷰 구조 자체가 성능에도 유리하다: 화면에 렌더해야 하는 세션이 하나뿐이므로 상시 렌더 부하가 그리드보다 낮다. 포커스되지 않은 세션은 상태와 안읽음 갱신을 위한 이벤트만 받는다.
- 파일 워처 디바운스, 폴링 대신 이벤트 구동.
- 목표 요약: 유휴 시 CPU ~0%, 앱 자체 메모리 수백 MB 미만. §7.1 참조.

#### FR-9. 에이전트 사용량 + 한도 상태

**출시된 것은 비용 대시보드가 아니라 한도 윈도우 뷰다.** 사용량 패널은 도구별 **구독 한도 윈도우**를 보여준다 — Claude의 5시간 + 주간 윈도우, Codex의 주간 윈도우 — 배열로 렌더하므로 도구에 새 윈도우가 생겨도 UI 변경이 필요 없다. 추가 결제 크레딧은 범위 밖이다.

- **한도 도달은 일급 상태다** (실사용에서 자주 만난다): 세션이 rate limit에 걸리면 세션 상태를 `limited`로 표시하고, 도구가 제공하는 한에서 **예상 리셋 시각**을 세션 헤더와 인박스에 보여준다.
- 원래의 주간 **비용** 대시보드(일별 막대, 프로젝트/모델별 분해, 추정 비용)는 미결로 남는다. 만들 경우 조사 결과는 여전히 유효하다: SDK로는 주간 집계가 불가능하므로(턴별 사용량만 제공, 구독 계정에는 plan-limit API 없음) **로그 파싱이 유일한 경로**다 — `~/.claude/projects/**` JSONL과 `~/.codex/sessions/**` token_count 이벤트를 SQLite에 증분 파싱으로 캐시. 그에 드는 시간이 가치가 있는지는 확정된 약속이 아니라 도그푸딩 시기의 판단이다.

#### FR-10. 재시작 시 복원

- 종료 시 워크스페이스 스냅숏 저장: 프로젝트 목록, 레이아웃, 프로젝트별로 열린 세션 ID·도구·이름·읽음 위치.
- 재시작 시:
  - UI와 레이아웃은 즉시 복원
  - 대화 기록은 로컬 로그/SQLite에서 즉시 로드 (먼저 읽기 전용으로 표시)
  - 세션 프로세스는 **resume이 가능한 곳에서는 resume** (Claude Agent SDK resume, `codex resume`); 불가능하면 "기록만 보기 + 새 세션 시작"을 제안
- 프로세스가 죽을 때 진행 중이던 에이전트 턴은 중단된다는 것을 명시한다 (복원은 "턴을 잇는 것"이 아니라 "대화를 잇는 것"이다).
- 크래시 안전성: 스냅숏은 종료 시가 아니라 상태가 바뀔 때마다 저장한다.

#### FR-11. 오케스트레이터 세션 (2026-08-25 구현, issues #13 · #30 — 이 절은 실제로 만들어진 것을 기술한다)

단일 워크스페이스 크라운 설계는, 대화 하나가 모든 프로젝트의 컨텍스트를 담을 수 없다는 것이 실사용에서 드러나면서 **계층 구조**로 바뀌었다:

- **Kind는 null 체크가 아니라 명시적 마커다**: 세션은 `kind: 'orchestrator'`이거나 일반 세션이다.
  **중앙 오케스트레이터** 하나(어느 프로젝트에도 속하지 않음)와, 선택적으로 **프로젝트당 오케스트레이터 하나**가 있다.
  범위는 중앙 > 프로젝트 > 세션 계층을 따른다: 중앙 오케스트레이터는 모든 것에 닿고, 프로젝트 오케스트레이터는
  자기 프로젝트의 세션에만 닿는다 (모든 도구 호출을 `inScope` 술어가 지킨다).
- 어떤 세션이든 자기 프로젝트의 오케스트레이터로 **승격**할 수 있다 (강등도 가능). 승격은 세션의 다음
  깨어남에 적용되며 cwd를 유지한다 — resume 히스토리는 역할 변경 후에도 살아남는다.
- 오케스트레이터는 **왕관 아이콘**으로 표시한다 (사이드바 버튼과 세션별 배지 — 2026-08-26 통일;
  무채색 규칙 유지: kind는 형태로, 긴급도는 밝기로).
- 호스트는 오케스트레이터 세션에 **선별된 도구**(세션 조회, 대화 읽기, 지시 전송,
  `create_session`, `update_session_settings`)와 **컴파일 시점에 내장된 앱 가이드**(overview/sessions/orchestrator/approvals/
  settings/updates)를 노출한다 — 런타임에 `docs/`를 읽지 않고 컴파일 시점에 내장하는데, 런타임 문서 읽기는
  한 단계 옆의 AGENTS.md류 인젝션 표면이기 때문이다.
- **권한 프리셋은 오케스트레이터의 settings 도구 스키마에서 의도적으로 표현할 수 없다** — 오케스트레이터가
  다른 세션의 승인 뒷문을 조용히 넓힐 수 있어서는 안 된다.
- `create_session`은 범위 안에서 동작한다; 설정 변경은 `settings_changed` 이벤트 + 토스트로 드러나서,
  오케스트레이터가 무엇을 바꾸는 순간 인간이 그것을 본다.
- 오케스트레이터가 보낸 지시는 대상 세션의 대화에 표시된다 (2026-08-26 구현): 말풍선 위의 출처 라벨과
  점선 테두리 — 팔레트 규칙에 따라 색이 아니라 형태로. 오케스트레이터 자신의 채팅에 오는 워커 완료 보고에도
  같은 마커가 붙는다. 스티키 배너에는 출처 이름이 접두로 붙는다.
- **폐기 (2026-08-27): 세션별 "오케스트레이터 지시 거부" 토글.** v0.4에서 안전장치 한 문장의 나머지 반쪽으로 적혔을
  뿐, 요청된 적도 아쉬웠던 적도 없다. 오케스트레이터를 만들고 그 범위를 정하는 사람과 이 스위치를 내릴 사람이 같은
  사람이라, 자기 관제탑의 지시를 거부하는 상황이 뒤에 없다. 어댑터에 적용한 규칙과 같다 — 설계 문장이 한때 다른
  것과 짝지어 놓았다는 이유가 아니라, 실제 사례가 관찰될 때 만든다. (여러 사람이 함께 쓰는 구성이라면 달라지지만,
  이 앱은 그런 앱이 아니다.)

#### FR-12. 대기 상태 표시 — 두 단계의 긴급도, 분리 (제어의 심장)

세션 상태 머신:

```
idle → working → (waiting_approval | waiting_input | limited | error) → working → …
```

| 상태 | 의미 | 긴급도 | 표시 |
|---|---|---|---|
| `working` | 에이전트 턴이 진행 중 | — | ⚙ 회전 |
| `waiting_approval` | **에이전트가 막혀 있다.** 내가 뭔가 누르지 않으면 아무 일도 일어나지 않는다 | **긴급** | 🔴 (+ 경과 시간) |
| `waiting_input` | 턴이 끝났다. 다음 지시가 없어도 해로울 것이 없다 | 긴급 아님 | 🔵 |
| `limited` | 사용량 한도에 막혀 리셋 시각을 기다리는 중 | 정보성 | ⏳ (+ 예상 리셋) |
| `error` | 프로세스 오류 등 | 긴급 | ⛔ |

- **`waiting_approval`과 `waiting_input`은 절대 같은 배지로 합치지 않는다.** 색, 아이콘, 정렬, 알림 정책 모두 분리한다.
- 전역 카운터도 분리한다: **"승인 2 · 응답 대기 3"** (합산된 "대기 5"는 금지).
- 표시 계층: ① 세션 행 상태 점 (사이드바) → ② 프로젝트 집계 → ③ 분리된 전역 카운터 (창 상단 고정) → ④ 독 아이콘 배지 / OS 알림 — 기본값: 승인과 오류는 즉시 알림, 응답 대기는 배지만. 대신 **모든 세션이 작업을 마쳤을 때(전부 대기/유휴) "all done" 알림 하나** — 자리를 비운 사람에게 필요한 신호는 개별 세션의 종료가 아니라 이것이다. (설정 가능)
- **"다음 대기 항목으로 가기"** 단축키: 승인 → 오류 → 응답 대기의 우선순위로 순회한다 (→ FR-17).
- 대기 경과 시간을 표시한다 ("3분째 대기 중").

#### FR-13. 파일 첨부 / 이미지 붙여넣기

- 클립보드에서 입력창으로 **이미지 붙여넣기** (스크린샷 워크플로), 파일 **드래그 앤 드롭**, 파일 선택 버튼.
- 프로젝트 안의 파일은 경로 참조(@path 멘션)로 전달; 외부 파일과 이미지는 도구가 지원하는 형태로 어댑터를 통해 전달한다.
- 전송 전 첨부 미리보기 (썸네일). 도구별 지원 차이는 어댑터가 보고하고 비활성화된 UI로 반영한다.

#### FR-14. 컨텍스트 사용량 표시

- 세션 헤더의 컨텍스트 게이지: 사용 토큰 / 컨텍스트 윈도우 (%). 스트리밍 usage 이벤트로 갱신.
- 임계값 경고 (예: 80%에서 게이지 색 변경 + "곧 압축/성능 저하가 올 수 있음" 툴팁).
- 압축(요약)이 일어나면 대화 뷰에 마커 표시.
- 도구가 정확한 수치를 주지 않으면 추정치임을 명시한다 (≈와 함께 표시).

### 4.2 사용성 리뷰에서 추가된 요구사항 (FR-15 ~ FR-19)

#### FR-15. 인박스 (트리아지 뷰) — 핵심 사용 루프의 입구

- 프로젝트 구조를 **무시하고**, 지금 내 개입을 기다리는 항목만 모으는 단일 목록.
- 정렬: 긴급도 우선 (승인 → 오류 → 응답 대기); 같은 긴급도 안에서는 대기 시작 시각 오름차순.
- 각 항목: 세션 이름, 프로젝트, 대기 종류, 경과 시간, 마지막 내용 한 줄 미리보기.
- 항목 선택 → 해당 세션의 포커스 뷰로 점프; 처리(승인/응답)가 끝나면 **자동으로 다음 항목으로 이동**.
- **`d` (dismiss)**: 응답 대기 항목을 읽고, 만족스러우면 키 하나로 세션을 아카이브한다 (FR-20). **인박스를 비우는 일급 수단** — 이것이 없으면 응답 대기 항목이 계속 쌓여 몇 시간 안에 인박스가 쓸모없어진다.
- 인박스 열기/닫기 단축키 하나 (기본 `⌘I`). 앱 시작 시 대기 항목이 있으면 인박스를 먼저 보여준다.
- FR-1의 사이드바가 "지도"라면 인박스는 "할 일 큐"다. 책상에 돌아왔을 때의 진입점은 인박스다.
- §1.3 루프의 입구이므로 **M1 범위다**. 목록 하나라서 구현 부담도 작다 — 사이드바보다 먼저 필요할 수도 있다.

#### FR-16. 읽음/안읽음

- 세션 상태(working/waiting)와 **독립적으로**, "마지막으로 본 이후 새 내용이 있는가"를 추적한다.
- 세션별로 `last_read_seq`를 저장. 읽음 처리 조건: 포커스 뷰에서 스크롤이 최신에 도달했을 때, **또는 세션에 포커스된 채 3초가 지났을 때** — 짧은 응답은 스크롤이 생기지 않아, 보조 조건이 없으면 영원히 안읽음으로 남는다.
- 사이드바 세션 행에 안읽음 표시 (굵기/점). "에이전트가 5분간 혼자 일하고 끝냈다"는 `waiting_input` + **안읽음** — "결과를 확인하지 않은 세션"을 놓치지 않으려면 두 축이 모두 보여야 한다.
- 인박스의 응답 대기 항목 중에서는 안읽은 것을 앞에 놓는다.

#### FR-17. 키보드 전용 조작

전체 제어 루프가 마우스 없이 돌아야 한다. v1 기본 단축키:

| 동작 | 키 |
|---|---|
| 다음 대기 항목으로 가기 (우선순위 순회) | `⌘⇧A` (잠정) |
| 인박스 열기/닫기 | `⌘I` |
| 프로젝트 점프 | `⌘1`~`⌘9` |
| 프로젝트 내 세션 간 이동 | `j` / `k` (입력창에 포커스가 없을 때) |
| 승인 허용 / 거부 / 항상 허용 | `y` / `n` / `a` (⌥a: 프로젝트 범위) |
| 인박스에서 세션 아카이브 (dismiss) | `d` |
| 커맨드 팔레트 (프로젝트·세션·액션 검색) | `⌘K` |
| 입력창 포커스 / 벗어나기 | `Enter` / `Esc` |
| 탭 전환 (대화/파일/git/뷰어) | `⌘⇧1`~`⌘⇧4` |

- 단축키는 설정에서 변경 가능. 충돌 감지.

#### FR-18. 자동 세션 이름

- "Session 1, Session 2"는 프로젝트가 4개를 넘으면 식별이 불가능해진다. 첫 프롬프트 기반의 **자동 제목**을 기본으로 한다.
- Claude Code는 이미 자체적으로 세션 제목을 생성하므로 그대로 받는다. Codex처럼 지원하지 않는 도구는 첫 사용자 메시지 앞부분을 잘라 초기 이름으로 쓴다.
- 수동으로 이름을 바꾸면 자동 갱신을 멈춘다.

#### FR-19. 첫 실행 경험 (온보딩)

**오케스트레이터 먼저** (#63, 2026-08-27 — 폴더 먼저 흐름을 대체한다). 목표는 효율이
아니라 습관 형성이다: 첫 실행에서 오케스트레이터에게 물어보는 경험을 겪지 않은 사람은
나중에도 누르지 않고, 앱에 대한 질문은 제작자가 아니라 오케스트레이터에게 가야 한다.
정확히 두 정거장, 위저드 없음:

1. **소개 화면** (정말 처음인 설치본 — 프로젝트도 세션도 0개 — 에 딱 한 번): 앱이
   무엇인지 한 줄, 오케스트레이터의 역할 설명 한두 문장(눈에 띄게), 큰 에이전트 카드
   두 장 (Claude Code / Codex). **카드가 곧 도구 감지 표시다**: 준비된 도구는 활성
   카드, 안 된 도구는 어둡게 비활성 + "Not connected" + 상태별 처방(설치 명령 vs
   로그인 명령 — 앱이 로그인 플로를 대신하지 않는다) + 재감지 버튼. 준비된 카드를
   클릭하면 오케스트레이터가 돌 도구를 저장하고("나중에 바꿀 수 있다"를 화면에 적는다)
   통과한다. 프로세스는 **뜨지 않는다**.
2. **보통의 오케스트레이터 세션 화면**, 빈 상태. 대화 메시지가 0개인 동안 행동 지향
   추천 질문 3개(프로젝트 만들기 / 오케스트레이터의 능력 / 다중 세션 관제)를 큰
   카드로 보여주고, 탈출구("그냥 폴더 고르기" → 네이티브 피커 → 세션 생성 창)를 항상
   함께 둔다. 질문 클릭은 **즉시 전송**이고, 그 클릭(또는 입력창의 첫 마디)이 비로소
   오케스트레이터 프로세스를 띄운다 (지연 기동). 추천 질문은 온보딩 상태 머신이 아니라
   메시지 수의 함수이며, 입력창·사이드바·그리드는 내내 전부 쓸 수 있다.

프로젝트 생성 질문의 답은 행동으로 끝난다: 오케스트레이터의 `propose_project` 도구는
제안 카드를 띄울 뿐이고, 카드의 유일한 힘은 **사람의 네이티브 피커를 여는 것**이다 —
도구 스스로 폴더를 등록하는 길은 없다 (제안-후-사람-확인; §FR-11 보안 노트 참조).

#### FR-20. 세션 아카이브와 기록

- 아카이브 = 에이전트 프로세스 종료 + 사이드바와 인박스에서 제거. **대화 기록은 SQLite에 보존된다.**
- 아카이브된 세션은 프로젝트별 "Archive" 목록과 커맨드 팔레트에서 볼 수 있다. resume이 가능하면 그 자리에서 resume한다 (활성으로 복귀).
- FR-10(재시작 시 복원)은 **활성 세션만** 복원한다 — 아카이브는 복원 범위 밖이다.
- 진입점: 인박스에서 `d`, 세션 헤더 버튼, 커맨드 팔레트.

#### FR-21. 대화 내용 검색

- M1: 커맨드 팔레트(⌘K)에서 세션 이름과 프로젝트 검색.
- M2: 대화 **내용**의 전문 검색 (SQLite FTS, 아카이브 포함) — 며칠에 걸쳐 세션 4개를 굴리면 "그 얘기 어디서 했더라"는 반드시 나온다.

## 5. 화면 구성

### 5.1 메인 레이아웃: 사이드바 + 포커스 뷰

관찰(왼쪽, 밀도 높게)과 조작(오른쪽, 전체 폭)의 분리. 그리드가 아니다.

```
┌──────────────────────────────────────────────────────────────────┐
│ ⌘ Centralu    [🔴 2 approvals · 🔵 3 awaiting]  [usage] [＋]     │
├────────────────┬─────────────────────────────────────────────────┤
│ ▾ project A    │  auth refactor (Claude · main · ctx 42%)        │
│   🔴 auth ref  │ ┌───────────────────────────────────────────┐   │
│   ⚙ fix tests  │ │                                           │   │
│ ▾ project B    │ │   conversation stream (full width —       │   │
│   🔵 API rev • │ │   it can actually be read)                │   │
│ ▾ project C    │ │  ┌─ approval request ─────────────────┐   │   │
│   ⏳ migration │ │  │ Bash: npm run build                │   │   │
│ ▾ project D    │ │  │ [y allow] [n deny] [a always]      │   │   │
│   ⚙ gen docs   │ │  └────────────────────────────────────┘   │   │
│                │ └───────────────────────────────────────────┘   │
│  (• = unread)  │  [input box + attachments]                      │
│                │  [conversation | files | git | viewer]          │
└────────────────┴─────────────────────────────────────────────────┘
```

- 사이드바: 프로젝트/세션 트리, 상태 점 (🔴 승인 / 🔵 응답 대기 / ⚙ 작업 중 / ⏳ 한도 / ⛔ 오류 / 👑 오케스트레이터), 안읽음 점, 브랜치와 변경 수 요약. 접을 수 있다.
- 포커스 뷰: 세션 하나가 전체 폭. 하단 탭으로 파일 트리/git/뷰어 전환 — 전체 폭에서는 각 탭이 실제로 쓸 만한 크기가 된다.

### 5.2 인박스 (⌘I)

```
┌─ inbox ── 2 approvals · 0 errors · 3 awaiting ──────────────────┐
│ 🔴 auth refactor (A)  Bash approval        4m    "npm run…"     │
│ 🔴 migration (C)      file write approval  1m    "schema…"      │
│ 🔵 API review (B) •   awaiting · unread    12m   "review done…" │
│ 🔵 gen docs (D)       awaiting            25m    "README…"      │
└─────────────────────────────────────────────────────────────────┘
```

- Enter로 점프 → 처리 → 자동으로 다음 항목으로. 루프가 끝나면 "inbox empty ✓".

### 5.3 보조 화면

- **사용량 대시보드**: 주간 막대 차트(일별), 도구/모델/프로젝트별 분해, 추정 비용, 한도 윈도우 상태.
- **세션 생성 대화상자**: 도구 → 모델 → 권한 프리셋 → 시작 프롬프트. 동시 세션 경고 포함 (FR-2).
- **설정**: 도구 경로/감지 상태, 기본 프리셋, 알림 정책(상태별), 단축키, 테마, **외관 — 5단계 텍스트 스케일** (2026-08-26; OS 디스플레이 배율처럼 화면 전체를 스케일하되, 최소 폭과 그리드 열 계산은 실제 픽셀에 고정).

### 5.4 그리드 뷰 (**experimental**)

원래 v1에서 제외되어 있었다. 이유는 세 가지였다:

1. 14인치 화면에서 2×2는 패널당 ~600×400px — 대화 스트림, 입력창, 탭을 넣으면 어느 것도 제대로 볼 수 없다.
2. "다음 대기 항목으로 가기" 루프(한 번에 하나씩 처리)와 인터랙션 모델이 충돌한다.
3. 멀티 프로젝트 요구사항은 사이드바(상시 관찰) + 키보드 전환(즉시 조작)으로 충족된다.

**2026-08-20: 결정이 바뀐다.** 그리드는 이미 만들어져 돌아가고 있었다 — 그런데 이 문서만
"만들지 않는다"고 말하고 있었고, 화면에도 아무 표시가 없었다 (issue #25). 제거하는 대신 **experimental 표시를 달고 출시한다.**

셋 중 **1과 2는 그대로 유효하다.** 죽은 이유가 아니라 살아 있는 이유로서 여기 유지한다:

- **1** — 폭에서 열 수를 계산하는 것(`columnsFor`)으로 패널이 최소 폭 아래로 떨어지는 것은 막았다.
  하지만 그리드에는 **오른쪽 근거 패널이 없다**: 화면이 이미 나뉘어 있는데 거기서 레인을 하나 더
  떼어내면 쓸 수 없는 폭이 남는다. 대화는 볼 수 있지만 "그게 정말 그랬나"는 볼 수 없다.
- **2** — ⌘⇧A(다음 대기 항목으로 가기)는 세션을 고르고 **화면을 포커스 뷰로 되돌린다.**
  한 번에 하나를 처리하는 루프와 여러 개를 동시에 보여주는 화면은 아직 화해하지 못했다.
- **3** — 여전히 참이다. FR-1을 충족하는 것은 사이드바이고, 그리드는 그 위에 얹힌 **또 하나의 보는 방식**이다.

그래서 표시는 화면 안이 아니라 **사이드바의 Grid 버튼**에 붙는다 (#1의 오케스트레이터와 같은
처방: slate 텍스트 + 점선 테두리, 색도 밝기도 쓰지 않는다). 다만 이유는 다르다 — #1은
모르고 누르는 것을 막으려던 것이지만, 그리드는 자유롭게 누를 수 있고 되돌릴 수 있다. 비싼 것은
그 안에서 보내는 시간이며, 그리드가 열려 있는 동안에도 사이드바는 가려지지 않으므로 표시 하나가 **누르기 전과
사용 중 내내**를 모두 커버한다.

표시가 화면을 얼려버린 것은 아니다: 표시가 붙은 이후로 그리드에는 패널을 같은 DOM 노드로 옮기는
드래그 재정렬(대화 스크롤이 살아남는다), 회전하는 working 테두리(§7.1의 측정 비용에 포함됨),
텍스트 스케일 아래에서도 버티는 실제 픽셀 열 계산이 더해졌다. **Experimental은 빌드 품질이 아니라
위의 미해결 반론 두 가지를 가리킨다.** 대형 모니터 사용자를 위한 옵션으로 v2에서 재검토한다.

## 6. 시스템 아키텍처

### 6.1 프로세스 구조

실제 구현에서 Rust 셸은 처음 그림보다 **얇아졌고** Node 호스트가 **더 많이 소유한다** — 셸은 감독하고,
호스트가 일하며, UI는 dev와 prod에서 동일한 WebSocket 하나로 호스트와 대화한다
(상세는 [architecture.ko.md](architecture.ko.md)):

```
┌─────────────────────────── Tauri app (Rust) ──────────────────────────┐
│  · window/tray/notifications      · sidecar supervisor                │
└──────────────────────────────┬────────────────────────────────────────┘
                               │ WebSocket (same protocol dev and prod)
┌──────────────────────────────┴────────────────────────────────────────┐
│                      Node sidecar (Agent Host)                        │
│  · ClaudeAdapter (Claude Agent SDK)   · CodexAdapter (app-server RPC) │
│  · common event normalisation         · orchestrator tools (FR-11)    │
│  · git CLI wrapper (FR-4)             · file tree IO + dir watchers   │
│  · SQLite (~/.centralu/store.db — sessions, messages, workspace)      │
└──────┬──────────────────────────┬─────────────────────────────────────┘
       │                          │
  Claude Code sessions       Codex sessions   (processes exist only while sessions do)
```

### 6.2 공통 어댑터 인터페이스 (확장의 심장)

```ts
interface AgentAdapter {
  createSession(opts: { cwd, model?, permissionPreset?, resumeId? }): SessionHandle
  send(sessionId, input: { text, attachments?: Attachment[] }): void
  respondApproval(sessionId, requestId, decision: 'allow'|'deny'|'always',
                  scope?: 'session'|'project'): void
  interrupt(sessionId): void
  dispose(sessionId): void
  // The adapter → app direction is normalised into a single event stream:
  // message_delta | tool_call | tool_result | approval_request
  // | turn_complete | usage_update | context_update | state_change
  // | limit_reached | session_title | error
  events: EventStream<NormalizedEvent>
}
```

- UI는 `NormalizedEvent`만 안다. 도구별 차이(승인 메커니즘, 사용량 형식, resume 메커니즘)는 어댑터 내부에서 흡수한다.
- 어댑터는 **capability 선언**을 제공한다: `{ approvals: boolean, contextUsage: 'exact'|'estimate', resume: boolean, autoTitle: boolean }` — UI는 이를 바탕으로 기능을 켜고 끈다 (예: 승인을 덮어쓸 수 없는 도구는 승인 UI를 숨김).
- v2에서 Gemini CLI 등을 추가한다는 것은 새 어댑터 하나를 쓰는 것, 그 이상이 아니다.

### 6.3 데이터 모델 (SQLite)

- `projects(id, path, name, default_tool, default_model, sidebar_order, …)`
- `sessions(id, project_id, tool, external_session_id, name, auto_named, state, is_orchestrator, verbosity, archived, last_read_seq, created_at, …)` — `kind`는 `is_orchestrator` + `project_id`에서 파생된다 (중앙 vs 프로젝트 오케스트레이터, FR-11)
- `messages(session_id, seq, role, kind, payload_json, ts)` — 복원용 대화 캐시 (+ FTS5 인덱스, M2). 한 행은 스트리밍 델타가 아니라 **메시지 하나**다 (#66): 스트리밍 중에는 열린 메시지의 행을 제자리에서 갱신하고(주기 flush), 닫힐 때 한 번 색인한다. 읽기는 델타 시절의 행도 병합하므로 마이그레이션 전 데이터도 같게 동작한다.
- `approval_rules(scope, project_id?, session_id?, matcher, decision, created_at)` — "항상 허용" 규칙
- `usage_facts(date, tool, model, project_id, input_tokens, output_tokens, cache_tokens, cost_est)` — 증분 집계
- `workspace(id, layout_json, updated_at)` — 스냅숏

## 7. 비기능 요구사항

### 7.1 성능·에너지 목표 ("가벼움"의 수치화)

| 지표 | 목표 |
|---|---|
| 유휴 시 CPU (세션 4개 유휴) | ≈ 0% (측정치 < 1%) |
| 앱 메모리 (프로젝트 4개, 세션 4개, 에이전트 프로세스 제외) | < 400MB |
| 콜드 스타트 → 워크스페이스 복원 완료 | < 3s |
| 스트리밍 중 UI 프레임 | 60fps 유지 (가상화 리스트) |
| 에너지 | macOS 활성 상태 보기의 에너지 영향을 "낮음"으로 유지 (스트리밍 중 제외) |

달성 방법: 이벤트 구동(폴링 없음), **포커스 뷰 단일 렌더**(포커스되지 않은 세션은 상태와 안읽음만 갱신), lazy 파일 트리, 워처 디바운스, 가상화된 대화 리스트.

**2026-08-26 측정** (perf 스위트, `pnpm perf` — WebKit, 프로덕션 엔진): 유휴 브라우저 프로세스 CPU
0.1–0.2%, React 커밋 0회; 세션이 *working*일 때 3.3% (포커스) / 4.0% (그리드, 패널 4개). working
수치는 그날까지 24.4% / 32.9%였다 — 스피너가 등록된 커스텀 프로퍼티를 통해 conic-gradient의 각도를
애니메이션하고 있었고, 이는 매 프레임 메인 스레드에서 리페인트한다; 지금은 미리 래스터화한 플레이트를
transform으로 회전시키며, 컴포지터가 소유한다. 이 교훈을 여기 기록하는 이유는 §7.1 원칙의
상시 부하 버전이기 때문이다: **아무 일도 없을 때 화면이 하는 일이 곧 배터리 청구서다.** perf 스위트
(`e2e/perf-idle.spec.ts`, `e2e/perf-grid.spec.ts`)는 판정이 아니라 숫자를 출력한다.

### 7.2 기타

- **오프라인/장애 내성**: 어댑터 프로세스 크래시 시 세션 상태를 `error`로 옮기고 + 원클릭 재시작. 앱 크래시 시 스냅숏에서 복원.
- **보안**: API 키를 직접 다루지 않는다 — 각 CLI 자체의 로그인(키체인)을 그대로 쓴다. 앱 DB에 시크릿을 저장하지 않는다.
- **플랫폼**: macOS 우선(개발 머신), 구조는 크로스 플랫폼 유지(Tauri).
- **언어**: 한국어 우선 UI, 문자열을 분리해 영어 추가가 쉽도록.
